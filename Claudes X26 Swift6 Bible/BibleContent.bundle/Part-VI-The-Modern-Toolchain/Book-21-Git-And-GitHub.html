VI.21.2  Why Version Control

VI.21.2 ¶1 Every file in your project has a history. Without version control, you have one copy of each file and whatever Time Machine remembered last night. With Git, every saved state is a named point you can return to, compare against, or share.

VI.21.2 ¶2 Git is the version control system. GitHub is one of several places to host Git repositories on the internet. You can use Git locally without ever talking to GitHub; you start needing GitHub (or something like it) when you want to sync across machines or collaborate.

VI.21.3  The Mental Model

VI.21.3 ¶1 Git tracks three places your files can live:

VI.21.3 ¶2
  1. Working tree -- the files you see and edit on disk.
  2. Staging area (index) -- files you've marked as "I want these changes in the next commit."
  3. Repository -- the stored history of past commits.

VI.21.3 ¶3 A typical change flow:

VI.21.3 ¶4
  • You edit a file. It lives only in the working tree.
  • git add thefile.swift moves that change from the working tree into the staging area.
  • git commit moves the staged changes into the repository as a single named snapshot.

VI.21.3 ¶5 You can stage many files at once and commit them together. Each commit is a whole-project snapshot: everything tracked, at a moment in time.

VI.21.4  Cloning a Build-Along Repo (Xcode 26 Step-by-Step)

VI.21.4 ¶1 Every Build-Along chapter in this book assumes the reader can pull the matching repo down from GitHub and open it in Xcode. This section is the step-by-step for doing exactly that, using Xcode 26's built-in Clone Git Repository flow. No Terminal required.

VI.21.4.1  Opening Xcode for the First Time

VI.21.4.1 ¶1 Launch Xcode from the Applications folder, the Dock, Launchpad, or Spotlight (Cmd-Space, type "Xcode," press Return). The first thing Xcode shows is the Welcome screen.

VI.21.4.1 ¶2 If Xcode is already open and the Welcome screen has been dismissed, bring it back with Window → Welcome to Xcode in the menu bar, or the keyboard shortcut Cmd-Shift-1.

VI.21.4.2  The Welcome Screen

VI.21.4.2 ¶1 The Welcome screen has three primary actions on the left and a list of recent projects on the right.

VI.21.4.2 ¶2 The three actions:

VI.21.4.2 ¶3
  • Create New Project — starts from one of Xcode's templates (App, Framework, Multiplatform App, etc.).
  • Clone Git Repository — pulls an existing project from a Git host (GitHub, GitLab, Bitbucket, a self-hosted server) using its repository URL.
  • Open Existing Project — opens a project that's already on disk.

VI.21.4.2 ¶4 For a Build-Along chapter, the second option is the entry point.

VI.21.4.3  Clone Git Repository — Step by Step

VI.21.4.3 ¶1
  1. Click "Clone Git Repository" on the Welcome screen. A dialog appears asking for the repository URL.
  2. Paste the repo URL into the field. Every Build-Along chapter prints the URL near the top of the chapter, in the form https://github.com/fluhartyml/{ProjectName}.git. The .git suffix is optional — Xcode accepts the URL with or without it.
  3. Click "Clone." Xcode shows a save panel asking where the project should land on disk.
  4. Pick a destination folder. The default is the home folder. Many readers keep a top-level ~/Developer/ folder for cloned projects; that's the convention this book uses, but the location doesn't affect the build — pick whatever stays organized.
  5. Click "Clone" in the save panel. Xcode reaches out to GitHub, downloads the repo, and opens the project in a new window. The first clone of any given repo takes a few seconds; subsequent clones of the same repo are nearly instant because Git reuses cached objects.

VI.21.4.3 ¶2 Public repos clone without authentication. Private repos prompt for GitHub credentials the first time — Xcode stores the token in the system keychain for future clones.

VI.21.4.4  Where the Project Lands

VI.21.4.4 ¶1 The cloned repo lands as a folder inside the chosen destination. The folder name matches the repo name from the URL. Inside, the structure is whatever the project author committed: an .xcodeproj bundle, a README.md, a .gitignore, source folders, a .git directory (hidden in Finder; visible to ls -la in Terminal) containing the full history.

VI.21.4.4 ¶2 Xcode opens the .xcodeproj automatically when the clone finishes. The folder on disk is the working tree from this chapter's mental model; the .git subdirectory is the repository.

VI.21.4.5  Building and Running the Cloned App

VI.21.4.5 ¶1
  1. Wait for Xcode to finish indexing. The activity indicator in the toolbar shows "Indexing…" briefly. Code completion and Quick Help don't fully work until indexing finishes — a small project takes a few seconds, a larger one a minute or two.
  2. Pick a run destination from the scheme menu in the toolbar (the field just to the right of the Run / Stop buttons). For most Build-Along apps this is an iPhone or iPad simulator that matches the chapter's target device.
  3. Press Cmd-R (or click the Run button). Xcode builds the project and launches it in the chosen simulator. The first build is slower than later builds because Xcode is compiling from scratch and caching artifacts in ~/Library/Developer/Xcode/DerivedData/.
  4. Read along. The Build-Along chapter walks through the source while the running app demonstrates the behavior. Stopping (Cmd-Period) and starting (Cmd-R) is cheap once the first build is cached.

VI.21.4.6  Updating a Cloned Repo Later

VI.21.4.6 ¶1 When the upstream repo on GitHub gains new commits and the reader wants to pull them down into the local clone, the path inside Xcode is Integrate → Pull… in the menu bar. Xcode shows the changes and brings them in. The Terminal equivalent is git pull from the project directory.

VI.21.4.6 ¶2 For Build-Along chapters tied to specific versions of the source, the chapter notes a tag (for example v1.0.0 or book-snapshot-2026-05-10). Checking out a specific tag is covered in the Tags and Releases section later in this chapter.

VI.21.5  Creating a Repository

VI.21.5 ¶1 From the project directory in Terminal:

VI.21.5 ¶2
cd ~/Developer/MyApp
git init
git add .
git commit -m "Initial commit"

VI.21.5 ¶3 What just happened:

VI.21.5 ¶4
  • git init created a hidden .git/ folder, which is the repository.
  • git add . staged every file in the current directory.
  • git commit took that snapshot with the message "Initial commit."

VI.21.5 ¶5 Xcode also has a "Create Git repository" checkbox when you make a new project. Either path gets you to the same place.

VI.21.6  .gitignore for Xcode Projects

VI.21.6 ¶1 A .gitignore file tells Git which paths to never track. Xcode generates a lot of user-specific junk that doesn't belong in shared history. A good starting .gitignore:

VI.21.6 ¶2
# macOS
.DS_Store
.AppleDouble
.LSOverride

# Xcode -- user-specific
xcuserdata/
*.xcuserstate
*.xcscmblueprint

# Xcode -- builds
build/
DerivedData/

# Swift Package Manager
.swiftpm/
Packages/
Package.resolved

# CocoaPods / Carthage (if you use them)
Pods/
Carthage/Build/

# Secrets
*.env
*.env.local

VI.21.6 ¶3 Drop that at the repo root before the first git add .. Files already tracked aren't automatically untracked by adding them here; that needs git rm --cached.

VI.21.7  Making Commits as You Work

VI.21.7 ¶1 The everyday cycle:

VI.21.7 ¶2
# See what changed
git status

# Stage specific files
git add Sources/ContentView.swift

# Or stage everything tracked
git add -u

# Commit
git commit -m "Wire up Home tab"

VI.21.7.1  Good Commit Messages

VI.21.7.1 ¶1
  • Imperative mood: "Add sidebar toggle," not "Added sidebar toggle" or "Adds sidebar toggle."
  • Short subject (under ~60 chars).
  • Optional body explaining why, not what -- the diff shows what.
  • One logical change per commit. Don't mix a bug fix with a feature; make two commits.

VI.21.8  Branches

VI.21.8 ¶1 A branch is a named line of history. The default name is main (older repos use master).

VI.21.8 ¶2
# Create and switch to a new branch
git checkout -b feature/import-csv

# Do work, commit, etc.

# Switch back to main
git checkout main

# Merge the branch in
git merge feature/import-csv

# Delete the merged branch
git branch -d feature/import-csv

VI.21.8 ¶3 A feature in progress shouldn't sit in main until it's done. Branches keep main shippable while experiments live off to the side.

VI.21.9  GitHub -- The Remote

VI.21.9 ¶1 GitHub is where your local repo lives on the internet. "Remote" is Git's word for "a copy of this repo somewhere else." The default remote name is origin.

VI.21.9.1  Create and Link a Remote Repo

VI.21.9.1 ¶1 On GitHub, create an empty repository (no README, no .gitignore -- let the local one be the source of truth). Copy the HTTPS or SSH URL.

VI.21.9.1 ¶2
git remote add origin https://github.com/yourname/MyApp.git
git branch -M main
git push -u origin main
VI.21.9.1 ¶3
  • git remote add registers the URL under the name origin.
  • git branch -M main renames the current branch to main (in case your local default is different).
  • git push -u origin main uploads the main branch and remembers the association (-u = "upstream").

VI.21.9.2  Everyday Push / Pull

VI.21.9.2 ¶1
# Grab the latest from GitHub (when someone else committed)
git pull

# Push your commits
git push

VI.21.10  Pull Requests

VI.21.10 ¶1 A pull request (PR) is GitHub's way of saying "I'd like my branch merged into yours; here's the diff, please review."

VI.21.10 ¶2 Typical flow:

VI.21.10 ¶3
  1. Create a branch locally and push it to GitHub.

VI.21.10 ¶4 ``bash git checkout -b feature/export-pdf # ... commits ... git push -u origin feature/export-pdf ``

VI.21.10 ¶5
  1. On GitHub, click "Compare & pull request."
  2. Fill in the title and description. Link related issues.
  3. Reviewers comment. You push follow-up commits to the same branch; the PR updates automatically.
  4. Merge when approved.

VI.21.10 ¶6 For a solo-developer repo, PRs are still useful: they force you to look at the full diff before merging, which catches things you wouldn't see in individual commits.

VI.21.11  Tags and Releases

VI.21.11 ¶1 Tags are named pointers to a specific commit. You use them to mark releases.

VI.21.11 ¶2
git tag v1.0.0
git push origin v1.0.0

VI.21.11 ¶3 On GitHub, navigate to Releases and cut a release from the tag. You can attach a built .ipa or .app binary, write release notes, and mark it prerelease or production.

VI.21.11 ¶4 Version tags usually follow semantic versioning: MAJOR.MINOR.PATCH. Bump MAJOR for breaking changes, MINOR for new features, PATCH for bug fixes.

VI.21.12  Undoing Things

VI.21.12.1  Undo Uncommitted Changes to a File

VI.21.12.1 ¶1
git checkout -- Sources/ContentView.swift

VI.21.12.1 ¶2 Resets that file to whatever was last committed. Be careful -- this loses your working changes.

VI.21.12.2  Undo a Commit You Haven't Pushed

VI.21.12.2 ¶1
git reset --soft HEAD~1

VI.21.12.2 ¶2 Moves HEAD back one commit but keeps the changes staged. You can fix them and recommit.

VI.21.12.3  Undo a Pushed Commit

VI.21.12.3 ¶1
git revert <commit-sha>

VI.21.12.3 ¶2 Creates a new commit that undoes the old one. Safe because history stays linear; nobody has to rebase their work.

VI.21.12.3 ¶3 Never use git push --force on a shared branch. It rewrites history and breaks every other clone of that branch.

VI.21.13  The Xcode Source Control Integration

VI.21.13 ¶1 Xcode has a Source Control menu that does the common Git operations through GUI. You can:

VI.21.13 ¶2
  • View history per file with Source Control > History.
  • Compare working changes against the last commit via the Changes tab in the navigator.
  • Commit from Source Control > Commit (⌥⌘C).
  • Push and pull from Source Control > Push / Pull.

VI.21.13 ¶3 The GUI is fine for day-to-day work. Drop to Terminal for anything unusual -- interactive rebases, surgical resets, tag management. The CLI is more powerful; the GUI is faster for the common case.

VI.21.14  Chapter Mini-Example -- First Push to GitHub

VI.21.14 ¶1 Walk through exactly what to type the first time you put a new Xcode project on GitHub.

VI.21.14 ¶2
# 1. Go to the project
cd ~/Developer/MyApp

# 2. (If Xcode didn't already) initialize Git
git init

# 3. Drop a .gitignore at the repo root (paste the template from earlier)
# 4. Check what Git sees
git status

# 5. Stage everything
git add .

# 6. First commit
git commit -m "Initial commit"

# 7. On GitHub: create an empty repo named MyApp, copy its URL.
# 8. Wire up the remote (HTTPS example)
git remote add origin https://github.com/yourname/MyApp.git
git branch -M main

# 9. First push
git push -u origin main

VI.21.14 ¶3 Refresh the GitHub repo page. Your code is up. Every future commit is one git push away from being backed up.
