Appendix E: ActivityKit (User's Manual)

Status: Public framework, iOS 16.1+ / iPadOS 17.0+, with Apple Watch and CarPlay surfaces added in 2024 and broadcast support in 2025. Not available on native macOS — the lock screen and Dynamic Island that ActivityKit draws to don't exist on Mac. Apps that build for both iOS and native macOS need #if canImport(ActivityKit) guards around every reference. See Book 13's "Cross-Platform" section and Appendix C's "Platform availability and the Mac build" for the pattern. ActivityKit is Apple's framework for Live Activities — the small, persistent UI that lives on the lock screen and in the Dynamic Island while something is in progress. A sports score that's still updating, a delivery driver on the way, a workout timer counting up: anything time-bounded the user wants to glance at without unlocking the device.

When to reach for it

Reach for ActivityKit when there's a real-time activity the user wants to track from outside the app — one with a clear start, an end the user is waiting for, and updates in between. The activity has to have an end. ActivityKit explicitly refuses indefinite content: it's not a notification, it's not a widget, it's an in-progress view.

Don't reach for ActivityKit for content that doesn't change ("today's weather"), for content with no end ("currently playing music" — that's MPNowPlayingInfoCenter), or for purely ambient state. If there's nothing for the user to wait for, ActivityKit isn't the right tool.

Three pieces an activity needs

Every Live Activity has three pieces:

  • A type that conforms to ActivityAttributes. This holds the static data — the parts that don't change over the life of the activity. A pizza order's number, the addresses for pickup and dropoff, the customer's name. The nested ContentState holds the dynamic data — the parts that update.
  • A widget extension that includes a Widget conforming to ActivityConfiguration<Attributes>. The widget defines the lock-screen and Dynamic Island UI for the activity.
  • A call from the app to Activity.request(attributes:content:pushType:) to start the activity, and follow-up calls to activity.update(_:) and activity.end(_:dismissalPolicy:) to advance and finish it.

The attributes type

import ActivityKit

struct DeliveryAttributes: ActivityAttributes {
    typealias DeliveryStatus = ContentState

    struct ContentState: Codable, Hashable {
        var driverName: String
        var minutesAway: Int
        var stage: Stage

        enum Stage: String, Codable, Hashable {
            case preparing, onTheWay, arrived
        }
    }

    var orderNumber: String
    var restaurantName: String
}

The outer struct (orderNumber, restaurantName) is fixed for the life of the activity. The inner ContentState (driverName, minutesAway, stage) is what the app pushes updates to. Both must be Codable and Hashable, and both must be small — the system enforces a payload cap.

The widget configuration

Inside the widget extension, the activity gets a configuration that maps states to views for each surface:

struct DeliveryLiveActivity: Widget {
    var body: some WidgetConfiguration {
        ActivityConfiguration(for: DeliveryAttributes.self) { context in
            DeliveryLockScreenView(context: context)
        } dynamicIsland: { context in
            DynamicIsland {
                DynamicIslandExpandedRegion(.leading) { ... }
                DynamicIslandExpandedRegion(.trailing) { ... }
                DynamicIslandExpandedRegion(.center) { ... }
                DynamicIslandExpandedRegion(.bottom) { ... }
            } compactLeading: {
                Text(context.state.minutesAway, format: .number)
            } compactTrailing: {
                Image(systemName: "bicycle")
            } minimal: {
                Image(systemName: "bicycle")
            }
        }
    }
}

The first closure is the lock-screen banner. The dynamicIsland closure declares four regions for the expanded view (leading, trailing, center, bottom) and three small views for the collapsed states (compact leading, compact trailing, minimal). The system picks which one to show based on what else is competing for the island at the time.

Starting, updating, ending

let attributes = DeliveryAttributes(orderNumber: "A412", restaurantName: "Mario's")
let initial = DeliveryAttributes.ContentState(
    driverName: "Sam",
    minutesAway: 18,
    stage: .preparing
)

let activity = try Activity.request(
    attributes: attributes,
    content: .init(state: initial, staleDate: nil),
    pushType: nil
)

try await activity.update(
    .init(
        state: DeliveryAttributes.ContentState(
            driverName: "Sam",
            minutesAway: 9,
            stage: .onTheWay
        ),
        staleDate: Date().addingTimeInterval(60 * 5)
    )
)

try await activity.end(
    .init(
        state: DeliveryAttributes.ContentState(
            driverName: "Sam",
            minutesAway: 0,
            stage: .arrived
        ),
        staleDate: nil
    ),
    dismissalPolicy: .default
)

request starts the activity. update pushes a new ContentState. end closes it — the activity stays visible for a short grace period (the dismissalPolicy) before the system removes it.

Stale dates

A staleDate on a content update tells the system when the data should be considered out of date. After the stale date passes, the system can dim the activity or stop showing it in the Dynamic Island until a fresh update arrives. Stale dates are how an activity tells the system "if you don't hear from me by 7:42 PM, this number isn't trustworthy anymore."

Push updates

Activities can be updated from a server with no app launch required. Set pushType: .token when requesting the activity and the system gives back a push token the app forwards to the server. The server then sends APNs payloads that update the activity in place. The payload format is documented separately in ActivityKit's "Updating live activities with ActivityKit push notifications" article. Push updates are the only way to keep an activity current while the app is suspended — the alternative is local timers that won't fire when the app isn't running.

Authorization

Live Activities are off by default in Settings. The app can read ActivityAuthorizationInfo().areActivitiesEnabled to check the user's preference, and request throws if activities are disabled. There's no separate permission prompt — the user toggles the master switch in Settings > Notifications > (App) > Live Activities.

The watch and CarPlay surfaces

Starting in 2024, a Live Activity also shows up on a paired Apple Watch in the Smart Stack, and in CarPlay during navigation or media playback. The widget extension's activity configuration drives both surfaces; no extra code is required, but the views need to render correctly at the watch's screen size and within CarPlay's safety constraints (no animations, limited interactivity).

What's new in 2025

  • Broadcast Live Activities. A single activity can be shared with all of a user's followers (sports app, news app), updated server-side, and dismissed in bulk. The activity is keyed on a topic the user subscribes to, not on an installed app instance.
  • Interactive activities with App Intents. Buttons inside the Dynamic Island and lock-screen banner can invoke an AppIntent directly — "pause," "resume," "mark delivered" — without launching the app.
  • Tighter alignment with the new design system. The lock-screen banner inherits the Liquid Glass material; widget views inside the activity should reach for .glassEffect() only on top-level surfaces, not on nested controls (see Appendix B — CryoKit for the "no glass on glass" rule and the broader material guidance).

Common mistakes

  • Putting mutable data in the outer attributes type. The outer attributes are fixed for the life of the activity. Anything that changes belongs in ContentState.
  • Forgetting the dismissal policy. .default keeps the activity visible briefly after end. .immediate removes it at once. .after(Date) keeps it visible until a specific moment. Pick deliberately — the default is rarely wrong, but the immediate dismissal is sometimes preferable for activities that should clear when the user is done.
  • Animating heavy content in the Dynamic Island. The island is performance-constrained. Static content with one or two animated SF Symbols looks crisp; full-bleed animations stutter or get truncated.
  • Skipping the stale date. An activity with no stale date that stops receiving updates looks "stuck" — the numbers freeze but the UI keeps showing them. Even a conservative stale date (5 minutes out) lets the system soften the display when data goes cold.
