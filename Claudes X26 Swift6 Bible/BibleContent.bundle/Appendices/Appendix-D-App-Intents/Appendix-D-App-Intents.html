Appendix D: App Intents (User's Manual)

Status: Public framework, iOS 16.0+ / iPadOS 16.0+ / macOS 13.0+, with substantial additions through iOS 26. App Intents is Apple's framework for letting other parts of the system — Shortcuts, Spotlight, Siri, the Action Button, widgets, focus filters, control center — run pieces of your app without launching the full UI. Each thing an app can do is described as an AppIntent type. The system reads those types, indexes them, and exposes them everywhere the user might want to reach for them.

When to reach for it

Reach for App Intents whenever the user might want to do something your app can do without opening your app first. "Start a timer," "create a record," "show me today's items," "log a workout" — any verb your app already implements is a candidate. The same intent code surfaces in Shortcuts, in Spotlight results, in Siri, on the lock screen, in widgets, in interactive notifications, and in the new system snippet UI. Writing the intent once and letting the system route it is the whole point.

Don't reach for App Intents when the action is purely visual and needs the full UI to make sense — a long form, a multi-step wizard, a video editor. Those belong inside the app. App Intents handles the verbs that can be expressed as a single self-contained operation.

The core type

An App Intent is a Swift type that conforms to AppIntent. The type carries a static title, an optional description, the parameters the intent needs, and a perform() method that does the work. perform() is async and throwing, and it returns an IntentResult describing what happened.

import AppIntents

struct AddRecordIntent: AppIntent {
    static let title: LocalizedStringResource = "Add Record"
    static let description = IntentDescription("Adds a record to OPerationsHOS.")

    @Parameter(title: "Title") var recordTitle: String
    @Parameter(title: "Type") var type: RecordTypeEntity

    func perform() async throws -> some IntentResult & ProvidesDialog {
        let store = OperatorStore.shared
        let item = store.add(title: recordTitle, type: type.rawType)
        return .result(dialog: "Added \(item.title).")
    }
}

The conformance tells the compiler this type is reachable from the system. The static title is what the user sees in Shortcuts and Siri. perform() is where the work happens.

Parameters

An @Parameter wrapper turns a stored property into a typed slot that the system can ask the user to fill in. Strings, numbers, dates, durations, URLs, files, and any custom AppEntity or AppEnum are valid parameter types.

Parameters carry a title string and optionally a description, a default value, an inputOptions set, and a requestValueDialog for the prompt the system shows when the parameter is missing. The wrapper handles all the UI plumbing — the developer only declares the type.

App Entities

An AppEntity is a strongly typed reference to one of the app's records. It exposes an id, a displayRepresentation, and (often) a defaultQuery. Entities let the system show meaningful pickers ("Which record?" rather than "Type a UUID") and let one intent pass its result into the next intent in a Shortcut.

struct RecordEntity: AppEntity {
    let id: UUID
    let title: String

    static let typeDisplayRepresentation: TypeDisplayRepresentation = "Record"
    static let defaultQuery = RecordQuery()

    var displayRepresentation: DisplayRepresentation {
        DisplayRepresentation(title: "\(title)")
    }
}

struct RecordQuery: EntityQuery {
    func entities(for identifiers: [UUID]) async throws -> [RecordEntity] {
        OperatorStore.shared.records(matching: identifiers).map { record in
            RecordEntity(id: record.id, title: record.title)
        }
    }

    func suggestedEntities() async throws -> [RecordEntity] {
        OperatorStore.shared.recent(limit: 10).map { record in
            RecordEntity(id: record.id, title: record.title)
        }
    }
}

App Enums

An AppEnum is a Swift enum that the system can present as a parameter picker. Each case gets a DisplayRepresentation, and the type declares a typeDisplayRepresentation for the parameter prompt.

Result types

The perform() return type composes one or more roles from a small set of protocols: ProvidesDialog for a spoken or written response, ReturnsValue for a piece of typed data that flows into the next intent, ShowsSnippetView for a small custom SwiftUI view to display in the result, and OpensIntent for opening the app to a particular destination. Composing the protocols with & lets one intent return all the shapes the system might use.

App Shortcuts

An AppShortcutsProvider declares a list of AppShortcut entries that ship with the app. Each shortcut wraps one intent, gives it a set of natural-language phrases, an SF Symbol, and a short description. Apple-provided shortcuts appear in the Shortcuts app the first time the user launches the app — no user setup required.

struct OperatorShortcuts: AppShortcutsProvider {
    static var appShortcuts: [AppShortcut] {
        AppShortcut(
            intent: AddRecordIntent(),
            phrases: [
                "Add a record to \(.applicationName)",
                "Log this in \(.applicationName)"
            ],
            shortTitle: "Add Record",
            systemImageName: "plus.rectangle"
        )
    }
}

The \(.applicationName) token resolves to the app's display name at runtime, so the same shortcut works on every device and in every locale.

What's new in 2025

Three additions are worth knowing about in the WWDC25 cycle:

  • SnippetIntent — a dedicated intent shape whose only job is returning a small SwiftUI view to be shown inline in the system snippet UI. Use it when the user wants a status read-out rather than an action: "What's on my schedule today" returns a snippet, not a side effect.
  • UndoableIntent — an intent that records its own undo. The system surfaces an Undo affordance after the intent runs, and a corresponding undo() method on the intent type reverses the change. Adopt it for any intent whose effect the user might regret immediately.
  • supportedModes — declares which surfaces an intent is appropriate for: Shortcuts only, Siri only, both, or neither. The default is "all surfaces," but actions that only make sense as voice commands (or only as Shortcuts steps) can narrow themselves explicitly.

Where the intent shows up

Once an AppIntent type is in the binary, the system indexes it. The same intent then surfaces in:

  • Shortcuts — the user can string the intent into a multi-step shortcut, possibly across multiple apps.
  • Spotlight — the intent appears as an actionable result when the user searches for its title or one of its phrases.
  • Siri — the intent runs when the user speaks one of its phrases.
  • Action Button (iPhone 15 Pro and later) — assignable as the button's action.
  • Control Center — with a matching ControlWidget, the intent runs from a custom control.
  • Widgets — an interactive widget can invoke the intent on tap.
  • Focus filters — the system can adjust the app's behavior per focus mode by running a configuration intent.

The framework's promise is "write the action once, run it from anywhere the user expects to reach it." That promise mostly holds. The places it doesn't hold are usually places where the action requires a UI step that App Intents can't express — in which case OpensIntent is the escape hatch: the intent opens the app to the right place and the user finishes there.

Common mistakes

A handful of mistakes show up over and over:

  • Forgetting typeDisplayRepresentation on an AppEntity or AppEnum. The compiler accepts the type, but the parameter picker is empty or unlabeled at runtime.
  • Doing heavy work directly in perform(). The system runs the intent in an extension-like context with a tight time budget. Use the intent to dispatch work to the app's actor, return a dialog, and let the rest run inside the app.
  • Hardcoding strings instead of LocalizedStringResource. Titles, dialogs, and parameter prompts all need LocalizedStringResource to localize properly — otherwise the App Intents extractor warns and Shortcuts shows English everywhere.
  • Treating an intent as a method. Each AppIntent type is one verb. Resist the urge to add a switch inside perform() to make one type cover three actions — the system can't surface them separately and the user can't pick between them in Shortcuts.
