Appendix C: AlarmKit (User's Manual)

Status: Public framework, iOS 26.0+ / iPadOS 26.0+ / Mac Catalyst 26.0+. AlarmKit is Apple's framework for scheduling system-level alarms and timers from a third-party app. Alarms scheduled with AlarmKit appear on the Lock Screen and in the Dynamic Island, ring with the system alarm sound, and override the device's focus and silent mode. They behave like Clock-app alarms, but they're authored by your app.

When to reach for it

Reach for AlarmKit when the user expects an alarm — a prominent alert that fires whether or not your app is running, whether or not the screen is on, whether or not the user has Do Not Disturb enabled. Cooking timers, medication reminders, reservation alerts, calibration windows: anything where missing the moment is the failure mode.

Don't reach for AlarmKit when a quiet notification will do. UNUserNotificationCenter remains the right tool for non-urgent reminders that should respect focus modes. AlarmKit is louder by design.

Apple's Clock app does not expose its own timers and alarms to other apps. There is no public API to read or modify a person's existing Clock-app entries. AlarmKit is the framework for creating new alarms that look and act like Clock-app alarms, not for reading or editing the ones already there.

Authorization

AlarmKit needs the user's permission before it will schedule anything. Two pieces have to be in place:

  • An NSAlarmKitUsageDescription key in the app's Info.plist, with a string explaining why the app schedules alarms. The string appears in the system permission prompt. If the key is missing or its value is empty, AlarmKit refuses to schedule.
  • A runtime call to AlarmManager.shared.requestAuthorization(), which is async and throwing, returning an AlarmManager.AuthorizationState.

The state enum has three cases: .authorized, .denied, and .notDetermined. If the user denies, every later schedule attempt fails until they grant access in Settings.

If the app skips the explicit authorization request, AlarmKit asks on the user's behalf the first time the app calls schedule(id:configuration:). That's a convenience, not a substitute — explicit requests give the app a chance to explain itself before the system prompt appears.

The shared instance

AlarmKit centers on a singleton: AlarmManager.shared. The whole framework hangs off it — scheduling, cancelling, pausing, resuming, observing. There is no other entry point.

Three ways to configure an alarm

An alarm is built by passing an AlarmManager.AlarmConfiguration<Metadata> to schedule(id:configuration:). The configuration has three creation paths, each tuned for a different shape of alert:

  • Traditional alarm — AlarmManager.AlarmConfiguration.alarm(schedule:attributes:stopIntent:secondaryIntent:sound:). Fires at a date you specify. The morning wake-up case.
  • Countdown — AlarmManager.AlarmConfiguration.init(countdownDuration:schedule:attributes:stopIntent:secondaryIntent:sound:). Shows a countdown UI on the Lock Screen leading up to the alert. The pre-alert countdown duration is configurable.
  • Timer — AlarmManager.AlarmConfiguration.timer(duration:attributes:stopIntent:secondaryIntent:sound:). Starts immediately, runs for the specified TimeInterval, alerts at the end. The kitchen-timer case.

Schedule types

For traditional alarms, the Alarm.Schedule type controls when the alarm fires. The relative form — Alarm.Schedule.Relative — takes a Time(hour:minute:) and a recurrence rule.

The recurrence rule is one of two cases: .never (a one-shot) or .weekly([Locale.Weekday]) (a weekly cadence on the listed weekdays). The weekday array uses Swift's Locale.Weekday enum, which respects the user's locale.

Presentations

An alarm can be in three states from the user's perspective: alerting (currently ringing), counting down (a pre-alert countdown is running), or paused (the user paused a running countdown). Each state has a corresponding presentation type:

  • AlarmPresentation.Alert — required. Carries the title, the stop button, and an optional secondary button.
  • AlarmPresentation.Countdown — optional. Used when a countdown duration is configured. Carries the title and a pause button.
  • AlarmPresentation.Paused — optional. Used when the user pauses a running countdown. Carries the title and a resume button.

The three presentations are wrapped in an AlarmAttributes<Metadata> together with a tintColor and any custom metadata. The tint color associates the alarm visually with the originating app and helps the user tell different apps' alarms apart on the Lock Screen.

Buttons and intents

The buttons in the alert UI come from AlarmButton. The framework includes built-in .stopButton, .pauseButton, .resumeButton, .repeatButton, and .openAppButton styles, each tied to a system behavior.

The secondary button can do one of two things, controlled by AlarmPresentation.Alert.SecondaryButtonBehavior:

  • .countdown — a Repeat action. The alarm re-triggers after a postAlert interval defined in the countdown duration.
  • .custom — an Open action that launches the app, with the actual work handled by an App Intent the app provides via secondaryIntent.

Both stopIntent and secondaryIntent on the configuration accept any type conforming to LiveActivityIntent. App Intents are how AlarmKit hands control back to the app when the user taps a button.

State control

Once an alarm is scheduled, the manager has five methods for changing its state, all keyed by Alarm.ID and all throwing:

  • cancel(id:) — remove the alarm from the system entirely.
  • countdown(id:) — trigger a countdown for an alarm currently alerting (used by the secondary button when its behavior is .countdown).
  • pause(id:) — pause an alarm in the countdown state.
  • resume(id:) — resume a paused alarm.
  • stop(id:) — stop a currently-alerting alarm without cancelling it (alarm stays scheduled for any future fires).

Observing alarms and authorization

AlarmKit exposes two async sequences for staying in sync with the system:

  • alarmUpdates: some AsyncSequence<[Alarm], Never> — emits the full list of alarms whenever any of them changes (scheduled, fired, paused, dismissed). The standard pattern is to spin a Task at view-model init and update local state from each emission.
  • authorizationUpdates: some AsyncSequence<AlarmManager.AuthorizationState, Never> — emits when authorization changes (user grants or revokes in Settings).

There's also a synchronous alarms: [Alarm] property and an authorizationState: AuthorizationState property for one-shot reads.

Critical pitfalls

Three things can quietly break an AlarmKit integration. Each is documented in Apple's reference, but each is the kind of detail that's easy to miss until alarms aren't firing in production.

Pitfall 1 — Alarms get deleted from the daemon when they fire. If the app needs to know whether a one-shot alarm has already fired, it has to persist its own copy and diff against manager.alarms. An alarm missing from that array is an alarm that already fired.
Pitfall 2 — A widget extension is required for any alarm that uses a countdown presentation. Without it, the system may dismiss alarms unexpectedly and fail to alert. The widget extension hosts the countdown Live Activity that AlarmKit drives. Apple's sample project includes one as a separate target named AlarmLiveActivity; an app shipping AlarmKit countdowns needs the same.
Pitfall 3 — The Info.plist key is load-bearing. Missing or empty NSAlarmKitUsageDescription means scheduling silently fails. The key must be present and have a non-empty string value.

Related frameworks

  • ActivityKit — the framework that powers Live Activities. AlarmKit's countdown and paused presentations are Live Activities under the hood. Apps shipping AlarmKit countdowns need a widget extension that uses ActivityKit's ActivityAttributes protocol — the same AlarmAttributes the app passes to AlarmManager.
  • App Intents — the framework behind stopIntent and secondaryIntent. The intents conform to LiveActivityIntent so they can run from the alert UI on the Lock Screen.
  • UserNotifications — the older, quieter alternative. Use it when an urgent system-overriding alert would be wrong for the moment.

Sample project

Apple ships a sample project demonstrating one-time alarms, weekly recurring alarms, and timers, including the required widget extension for countdown Live Activities. It's the right starting point for an AlarmKit integration.
