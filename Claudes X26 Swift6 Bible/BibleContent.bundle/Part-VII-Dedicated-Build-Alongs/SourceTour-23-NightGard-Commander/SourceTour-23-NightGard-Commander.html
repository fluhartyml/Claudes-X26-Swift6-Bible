Source Tour 23: NightGard Commander (Self-Publishing Case Study)

Status: self-distributed, notarized. Mac app, descendant of Midnight Commander and Norton Commander. The book's primary case study for the third distribution path: notarized self-publishing, neither App Store nor TestFlight.

A file manager that needs to browse the whole disk by definition cannot live inside the App Store sandbox. NightGard Commander ships notarized with full disk access — the right call for an app whose value is exactly "see and act on everything." Source: github.com/fluhartyml/NightGard-Commander. See Book 21 Git-And-GitHub for the clone workflow.

What NightGard Commander shows at production scale

  • Two-pane file manager UI — source and destination panes visible simultaneously, keyboard-driven, descended directly from Midnight Commander's three-decade-tested layout
  • The production-hardened Shazam stack — Service, Queue, Session Delegate, Scanned Database, Settings, Results Dialog, Settings Panel. Eight files of production-tuned audio-fingerprint workflow that Library Commander now ports rather than rebuilds (see Source Tour 22).
  • Notarized self-publishing — how a Mac app gets distributed outside the App Store and still passes Gatekeeper, gets the user's trust on first launch, and updates without going through Apple's review queue.
  • Differentiation against Finder — Finder has tabs in 2026, but tabs aren't side-by-side. Commander's value is spatial awareness: source and destination visible at the same time for batch workflows like "compare two album folders, copy the missing tracks across."

Why this app cannot live in the App Store sandbox

The Mac App Store sandbox restricts apps to specific user-granted directories. A file manager whose whole purpose is browsing arbitrary locations on disk cannot work under that restriction. The user would be confronted with permission prompts on every directory navigation, the app would lose its ability to compare paths it doesn't have current grants for, and the workflow value (spatial awareness across the whole filesystem) would evaporate.

Apple is explicit about this in their developer guidance: file managers, system utilities, developer tools, and similar "see and act on everything" apps are appropriate candidates for unsandboxed notarized distribution. NightGard Commander is a textbook member of that category. The rejection conversation never even starts because the submission would be wrong from the first frame.

The notarized-self-publish flow

Self-publishing a Mac app for distribution outside the App Store is roughly four steps once the binary is built:

  1. Code-sign with a Developer ID Application certificate (codesign --sign "Developer ID Application: Your Name" --options=runtime ...). The Developer ID certificate is the same Apple Developer Program membership the App Store uses, just configured for outside-the-store distribution.
  2. Wrap the app in a DMG or zip for distribution.
  3. Submit to Apple's notarization service (xcrun notarytool submit). Apple's automated scan checks for malware signatures and confirms the signing chain. Notarization is not App Review; it's a security check that takes minutes, not days.
  4. Staple the notarization ticket to the binary (xcrun stapler staple) so Gatekeeper can verify offline. Without stapling, Gatekeeper has to phone home on first launch; with the ticket stapled, the app launches instantly even on a network-isolated Mac.

The user installs the notarized DMG, drags the app to /Applications, and on first launch sees the Gatekeeper prompt confirming Apple verified the developer's identity. After that, the app launches like any App Store app. Updates ship by replacing the binary in /Applications; there is no auto-update infrastructure unless the developer builds one (Sparkle is the standard third-party framework for that).

The production-hardened Shazam stack

Commander's Shazam stack is the most ported piece of architecture in the NightGard family. Eight files in the app target:

  • ShazamService — the public API surface other code calls into
  • ShazamQueue — rate-limit-respecting work queue (Apple's Shazam servers throttle aggressive batch use; the queue is what keeps the app from getting blocked)
  • ShazamSessionDelegate — the SHSession callback handler that resolves match results into the queue
  • ShazamScannedDatabase — persistent record of what's already been Shazamed, so re-running a batch doesn't re-fingerprint files that already have results
  • ShazamSettings + ShazamSettingsPanel — user-configurable rate-limit and batch-size knobs
  • ShazamResultsDialog + BatchShazamDialog — the user-facing UIs for kicking off batches and viewing results

The lesson the apartment memory captures (in feedback_shazam_rate_limit.md and reference_nightgard_commander_shazam.md) is direct: do not re-implement this stack in another app from scratch. Apple's Shazam servers rate-limit batch use aggressively, and getting the queue's pacing wrong invites server-side timeouts that look indistinguishable from real failures. Library Commander ports this stack verbatim rather than reinventing it; that discipline is the right call for any future app in the family that needs Shazam at batch scale.
