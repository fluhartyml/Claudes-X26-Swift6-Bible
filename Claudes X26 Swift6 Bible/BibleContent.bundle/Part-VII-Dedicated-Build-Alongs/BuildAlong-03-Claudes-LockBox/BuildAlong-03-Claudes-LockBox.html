Build-Along 03: Claudes LockBox

A locked personal vault for cards, codes, photos, and notes. Face ID gate, three-column NavigationSplitView, SwiftData-backed model, VisionKit document scanner, PhotosPicker, camera capture, share sheets, and a pinch-to-zoom image viewer. From an empty Xcode project to a submitted App Store build in a single sitting on 2026 April 16. The chapter follows the actual git commit timeline of that build — ten commits across roughly four hours, each one a small forward step you can mirror in your own copy. Source: github.com/fluhartyml/Claudes-LockBox.

Creating the Project

1.1 Open Xcode 26. The Welcome screen shows three options on the left and your recent projects on the right. Click Create New Project.

1.2 The template picker appears. Across the top is a row of platform tabs — Multiplatform, iOS, macOS, watchOS, tvOS, visionOS, DriverKit, Other. Pick Multiplatform. Under Application, pick App. Click Next.

1.3 Fill in the project details:

  • Product Name: Claudes LockBox
  • Team: Your Apple Developer account name (e.g., "Michael Fluharty")
  • Organization Identifier: com.ClaudeX26Bible (whatever fits your developer account; this never changes after submission)
  • Bundle Identifier: Xcode builds this automatically as com.ClaudeX26Bible.Claudes-LockBox. This is how Apple tells your app apart from every other app in the world — once it ships, the bundle ID is locked forever (see Build-Along 01 Section 15 for why this matters).
  • Testing System: Swift Testing with XCTest UI Tests (the default is fine)
  • Storage: SwiftData — LockBox's whole job is storing the user's vault items, so SwiftData is the natural pick
  • Host in CloudKit: Leave unchecked. We are not syncing across devices for v1.0; the vault stays local. iCloud sync can be added later as a v1.x feature without breaking the existing data model.

The Folder and VaultItem Models

3.1 LockBox's data layer is two SwiftData models: Folder (a category like Cards or Notes) and VaultItem (an individual entry like "Visa ending 4242"). Both go in their own files.

3.2 Right-click the Claudes LockBox group in the navigator and choose New File from Template. Pick Swift File, name it Folder.swift. Replace the file's contents with:

import Foundation
import SwiftData

@Model
final class Folder {
    var name: String
    var iconName: String
    var dateCreated: Date
    var sortOrder: Int

    @Relationship(deleteRule: .cascade, inverse: \VaultItem.folder)
    var items: [VaultItem] = []

    init(name: String, iconName: String = "folder.fill", sortOrder: Int = 0) {
        self.name = name
        self.iconName = iconName
        self.dateCreated = Date()
        self.sortOrder = sortOrder
    }
}

3.3 Three things to notice. @Model is the SwiftData macro that turns a plain class into a persisted record — Swift generates the boilerplate for storing properties, tracking changes, and integrating with the model context. The @Relationship macro tells SwiftData that a Folder owns its items: when you delete a Folder, every VaultItem that pointed at it is deleted too (deleteRule: .cascade). The inverse parameter points at the matching property on VaultItem — SwiftData uses that to keep both sides of the relationship in sync.

3.4 Now create VaultItem.swift the same way:

import Foundation
import SwiftData

@Model
final class VaultItem {
    var title: String
    var notes: String
    var pin: String
    var dateCreated: Date
    var dateModified: Date

    @Attribute(.externalStorage)
    var imageData: [Data] = []

    var folder: Folder?

    init(title: String, notes: String = "", pin: String = "",
         folder: Folder? = nil) {
        self.title = title
        self.notes = notes
        self.pin = pin
        self.dateCreated = Date()
        self.dateModified = Date()
        self.folder = folder
    }
}

3.5 The interesting line is @Attribute(.externalStorage) var imageData: [Data] = []. SwiftData stores small properties inline in its database file. Photos are large — embedding them inline would bloat the database and slow every query. The .externalStorage attribute tells SwiftData to write photo data to separate files on disk and keep only references in the database row. The reader still sees a plain [Data] array; SwiftData handles the indirection.

3.6 Notice folder: Folder? — the inverse side of the cascade relationship from Section 3.3. A VaultItem can exist without a folder (briefly, during creation); a folder can have many items.

The App Entry Point and ModelContainer

4.1 SwiftData needs to know which models to persist and where. The app entry point is where you wire that up. Open Claudes_LockBoxApp.swift.

4.2 Replace the template's contents with:

import SwiftUI
import SwiftData

@main
struct Claudes_LockBoxApp: App {
    var sharedModelContainer: ModelContainer = {
        let schema = Schema([
            Folder.self,
            VaultItem.self,
        ])
        let modelConfiguration = ModelConfiguration(
            schema: schema,
            isStoredInMemoryOnly: false
        )

        do {
            return try ModelContainer(
                for: schema,
                configurations: [modelConfiguration]
            )
        } catch {
            fatalError("Could not create ModelContainer: \(error)")
        }
    }()

    var body: some Scene {
        WindowGroup {
            LockScreenView()
        }
        .modelContainer(sharedModelContainer)
    }
}

4.3 The Schema lists every @Model type the app persists. Adding a new model later means adding it here too — if you forget, queries for that type silently return nothing. The ModelConfiguration with isStoredInMemoryOnly: false persists to disk; setting it true is useful for tests where you want a fresh database every run.

4.4 The WindowGroup { LockScreenView() } says the app's first scene is the lock screen, not the content. We will write that view in the next section. The .modelContainer modifier injects the SwiftData environment so every child view can access @Query and modelContext.

The Lock Screen with Face ID

5.1 Face ID lives in the LocalAuthentication framework. Create a new Swift file named LockScreenView.swift:

import SwiftUI
import LocalAuthentication

struct LockScreenView: View {
    @State private var isUnlocked = false
    @State private var authError: String?
    @Environment(\.scenePhase) private var scenePhase

    var body: some View {
        if isUnlocked {
            ContentView()
                .onChange(of: scenePhase) { _, newPhase in
                    if newPhase == .background {
                        isUnlocked = false
                    }
                }
        } else {
            VStack(spacing: 30) {
                Image(systemName: "lock.shield.fill")
                    .font(.system(size: 80))
                    .foregroundStyle(.blue)

                Text("LockBox by Claude")
                    .font(.system(size: 28, weight: .bold))

                Text("Tap to unlock")
                    .font(.system(size: 18))
                    .foregroundStyle(.secondary)

                if let authError {
                    Text(authError)
                        .font(.system(size: 18))
                        .foregroundStyle(.red)
                }

                Button {
                    authenticate()
                } label: {
                    Label("Unlock with Face ID", systemImage: "faceid")
                        .font(.system(size: 20, weight: .semibold))
                        .padding(.horizontal, 30)
                        .padding(.vertical, 14)
                        .background(.blue)
                        .foregroundStyle(.white)
                        .clipShape(RoundedRectangle(cornerRadius: 12))
                }
            }
            .frame(maxWidth: .infinity, maxHeight: .infinity)
            .background(Color(.systemBackground))
            .ignoresSafeArea()
            .onAppear {
                authenticate()
            }
        }
    }

    private func authenticate() {
        let context = LAContext()
        var error: NSError?

        if context.canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics,
                                      error: &error) {
            context.evaluatePolicy(
                .deviceOwnerAuthenticationWithBiometrics,
                localizedReason: "Unlock your vault"
            ) { success, authenticationError in
                if success {
                    isUnlocked = true
                    authError = nil
                } else {
                    authError = "Authentication failed"
                }
            }
        } else if context.canEvaluatePolicy(.deviceOwnerAuthentication,
                                              error: &error) {
            context.evaluatePolicy(
                .deviceOwnerAuthentication,
                localizedReason: "Unlock your vault"
            ) { success, _ in
                if success { isUnlocked = true }
                else { authError = "Authentication failed" }
            }
        } else {
            isUnlocked = true   // simulator path
        }
    }
}

5.2 The view has two states: unlocked shows the main content; locked shows the unlock prompt. The state lives in @State private var isUnlocked.

5.3 The @Environment(\.scenePhase) observation is what makes this screen actually secure. .onChange(of: scenePhase) watches for the app going to .background and flips isUnlocked back to false. The next time the user opens the app, they have to authenticate again. Without that line, the app would stay unlocked across the whole life of the process — a significant security hole for a vault.

5.4 The authenticate() function tries three paths in order: Face ID / Touch ID, then device passcode if biometrics aren't available, then a simulator-only direct unlock as a last resort so the build is testable in Xcode previews. The system framework handles the actual biometric prompt; we just trigger it.

5.5 Before this view runs on a real device, you have to add a Face ID usage description to the project. Open Info.plist (or the Info tab on the project file) and add a key NSFaceIDUsageDescription with a value like "Unlock your vault with Face ID." Without it, the app crashes the first time it tries to authenticate — iOS requires the explanation string before invoking the biometric prompt.

The Sidebar and Three-Column Layout

7.1 LockBox uses a three-column NavigationSplitView. On iPhone, the columns stack as you drill in (Folders → Items in Folder → Item Detail). On iPad and Mac, all three columns can show side by side.

7.2 Replace the template ContentView.swift with a NavigationSplitView structure that hosts a sidebar (folder list), a content view (items in the selected folder), and a detail view (the selected item). The SidebarView.swift and ItemListView.swift and ItemDetailView.swift files in the repo are the three columns. The chapter does not paste each one verbatim — they are larger SwiftUI files that read most cleanly in Xcode where syntax coloring helps. Open them in the cloned repo as you read this section.

7.3 The sidebar's @Query attribute on folders: [Folder] with sort: \.sortOrder is the first concrete win of the SwiftData choice from Section 1.3. The sidebar redraws automatically whenever a Folder is added, deleted, or renamed — you do not write any of the synchronization plumbing yourself.

The Cards Workflow: Document Scanner Integration

8.1 The first end-to-end vertical slice the build went after was the Cards folder workflow. The commit at 11:21 AM captures the moment it first all worked end-to-end. Quoting the commit message:

Cards workflow is built: Tap + in Cards → document scanner opens; Scan front, flip card, scan back → tap Save; New Item form appears with scanned thumbnails showing; Type the card name, add a PIN if needed, notes if needed → Save; Tapping an existing card opens the detail view; Tap any thumbnail → full-size viewer with share button (email, AirDrop, etc.); Long-press a thumbnail → View Full Size or Delete Page; Add more pages anytime with the Scan button in the detail view.

8.2 Scanner integration lives in DocumentScannerView.swift. It's a UIViewControllerRepresentable that wraps Apple's VNDocumentCameraViewController from the VisionKit framework — the same system controller covered in detail at Source Tour 20 (Snap & ScanKeeper). The bridge pattern is identical; the difference is what LockBox does with the result.

8.3 When the scanner finishes, its didFinishWith scan: VNDocumentCameraScan callback fires. LockBox reads each page from scan.pageCount as a UIImage, converts each to JPEG Data at 0.85 compression, and hands the array of Data values to a New Item form via a @Binding. That binding is what feeds the photo strip in the form below.

8.4 The new-item-form-after-scan flow uses a fullScreenCover, not a .sheet. The reason for that choice is in Section 10 below — it was the third of three polish fixes that landed in a single commit later in the build day.

Bug Fixed at 11:34 — Two Refinements

9.1 Right after the Cards flow first worked, two small problems surfaced. The commit message for 11:34 AM captures both:

1. Thumbnail transfer — fixed the timing so scanned images properly pass to the New Item form. 2. Button layout — icons centered above labels (Library, Camera, Scan) instead of inline text wrapping.

9.2 The thumbnail transfer fix is small but worth understanding. Initially, the scanner-completion handler captured the page images and then dismissed itself. The New Item form showed up with no thumbnails because the array was passed by value at the moment the scanner completed, before the form mounted. The form's binding read its own (empty) initial state instead of the scanner's freshly-captured images.

9.3 The minute-later commit at 11:39 AM nails the actual fix:

Yes — the thumbnails were missing because the scanned images weren't being passed correctly to the form. The fix changes initialImages from a plain value to a @Binding, so the New Item form reads the scanned pages directly from the source instead of getting a stale copy.

9.4 The @Binding change is the textbook SwiftUI fix for "this view sees stale data": instead of receiving a value the parent had at construction time, receive a two-way connection to the parent's source-of-truth and read it on every render. Worth committing to memory — this exact pattern recurs constantly in SwiftUI codebases.

Polish Pass at 11:48 — Three Fixes

10.1 The 11:48 AM commit message lists three small fixes that together took the app from "works" to "feels finished":

1. Letterboxing — lock screen now fills the full display, no black bars. 2. Duplicate title — removed the navigation title from the detail view since the editable title field already serves that purpose. 3. Keyboard crushing — New Item form now uses fullScreenCover instead of .sheet, giving the keyboard room.

10.2 The letterboxing fix was a single .ignoresSafeArea() on the lock screen background. SwiftUI's default behavior keeps content within the safe area; for an immersive full-screen lock view, that produces a band of unused space at top and bottom. The modifier extends the background under the system bars.

10.3 The duplicate-title fix is a polish detail worth naming explicitly. The detail view had both a navigation title (system-drawn at the top of the screen) and an editable title field (in the form below). Both showed the same text. Removing the navigation title removes the redundancy without losing functionality — the editable field is the source-of-truth, and the user reads it there directly.

10.4 The keyboard-crushing fix is the most consequential. SwiftUI's .sheet takes the bottom 60-something percent of the screen when presented at .medium detent. With a software keyboard up, that leaves maybe 200 vertical points of usable space. .fullScreenCover covers the entire screen, so the keyboard pushes content up but does not have to fight with the sheet's height. The form is genuinely usable on iPhone. .fullScreenCover for forms with required keyboard input is a pattern worth reusing.

The Pinch-to-Zoom Image Viewer

11.1 The 12:24 PM commit added a real photo viewer for the scanned card images. Quoting the commit message:

The fix I just built adds: Pinch to zoom in and out; Double-tap to toggle between fit-to-screen and 3x zoom; Drag to pan when zoomed in; Snap back to fit-to-screen if you pinch below 1x; Black background for the viewer.

11.2 ImageViewerView.swift in the repo holds the implementation. The structure is a ZStack with a black Rectangle background and an Image centered on top. Three gesture modifiers attach to the image:

  • MagnificationGesture drives a scale state with a clamp at 1x (snap back if the user pinches below) and 5x (cap if they pinch beyond)
  • DragGesture updates an offset state, but only when scale > 1 — panning a fit-to-screen image is meaningless
  • onTapGesture(count: 2) toggles between scale 1.0 and 3.0 with withAnimation(.spring()) for a tactile snap feel

11.3 The pinch-below-1x snap-back behavior is what makes this feel like a polished system viewer rather than a math-strict gesture handler. Users naturally over-pinch when "closing" a zoom; without the snap-back, they'd land at 0.7x scale and be confused. The clamp logic is a five-line guard inside the MagnificationGesture's onChanged; a small detail, big UX payoff.

Folder Consolidation: Codes/Accounts + Photos Picker

12.1 The 12:54 PM commit reduced the folder roster from five to four and added a Photos folder type. The commit message:

Codes and Accounts merged into "Codes / Accounts" — one folder. Photos folder — tap + opens photo picker, select photos, then New Item form appears with them attached. Default folders now: Cards, Codes / Accounts, Photos, Notes. Detail view still has Library, Camera, Scan buttons on every item regardless of folder.

12.2 The folder merge is a small but meaningful design call. Codes and Accounts had identical data shapes (a title, an optional PIN, optional notes, optional photos). Two folders for the same shape just gave the user a categorization decision they didn't need to make. Merging them removes the noise.

12.3 The Photos folder uses Apple's PhotosPicker instead of the document scanner. PhotosPicker ships in the PhotosUI framework and presents the user's photo library in a system-curated picker. The user multi-selects, the picker returns [PhotosPickerItem], the items are loaded as Data via loadTransferable(type: Data.self), and the resulting array feeds the same New Item form the scanner uses. Two acquisition paths, one form, one storage path.

12.4 The "every detail view has Library / Camera / Scan buttons regardless of folder" line is worth highlighting. Originally the buttons were folder-conditional (Cards got Scan, Photos got Library, etc.). The simplification makes the detail view's affordance set predictable — every item, no matter what folder it lives in, can have any kind of attachment added. Users don't have to remember which buttons appear where.

App Icons: Light + Dark + Tinted + Mac

13.1 The 13:19 commit installed the icon set. The commit message captures the design rationale:

Light mode — Lockbox (tool by day). Dark mode — Safe (safe crackers at night). Tinted — uses the safe (same as dark). Mac — uses the lockbox for all sizes.

13.2 The light/dark split is conceptual: a lockbox is the daytime tool you hand to a contractor; a safe is what you put in the wall and crack at night. Each icon shares the family's terracotta starburst background, so the apps in the Claudes-X26-Swift-Bible roster read as siblings even though their primary glyphs differ.

13.3 In Xcode 26, multi-mode icons live in Assets.xcassets/AppIcon.appiconset. Drop the 1024×1024 PNG masters into the appropriate slots: AppIcon-Light.png, AppIcon-Dark.png, and AppIcon-Tinted.png. The Mac variant is also a 1024×1024 master in the Mac slot; macOS has its own icon-rendering pipeline that derives the menu-bar and dock sizes from the master.

Submitting to the App Store

15.1 With the build clean, the icon installed, and the supporting surfaces wired, the app is ready for App Store Connect. We followed the same submission path Build-Along 01 Section 13 walks through for Web Wrapper. The differences worth naming for LockBox specifically:

  • App icon needs all three modes installed before validation passes. Light + dark + tinted; Mac variants too if shipping to Mac. Xcode catches missing variants late in the validation step, not during build.
  • Privacy URL pattern. The book's pattern is fluharty.me/{appname}-privacy.html. For LockBox specifically, it's fluharty.me/lockbox-privacy. The wiki support URL is github.com/fluhartyml/Claudes-LockBox/wiki/Support.
  • iPhone screenshot dimensions are 1284×2778 (6.7" Display), not the newer 1290×2796 that some Pro Max simulators capture. App Store Connect rejects 1290×2796 with a confusingly-worded size error. Resize via sips -z 2778 1284 if your simulator captured the wrong dimensions.
  • Face ID usage description is a hard requirement. If NSFaceIDUsageDescription is missing from Info.plist, Apple's pre-submission validation accepts the build but the app crashes the first time a real device tries to authenticate. The crash log surfaces in TestFlight or App Store Connect within an hour.

15.2 LockBox v1.0 was approved on 2026 April 16 evening, then resubmitted as v2.0 on 2026 April 27 with the under-the-hood retool, the Lexicon Quick-Define addition, the new icon set, and the deployment-floor raise to iOS 26 / macOS 26. Both versions ship under the same bundle ID; the v2.0 update was a normal in-place version bump, not a second listing.

R&D Moments: Bugs Hit During the Build

16.1 A few non-obvious things bit during the build day. Each is worth flagging for your own first-shipped-app cycle.

16.2 The Xcode 26 Enable Destination Support dialog defaulted to macOS-only. Creating a new project, the dialog asking which destinations to support pre-checked Mac and not iPhone. We had to add iPhone manually before the project would build on iPhone simulators. May be tied to which simulator runtimes are downloaded; worth checking immediately after project creation.

16.3 Reading full-resolution screenshots in chat sessions blew context limits. The 2880×1864 PNGs Mac saves by default for Cmd+Shift+4 captures pushed past the model's per-image dimension limit, forcing repeated /compact mid-session. Practical fix: resize to a thumbnail with sips -z 800 600 or use file to read metadata only when you need to reference an image without seeing its content.

16.4 App Store Connect's iPhone screenshot size error is misleading. Submitting 1290×2796 returns a generic "wrong dimensions" error without saying what dimensions are expected. The right answer is 1284×2778, and the right tool is sips. Documented separately at feedback_app_store_screenshot_ip_rule.md in the apartment memory.

16.5 iPad ran in iPhone compatibility mode initially. The project's TARGETED_DEVICE_FAMILY defaulted to iPhone-only. iPad ran the app in a narrow phone-shaped column on the iPad screen. Expected if you don't enable iPad as a destination; not a bug. Add iPad to Supported Destinations in the General tab if you want native iPad layout.

16.6 Privacy policy URL pattern slip. The first attempt put the privacy policy on the GitHub wiki. The book's standard is fluharty.me/{appname}-privacy.html for the privacy URL and the GitHub wiki for the support URL. Saved as a feedback memory after the slip; the corrected pattern shipped with v1.1.
