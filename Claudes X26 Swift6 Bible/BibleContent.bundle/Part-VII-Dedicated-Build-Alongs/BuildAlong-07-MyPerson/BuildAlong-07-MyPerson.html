Build-Along 07: My Person CRM — Contacts, EventKit, and SwiftData Together

My Person CRM is a personal customer-relationship manager for the people you actually want to keep in touch with. Pick a contact from your address book, log how you stay in touch (calls, messages, emails, visits, free-form notes), and let the calendar surface upcoming events that mention them. Spring-green accent. Multiplatform — iPhone, iPad, Mac, Apple Vision — with SwiftData under the hood and a CloudKit-shaped schema ready to sync.

The repository: github.com/fluhartyml/My-Person-CRM. The wiki: github.com/fluhartyml/My-Person-CRM/wiki. Three privacy-gated frameworks (Contacts, ContactsUI, EventKit) coexist in one app, plus SwiftData with relationships and an enum stored as a raw string for CloudKit safety. Aiming for App Store distribution — the CRM space (Monica, Dex, Clay, Cloze, Contacts Journal) is real and Apple doesn't ship one.

The Brainstorm

Apple Contacts is a flat directory. It is not a relationship manager. It tells you a person's phone number; it does not tell you when you last spoke to them, what you said, or whether you owe them a follow-up. My Person CRM is a thin relationship layer on top of Contacts: contact details (phone, email, birthday, photo) come live from CNContactStore, while the interaction log is the value-add that lives only in this app.

v0.1 spec:

  • List of tracked people with photo, name, and "days since last contact"
  • Per-person detail screen with quick-action buttons (Call, Message, Email)
  • Live contact details pulled from Contacts (phone, email, birthday)
  • Upcoming calendar events that mention the person (next 12 months)
  • Interaction log — type, date, free-form note, sorted newest-first
  • iOS contact picker via CNContactPickerViewController
  • Mac manual-entry sheet (ContactsUI doesn't ship on macOS)
  • Empty state with friendly guidance and a single Add button
  • About sheet with Privacy, Source on GitHub, Send Feedback links

What is intentionally NOT in v0.1:

  • No CallKit — tel:// URL is enough
  • No reminders — "haven't called in N days" is a future feature
  • No Apple Watch companion — doubles the build, separate chapter material
  • No CloudKit sync turned on yet — the schema is ready, the container isn't wired
  • No NearbyInteraction or peer-to-peer contact exchange — future feature; v0.1 stays focused

The Architecture

Two SwiftData models hold the persistent state. Two @Observable @MainActor stores wrap Apple's framework APIs and own the auth state machines. Views read both directly.

@Model
final class TrackedPerson {
    var contactIdentifier: String = ""
    var displayName: String = ""
    var photoData: Data? = nil
    var addedAt: Date = Date()
    var personalNotes: String = ""

    @Relationship(deleteRule: .cascade, inverse: \Interaction.person)
    var interactions: [Interaction]? = nil

    var lastInteractionDate: Date? {
        interactions?.sorted(by: { $0.date > $1.date }).first?.date
    }
}
@Model
final class Interaction {
    var typeRaw: String = InteractionType.note.rawValue
    var date: Date = Date()
    var note: String = ""
    var person: TrackedPerson? = nil

    var type: InteractionType {
        get { InteractionType(rawValue: typeRaw) ?? .note }
        set { typeRaw = newValue.rawValue }
    }
}

Three details in this model are deliberate. Every stored property has a default value. The to-many relationship is optional. The enum is stored as a raw string with a computed property bridge. All three are CloudKit-required patterns — SwiftData with CloudKit refuses to migrate a schema that violates them. Setting them up correctly on day one means turning on iCloud sync later is a one-line change in ModelConfiguration, not a model migration.

The app entry wires the schema and injects the model container:

@main
struct My_Person_CRMApp: App {
    var sharedModelContainer: ModelContainer = {
        let schema = Schema([TrackedPerson.self, Interaction.self])
        let modelConfiguration = ModelConfiguration(
            schema: schema,
            isStoredInMemoryOnly: false
        )
        do {
            return try ModelContainer(for: schema, configurations: [modelConfiguration])
        } catch {
            fatalError("Could not create ModelContainer: \(error)")
        }
    }()

    var body: some Scene {
        WindowGroup { ContentView() }
            .modelContainer(sharedModelContainer)
    }
}

Notice what is not there: cloudKitDatabase: .private(...). The project's iCloud entitlement is declared but the iCloud container hasn't been wired in Signing & Capabilities yet. Setting .private against a non-existent container would crash at launch. The default behavior runs as local SwiftData and quietly ignores the entitlement until a container exists. Wiring CloudKit later is the one-line change.

The Contacts Store

The Contacts framework is a privacy-gated read of the system address book. Authorization is async; lookup is synchronous and returns an optional.

@MainActor
@Observable
final class ContactsStore {
    enum AuthState { case unknown, authorized, denied, notDetermined }

    var authState: AuthState = .unknown
    var lastError: String?

    private let store = CNContactStore()

    func refreshAuth() {
        switch CNContactStore.authorizationStatus(for: .contacts) {
        case .authorized: authState = .authorized
        case .denied, .restricted: authState = .denied
        case .notDetermined: authState = .notDetermined
        @unknown default: authState = .unknown
        }
    }

    func requestAccess() async {
        do {
            let granted = try await store.requestAccess(for: .contacts)
            authState = granted ? .authorized : .denied
        } catch {
            lastError = error.localizedDescription
            authState = .denied
        }
    }

    func contact(forIdentifier identifier: String) -> CNContact? {
        let keys: [CNKeyDescriptor] = [
            CNContactGivenNameKey as CNKeyDescriptor,
            CNContactFamilyNameKey as CNKeyDescriptor,
            CNContactPhoneNumbersKey as CNKeyDescriptor,
            CNContactEmailAddressesKey as CNKeyDescriptor,
            CNContactBirthdayKey as CNKeyDescriptor,
            CNContactImageDataKey as CNKeyDescriptor,
            CNContactImageDataAvailableKey as CNKeyDescriptor,
            CNContactFormatter.descriptorForRequiredKeys(for: .fullName)
        ]
        return try? store.unifiedContact(withIdentifier: identifier, keysToFetch: keys)
    }
}

The keysToFetch array deserves attention. The Contacts framework refuses to return a property unless you've asked for it explicitly. Trying to read contact.phoneNumbers on a CNContact that wasn't fetched with CNContactPhoneNumbersKey raises an exception. Listing every property the app actually displays here, once, prevents a class of runtime crashes that don't appear during testing on a developer's well-formed contact card.

CNContactFormatter.descriptorForRequiredKeys(for: .fullName) is a meta-descriptor: it asks "which keys does the formatter need to produce a full name?" and returns whatever Apple has decided that takes (currently given name, family name, middle name, prefix, suffix, nickname). Always pull it through this API rather than hand-listing the name keys, because Apple has changed which keys are needed across iOS versions.

The Calendar Store

EventKit is the calendar / reminders framework. iOS 17 introduced requestFullAccessToEvents() as the modern replacement for the deprecated requestAccess(to:). The deployment target here is iOS 26.4, so the modern API is the only one we use.

@MainActor
@Observable
final class CalendarStore {
    var authState: AuthState = .unknown
    private let store = EKEventStore()

    func requestAccess() async {
        do {
            let granted = try await store.requestFullAccessToEvents()
            authState = granted ? .authorized : .denied
        } catch {
            authState = .denied
        }
    }

    func upcomingEvents(matching searchTerm: String, limit: Int = 5) -> [EKEvent] {
        guard !searchTerm.isEmpty else { return [] }
        let now = Date()
        let oneYearFromNow = Calendar.current.date(byAdding: .year, value: 1, to: now) ?? now
        let predicate = store.predicateForEvents(withStart: now, end: oneYearFromNow, calendars: nil)
        let lc = searchTerm.lowercased()
        return store.events(matching: predicate)
            .filter { event in
                if event.title?.lowercased().contains(lc) == true { return true }
                if event.notes?.lowercased().contains(lc) == true { return true }
                if event.attendees?.contains(where: { $0.name?.lowercased().contains(lc) == true }) == true { return true }
                return false
            }
            .prefix(limit)
            .map { $0 }
    }
}

The matching logic checks three places where a person's name might live in an event: the title, the notes body, and the attendee list. A meeting titled "Lunch with Alice" matches; a meeting with "Alice" in attendees matches; a meeting whose notes say "Alice will join late" matches. Three OR'd conditions cover every realistic way an event records a person's involvement.

predicateForEvents(withStart:end:calendars:) with calendars: nil queries all calendars the user has granted access to — iCloud, Google, Exchange, work, personal, holidays. The user's mental model is "my calendar"; the framework's model is "all calendars I can see"; passing nil aligns the two.

Bridging UIKit's Contact Picker into SwiftUI

SwiftUI doesn't ship a contact picker view. The ContactsUI framework provides CNContactPickerViewController — a UIKit view controller. Bridging it into SwiftUI is a textbook UIViewControllerRepresentable application.

#if os(iOS)
import ContactsUI

struct PersonPickerView: UIViewControllerRepresentable {
    let onPick: (CNContact) -> Void

    func makeUIViewController(context: Context) -> CNContactPickerViewController {
        let picker = CNContactPickerViewController()
        picker.delegate = context.coordinator
        return picker
    }

    func updateUIViewController(_ uiViewController: CNContactPickerViewController, context: Context) {}

    func makeCoordinator() -> Coordinator { Coordinator(onPick: onPick) }

    final class Coordinator: NSObject, CNContactPickerDelegate {
        let onPick: (CNContact) -> Void
        init(onPick: @escaping (CNContact) -> Void) { self.onPick = onPick }
        func contactPicker(_ picker: CNContactPickerViewController, didSelect contact: CNContact) {
            onPick(contact)
        }
    }
}
#endif

Three pieces make this bridge work. makeUIViewController creates the actual UIKit object once and SwiftUI keeps it. updateUIViewController is empty here because the picker doesn't need re-configuring on view updates. The Coordinator sits between the UIKit delegate protocol and the Swift closure the parent SwiftUI view actually wants.

Why a closure and not a binding? A binding would force the parent to hold a @State CNContact?, observe it, and react when it becomes non-nil. A closure expresses "when the user picks, do this" directly. Closures fit one-shot events; bindings fit ongoing two-way state.

The #if os(iOS) guard exists because ContactsUI doesn't ship on macOS. The Mac path uses a simpler SwiftUI sheet that just collects a name in a TextField and creates a TrackedPerson with no underlying CNContact — the contact identifier stays empty, the contact-detail card stays hidden, but the person can still be tracked and have interactions logged.

Permissions and Info.plist

Three privacy-gated frameworks need three usage-description strings. iOS shows each string verbatim inside the system permission dialog the first time the app reaches a feature that needs it.

<key>NSContactsUsageDescription</key>
<string>My Person CRM uses Contacts to let you pick the people you want to keep track of and to surface their phone, email, and birthday on each person's detail screen.</string>
<key>NSCalendarsFullAccessUsageDescription</key>
<string>My Person CRM reads your calendar to show upcoming events that mention each person you track, so you can see what's coming up with them.</string>

These strings are user-visible UI copy. Write them in the user's voice, name the benefit, never make a defensive engineering claim. App Review reads them. A vague string ("Required for app function") is the fastest way to get rejected.

NSCalendarsFullAccessUsageDescription is the iOS 17+ name. The older NSCalendarsUsageDescription still exists for backward compatibility, but the modern key is what the framework looks for first when calling requestFullAccessToEvents. Including only the modern key is correct for iOS 17 / iOS 26 deployment targets.

The CoreData Errno-2 Story

The first real-device launch produced an alarming wall of red error logs. Dozens of lines of CoreData: error: Failed to stat path '/var/mobile/Containers/.../Library/Application Support/default.store', sandbox-access-denied messages, full filesystem dumps. To a fresh reader it looks like the app is broken.

It is not. The last log line tells the truth:

CoreData: error: Recovery attempt while adding
<NSPersistentStoreDescription: 0x...> ... was successful!

What's happening: SwiftData tries to create the SQLite store at ~/Library/Application Support/default.store. On a fresh install, the Application Support directory itself doesn't exist yet — iOS only creates Library by default. The first creation attempt fails with errno 2 / No such file or directory. Core Data dumps a verbose diagnostic (a full filesystem walk, every parent directory's permissions, the file system metadata) and then quietly executes the recovery path: create the missing parent directory, retry. The retry succeeds. Apple's own apps log the same noise.

There is no code-side fix. The errors are loud because Core Data was designed to make filesystem problems easy to diagnose, not because something is wrong. A clean console arrives only by wiring CloudKit (which makes SwiftData use a different store path that doesn't hit this race) or by filing a feedback report to Apple about the verbosity.

The teaching point: read the entire log before declaring a bug. The shape of an actual fatal error is different from a recovered error. "Recovery attempt was successful" is the all-clear.

Quick Actions: tel, sms, mailto

The detail view's three quick-action buttons (Call, Message, Email) route to the system apps using URL schemes. No CallKit, no MFMessageComposeViewController, no MFMailComposeViewController. iOS routes the URLs to the right destination automatically.

private func callTapped() {
    guard let phone = contact?.phoneNumbers.first?.value.stringValue else { return }
    openURL("tel://\(phone.filter { $0.isNumber || $0 == "+" })")
}

private func messageTapped() {
    guard let phone = contact?.phoneNumbers.first?.value.stringValue else { return }
    openURL("sms:\(phone.filter { $0.isNumber || $0 == "+" })")
}

private func emailTapped() {
    guard let email = contact?.emailAddresses.first?.value as String? else { return }
    openURL("mailto:\(email)")
}

private func openURL(_ string: String) {
    guard let url = URL(string: string) else { return }
    #if os(iOS)
    UIApplication.shared.open(url)
    #elseif os(macOS)
    NSWorkspace.shared.open(url)
    #endif
}

The phone number sanitization (filter { $0.isNumber || $0 == "+" }) strips parentheses, dashes, dots, and spaces. tel:// URLs accept those characters in practice, but a clean digit-only string — with the leading + for international format preserved — is the safest input.

The buttons disable themselves when the underlying CNContact has no phone (Call / Message) or no email (Email). A button that would no-op is worse than a button that's clearly inactive; iOS's .disabled + .opacity(0.4) renders the unavailability honestly.

Mac vs iOS dispatch. UIApplication.shared.open on iOS, NSWorkspace.shared.open on macOS. Same idea, two frameworks, conditional compilation in the same function. This is the cleanest place to put the platform split because the rest of the view doesn't care.

The Three UI States

The list view has to render three distinct states. A reader can hit any of them.

Empty list: no TrackedPerson records exist. The view shows a centered icon, a "No People Yet" headline, and a friendly invitation to tap the Add button. The List view is replaced by a VStack so the empty state can be properly centered — an empty List would just show a blank scrolling area.

Populated list: at least one person exists. The view shows a List of NavigationLink rows, each rendering a PersonRow with photo, name, and a "days since last contact" caption. onDelete handles swipe-to-delete on iOS.

Permission-pending: the user tapped Add but Contacts auth hasn't resolved yet. The view doesn't render anything special — iOS's permission dialog is a system overlay that appears on top of whatever the app is showing. After the user responds, the auth state in ContactsStore updates and the picker sheet either presents (if authorized) or doesn't (if denied).

Why a separate empty state instead of just rendering an empty List? Empty List is silent — the user sees nothing and doesn't know why. Explicit empty-state copy with a friendly icon and a clear next-action turns "this app is broken" into "I haven't done the first thing yet." Same teaching point as BodyReadings' three-state UI: empty + loading + populated each deserve their own visual.

What This Build-Along Teaches

  • SwiftData with relationships — @Model, @Relationship(deleteRule:inverse:), optional to-many, cascade delete
  • CloudKit-shaped schemas — defaults on every property, optional relationships, raw-string-with-computed enum bridge
  • Three privacy frameworks side by side — Contacts, ContactsUI, EventKit, each with its own auth pattern
  • iOS 17 modern auth APIs — async requestAccess(for:) for Contacts, async requestFullAccessToEvents() for EventKit
  • CNContactStore.unifiedContact(withIdentifier:keysToFetch:) — the lookup pattern, the keys-to-fetch contract, the CNContactFormatter meta-descriptor
  • EventKit predicate search — predicateForEvents(withStart:end:calendars:), three-way OR matching across title / notes / attendees
  • UIViewControllerRepresentable bridges — wrapping CNContactPickerViewController, the Coordinator pattern, when to use closures vs bindings
  • Multiplatform conditional code — #if os(iOS) for ContactsUI, #if os(macOS) for AppKit dispatch, single source for shared logic
  • URL-scheme dispatch — tel://, sms:, mailto: as the lightweight alternative to CallKit / MFMessageCompose / MFMailCompose
  • Reading verbose Core Data logs — recognizing the difference between a recovered error (loud, harmless) and a fatal error (loud, real)

Cloning and Building

My Person CRM is a clone-and-build app for Volume 1 with App Store distribution as the next-stage goal. To get a working copy:

  1. Open Xcode and choose Source Control → Clone; paste https://github.com/fluhartyml/My-Person-CRM.
  2. Pick a real iPhone destination (the simulator runs the app fine but has no real Contacts data — you can still test the auth flow and the empty state, but adding a person will pull from the simulator's stub address book).
  3. ⌘R to build and run.
  4. On first launch, tap the person-with-plus button in the top right. iOS shows the Contacts permission dialog; choose Select Contacts to share only specific people, or Allow Full Access for the whole address book.
  5. Pick a contact. Tap the row to open their detail view. iOS now asks for Calendar permission — allow it to see upcoming events that mention them.
  6. Tap the + in the top right of the detail view to log an interaction.

The wiki at github.com/fluhartyml/My-Person-CRM/wiki carries the full Chilton-depth shop manual: User's Manual half (how to use the app, what every screen does, every permission explained) and Developer's Manual half (architecture, every Swift file documented, every framework contract spelled out, every decision logged, every failure mode mapped to its recovery). The chapter teaches the patterns; the wiki is the reference.
