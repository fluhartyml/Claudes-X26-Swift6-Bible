VII.11  Build-Along 11: ReportMaker — Trip, Charts, and PDF

Distribution: GitHub clone-and-build, App Store target. ReportMaker is a focused business expense tracker for one job: capture spending during a trip, then produce a clean PDF the user can email to whoever reimburses them. Apple does not ship one; Expensify, SAP Concur, and FreshBooks all do for a fee. ReportMaker is the small, native, no-account-required alternative.

The repository: github.com/fluhartyml/ReportMaker. Built atop SwiftData (@Model with an inverse @Relationship), Swift Charts (BarMark, LineMark), PhotosPicker, UIGraphicsPDFRenderer driving native NSAttributedString draws, and a UIActivityViewController bridge for the share sheet. iPhone and iPad universal target. No third-party SDKs, no accounts, no servers.

This chapter is the first build-along that bundles four major frameworks — SwiftData, Swift Charts, PDFKit, PhotosUI — into a single product instead of demonstrating each in isolation. The lessons up to Build-Along 10 have been single-concept; ReportMaker is where those concepts compose.

VII.11.1  The Brainstorm

VII.11.1 ¶1 Every employee who flies for work has done the same chore at the end of a trip: collect receipts, sort them by category, total them, scan or photograph each one, paste everything into an email or a spreadsheet, and send it to whoever reimburses. The chore is universal and unloved.

VII.11.1 ¶2 The category is mature on the App Store. Expensify, SAP Concur, FreshBooks, and several others sell subscriptions to do exactly this. They sell because the chore is real and Apple does not ship a first-party version.

VII.11.1 ¶3 The opening for ReportMaker is what the existing apps share: account-required, server-backed, and priced for an accountant. A focused native app that does the chore well and stops there has room. ReportMaker keeps everything on-device, ships no telemetry, and writes a PDF the user owns.

VII.11.1 ¶4 v0.1 spec:

VII.11.1 ¶5
  • One trip at a time, with a name, purpose, start date, and end date
  • Per-trip expense list with category, amount, vendor, optional note, optional receipt photo, and date constrained to the trip's range
  • Five categories: Hotel, Meals, Transport, Incidentals, Other (each with an SF Symbol)
  • Trip dashboard with a category bar chart and a day-over-day line chart
  • Generate Report button writes a multi-page PDF: cover page, expense table, one page per receipt photo
  • Share sheet for the PDF (email, AirDrop, Files, Messages)
  • SwiftData persistence between sessions
  • Under the Hood sheet (developer notes inside the app)
  • About sheet (icon, attribution, links)
  • Light + dark icon variants. No tinted variant.

VII.11.1 ¶6 What is intentionally not in v0.1:

VII.11.1 ¶7
  • No multi-trip aggregation — the dashboard is per-trip
  • No OCR auto-extraction from receipt photos — the user types the amount
  • No mileage tracking — the category list does not include mileage; vehicle costs go under Transport with a manual amount
  • No CloudKit sync in v0.1 — SwiftData is local-only; CloudKit is a v0.2 candidate (the model is already CloudKit-safe; see §3 on the categoryRaw pattern)
  • No accounts, no server, no telemetry — nothing leaves the device unless the user invokes the share sheet

VII.11.2  The Architecture

VII.11.2 ¶1 Eleven Swift files in the main target plus the asset catalog and the Info.plist.

VII.11.2 ¶2
ReportMakerApp.swift       # @main · SwiftData ModelContainer · root WindowGroup
ContentView.swift          # Trip list + ContentUnavailableView + nav to detail
Trip.swift                 # @Model · expenses inverse relationship · computed totals
Expense.swift              # @Model · ExpenseCategory enum + raw-string persistence
AddTripSheet.swift         # Form sheet for new trip
AddExpenseSheet.swift      # Form sheet for new expense + PhotosPicker
TripDetailView.swift       # Per-trip dashboard · charts · expense list · toolbar
ReportPDFRenderer.swift    # UIGraphicsPDFRenderer · cover/expenses/receipts pages

UnderTheHoodView.swift     # Sectioned reader for the notes
AboutView.swift            # Icon · attribution · links

VII.11.2 ¶3 The flow of a single end-to-end pass: the user lands on ContentView, taps Add Trip, fills out the AddTripSheet form, saves. SwiftData inserts a Trip into the container. The new trip appears in the list. The user taps the trip, lands on TripDetailView, taps Add Expense, fills out the AddExpenseSheet form, optionally picks a receipt photo via PhotosPicker, saves. SwiftData inserts an Expense with its trip relationship pointing at the parent. The dashboard's category bar chart and day-over-day line chart re-render as the totals change. When the trip ends, the user taps Generate Report; ReportPDFRenderer.makePDF(for:) writes a multi-page PDF to the temporary directory and the share sheet pops up. The user emails or AirDrops the PDF, and ReportMaker is done.

VII.11.3  SwiftData: @Model with an Inverse Relationship

VII.11.3 ¶1 SwiftData replaced Core Data as the canonical Apple persistence layer at WWDC 2023, and by 2026 the SwiftUI templates ship with it as the default. ReportMaker uses two @Model classes joined by an inverse @Relationship.

VII.11.3 ¶2
@Model
final class Trip {
    var name: String = ""
    var purpose: String = ""
    var startDate: Date = Date()
    var endDate: Date = Date()
    var createdAt: Date = Date()

    @Relationship(deleteRule: .cascade, inverse: \Expense.trip)
    var expenses: [Expense]? = nil

    init(name: String, purpose: String, startDate: Date, endDate: Date) { ... }
}
VII.11.3 ¶3
@Model
final class Expense {
    var categoryRaw: String = ExpenseCategory.other.rawValue
    var amount: Decimal = Decimal(0)
    var vendor: String = ""
    var note: String = ""
    var date: Date = Date()
    var receiptImageData: Data? = nil
    var trip: Trip? = nil
}

VII.11.3 ¶4 Three details are load-bearing.

VII.11.3 ¶5 The inverse relationship. The @Relationship(deleteRule: .cascade, inverse: \Expense.trip) declaration on Trip.expenses is paired with a plain var trip: Trip? on Expense. SwiftData reads the inverse: key path and links the two sides for you, so reading trip.expenses returns the same array that expense.trip belongs to. .cascade means deleting a Trip automatically deletes its expenses, which is the right semantic for this app — an expense without its trip is meaningless.

VII.11.3 ¶6 Default values on every property. Every stored property on both models has a default value (= "", = Date(), = Decimal(0), = nil). SwiftData's automatic migrations and CloudKit's schema requirements both want defaults so that adding a new property to an existing model does not crash apps that have older records on disk. Bake the habit in from the first model.

VII.11.3 ¶7 Enum stored as raw String. ExpenseCategory is a Swift enum with cases like .hotel and .meals, but the @Model stores categoryRaw: String rather than the enum directly. The enum is exposed as a computed get/set on top:

VII.11.3 ¶8
var category: ExpenseCategory {
    get { ExpenseCategory(rawValue: categoryRaw) ?? .other }
    set { categoryRaw = newValue.rawValue }
}

VII.11.3 ¶9 The reason is CloudKit. SwiftData can sync String; it cannot sync a Swift enum directly. Storing the raw value as the persisted property and the enum as a computed convenience keeps the model CloudKit-ready without giving up the type-safe call sites elsewhere in the app. Even though v0.1 does not enable CloudKit sync, the model is built so v0.2 only has to flip the container's cloudKitDatabase option.

VII.11.3 ¶10 The container itself is set up in ReportMakerApp.swift:

VII.11.3 ¶11
@main
struct ReportMakerApp: App {
    var sharedModelContainer: ModelContainer = {
        let schema = Schema([Trip.self, Expense.self])
        let modelConfiguration = ModelConfiguration(schema: schema, isStoredInMemoryOnly: false)
        return try! ModelContainer(for: schema, configurations: [modelConfiguration])
    }()

    var body: some Scene {
        WindowGroup { ContentView() }
            .modelContainer(sharedModelContainer)
    }
}

VII.11.3 ¶12 The .modelContainer(_:) modifier on the WindowGroup publishes the container into the SwiftUI environment. Any view downstream reads @Environment(\.modelContext) to insert or delete records, or uses @Query to fetch them. ContentView does both:

VII.11.3 ¶13
@Environment(\.modelContext) private var modelContext
@Query(sort: \Trip.createdAt, order: .reverse) private var trips: [Trip]

VII.11.3 ¶14 @Query is the SwiftData equivalent of @FetchRequest from Core Data. The view re-renders automatically when the underlying records change, which is why deleting a trip from the list updates the UI without a manual refresh call.

VII.11.4  Computed Totals on the Model

VII.11.4 ¶1 The trip dashboard does not run aggregation queries against SwiftData; the model itself exposes the totals as Swift computed properties. Trip.total, Trip.totalsByCategory, Trip.totalsByDay, and Trip.sortedExpenses all derive from the expenses relationship.

VII.11.4 ¶2
var total: Decimal {
    var sum: Decimal = 0
    for expense in (expenses ?? []) { sum += expense.amount }
    return sum
}

var totalsByCategory: [(ExpenseCategory, Decimal)] {
    var bucket: [ExpenseCategory: Decimal] = [:]
    for expense in (expenses ?? []) {
        bucket[expense.category, default: 0] += expense.amount
    }
    return ExpenseCategory.allCases
        .map { ($0, bucket[$0] ?? 0) }
        .filter { $0.1 > 0 }
}

var totalsByDay: [(Date, Decimal)] {
    let cal = Calendar.current
    var bucket: [Date: Decimal] = [:]
    for expense in (expenses ?? []) {
        let day = cal.startOfDay(for: expense.date)
        bucket[day, default: 0] += expense.amount
    }
    return bucket.sorted(by: { $0.key < $1.key })
}

VII.11.4 ¶3 Two design choices to point out.

VII.11.4 ¶4 Currency math uses Decimal, not Double. Floating-point arithmetic is famous for losing pennies: 0.1 + 0.2 is not 0.3 in Double. Decimal keeps base-10 arithmetic exact, which is what an expense report needs. The cost is that Decimal is not directly graphable in Swift Charts — the chart consumes Double, so the conversion happens at the chart boundary via NSDecimalNumber(decimal:).doubleValue. The model holds the truth in Decimal; only the visual layer downcasts.

VII.11.4 ¶5 The shape of totalsByCategory matches what Swift Charts wants. An array of tuples, one per data point, identifiable by the first element. Most chart APIs in other ecosystems take parallel arrays (one for X, one for Y); Swift Charts takes a single sequence and pulls X and Y out of each element via .value(_:). Computing the array on the model keeps the view code short and lets the chart's id: keypath be a clean \.0.

VII.11.5  Swift Charts: BarMark and LineMark

VII.11.5 ¶1 The trip dashboard is two charts in two List sections. The bar chart shows totals by category; the line chart shows totals by day, but only when the trip spans more than one day.

VII.11.5 ¶2
if !trip.totalsByCategory.isEmpty {
    Section("By Category") {
        Chart(trip.totalsByCategory, id: \.0) { item in
            BarMark(
                x: .value("Category", item.0.label),
                y: .value("Amount", NSDecimalNumber(decimal: item.1).doubleValue)
            )
            .foregroundStyle(by: .value("Category", item.0.label))
        }
        .frame(height: 220)
        .chartLegend(.hidden)
    }
}

if trip.totalsByDay.count > 1 {
    Section("Day Over Day") {
        Chart(trip.totalsByDay, id: \.0) { item in
            LineMark(
                x: .value("Day", item.0),
                y: .value("Amount", NSDecimalNumber(decimal: item.1).doubleValue)
            )
            .symbol(Circle())
        }
        .frame(height: 200)
    }
}

VII.11.5 ¶3 Chart(_:id:content:) takes the data, a key path to the identifier of each row, and a closure that returns one or more ChartContent marks per row. BarMark draws a bar; LineMark draws a connected line; .symbol(Circle()) places a circular dot at each line vertex. foregroundStyle(by:) tells the chart to color each bar by category, picking a palette automatically; .chartLegend(.hidden) hides the legend because the bars are already labeled on the X axis.

VII.11.5 ¶4 The conditional if trip.totalsByDay.count > 1 is a small UX choice with real teaching value. A line chart of one point is just a dot — it teaches the reader of the report nothing. Hiding the section until there is enough data to make a line is honest: charts that would mislead are not drawn.

VII.11.6  PhotosPicker for Receipts

VII.11.6 ¶1 iOS has historically had two paths for picking a photo: UIImagePickerController (UIKit) and the SwiftUI-native PhotosPicker introduced at WWDC 2022. PhotosPicker is the right choice in 2026 — it does not require NSPhotoLibraryUsageDescription in the Info.plist because the system runs the picker out-of-process and only hands back the bytes the user explicitly chose.

VII.11.6 ¶2
@State private var receiptItem: PhotosPickerItem?
@State private var receiptData: Data?

PhotosPicker(selection: $receiptItem, matching: .images, photoLibrary: .shared()) {
    Label(receiptData == nil ? "Add Receipt Photo" : "Change Receipt Photo",
          systemImage: "camera")
}
.onChange(of: receiptItem) { _, newItem in
    guard let newItem else { return }
    Task {
        if let data = try? await newItem.loadTransferable(type: Data.self) {
            receiptData = data
        }
    }
}

VII.11.6 ¶3 The picker binds to a PhotosPickerItem, which is a lazy reference, not the bytes themselves. To get the bytes, call loadTransferable(type: Data.self) in a Task; the call is asynchronous because the photo may live in iCloud Photo Library and need to be downloaded. Once the data lands, it is stored in the Expense.receiptImageData field and travels with the record.

VII.11.6 ¶4 Storing image bytes inside the model is a deliberate v0.1 trade-off. SwiftData (and CloudKit) handle Data properties by writing them as blobs alongside the record. For a small expense report — tens of receipts per trip, hundreds of trips per year — the database stays comfortable. A production-scale app with thousands of receipts per user would offload the bytes to the file system or to CKAsset on CloudKit and store only a URL on the model. ReportMaker's scale does not need that, and the simplicity of "the bytes go with the record" is worth keeping until it stops working.

VII.11.7  UIGraphicsPDFRenderer: Native Multi-Page PDFs

VII.11.7 ¶1 The Generate Report button is the moment ReportMaker becomes a product instead of a shoebox. Tapping it calls ReportPDFRenderer.makePDF(for: trip), which writes a real, multi-page PDF using UIGraphicsPDFRenderer.

VII.11.7 ¶2
enum ReportPDFRenderer {
    static func makePDF(for trip: Trip) -> URL? {
        let pageSize = CGSize(width: 612, height: 792)  // US Letter at 72 DPI
        let renderer = UIGraphicsPDFRenderer(bounds: CGRect(origin: .zero, size: pageSize))

        let url = FileManager.default.temporaryDirectory
            .appendingPathComponent("\(safeFileName(trip.name))-Expense-Report.pdf")

        do {
            try renderer.writePDF(to: url) { context in
                drawCoverPage(trip: trip, in: context, size: pageSize)
                drawExpenseList(trip: trip, in: context, size: pageSize)
                drawReceipts(trip: trip, in: context, size: pageSize)
            }
            return url
        } catch {
            print("PDF render failed: \(error)")
            return nil
        }
    }
}

VII.11.7 ¶3 The closure passed to renderer.writePDF(to:_:) receives a UIGraphicsPDFRendererContext, which is the drawing surface for the whole document. Inside the closure, each call to context.beginPage() opens a new page; everything drawn after that lands on the current page until the next beginPage(). Three pages get drawn: cover, expense table, then one page per receipt photo.

VII.11.7 ¶4 The page size is US Letter at 72 DPI. 612 by 792 points is the standard PDF unit for an 8.5×11 inch page. PDF coordinates are in points, not pixels; the renderer rasterizes at print resolution automatically. Apple's PDF Reference Guide is the canonical source for these dimensions; for ReportMaker the only thing the chapter needs the reader to take away is "612×792 is letter, 595×842 is A4, and the rest of the world's paper sizes are out there waiting for a future enhancement."

VII.11.7 ¶5 Each page is drawn with NSAttributedString's .draw(at:withAttributes:) and .draw(in:withAttributes:) methods, which are the lowest-level Apple text-drawing APIs. The cover page builds attribute dictionaries for title, label, value, and total styles, then draws each line at a tracked y coordinate that increments after each draw:

VII.11.7 ¶6
var y: CGFloat = margin

("Expense Report" as NSString).draw(
    at: CGPoint(x: margin, y: y),
    withAttributes: titleAttrs)
y += 50

(trip.name as NSString).draw(
    at: CGPoint(x: margin, y: y),
    withAttributes: [.font: UIFont.systemFont(ofSize: 22, weight: .medium)])
y += 36

// ...DATES, PURPOSE, DAYS, TOTAL, BY CATEGORY...

VII.11.7 ¶7 Auto-pagination on the expense table is the one bit of bookkeeping in the renderer. As rows draw, y grows; when y exceeds size.height - 80, the table starts a new page:

VII.11.7 ¶8
for expense in trip.sortedExpenses {
    if y > size.height - 80 {
        context.beginPage()
        y = margin
    }
    // ...draw row...
    y += 22
}

VII.11.7 ¶9 The receipts pages are one image per page. UIImage(data: expense.receiptImageData!) reconstructs the image from the bytes that traveled with the model, then image.draw(in: rect) places it on the page. The aspect-ratio math fits the image into the available rectangle without distortion:

VII.11.7 ¶10
let availableWidth = size.width - margin * 2
let availableHeight = size.height - y - margin
let aspect = image.size.width / image.size.height
var drawWidth = availableWidth
var drawHeight = drawWidth / aspect
if drawHeight > availableHeight {
    drawHeight = availableHeight
    drawWidth = drawHeight * aspect
}
image.draw(in: CGRect(x: margin, y: y, width: drawWidth, height: drawHeight))

VII.11.7 ¶11 This is the canonical Apple approach for native PDF generation: UIGraphicsPDFRenderer for the document, NSAttributedString for text, UIImage.draw(in:) for images, page breaks called explicitly. There is no HTML-to-PDF conversion, no UIView snapshotting, no third-party dependency. Every "Export PDF" feature in iOS apps ends up at this same surface.

VII.11.8  The Share Sheet Bridge

VII.11.8 ¶1 SwiftUI in 2026 still does not have a native share sheet for arbitrary file URLs. There is ShareLink, which works for Transferable values and simple URLs, but for a generated PDF that the user wants to email, AirDrop, or save to Files, the right surface is still UIActivityViewController. ReportMaker wraps it once in a 12-line file:

VII.11.8 ¶2
struct ShareSheet: UIViewControllerRepresentable {
    let items: [Any]

    func makeUIViewController(context: Context) -> UIActivityViewController {
        UIActivityViewController(activityItems: items, applicationActivities: nil)
    }

    func updateUIViewController(_ controller: UIActivityViewController, context: Context) {}
}

VII.11.8 ¶3 UIViewControllerRepresentable is the SwiftUI bridge for any UIKit view controller that has not yet been ported. It is one of the most useful generalist patterns in the framework: when SwiftUI does not ship the surface, wrap UIKit. The pattern recurs in PHPickerViewController, VNDocumentCameraViewController, and any Apple SDK that has not finished its SwiftUI rewrite.

VII.11.8 ¶4 The trip detail view drives the bridge with a .sheet that fires after the PDF is generated:

VII.11.8 ¶5
@State private var generatedReportURL: URL?
@State private var showingShareSheet = false

.sheet(isPresented: $showingShareSheet) {
    if let url = generatedReportURL {
        ShareSheet(items: [url])
    }
}

private func generateReport() {
    let url = ReportPDFRenderer.makePDF(for: trip)
    generatedReportURL = url
    showingShareSheet = url != nil
}

VII.11.8 ¶6 The PDF lives in the temporary directory because there is no reason to keep it around after sharing. The source data is in SwiftData; the PDF is a derivative artifact and can be regenerated on demand.

VII.11.9  The Form Sheets

VII.11.9 ¶1 AddTripSheet and AddExpenseSheet are both built around SwiftUI's Form — the same primitive that powers the iOS Settings app. Each sheet is its own NavigationStack with a Cancel / Save toolbar pair.

VII.11.9 ¶2 Date constraint on the expense. The expense date picker constrains itself to the trip's range:

VII.11.9 ¶3
DatePicker("Date", selection: $date,
           in: trip.startDate...trip.endDate,
           displayedComponents: .date)

VII.11.9 ¶4 The in: argument takes a ClosedRange<Date>, and SwiftUI dims any date outside the range. The user cannot enter an expense for a date the trip did not cover. This is the kind of validation that earns its keep on the model side and the UI side both.

VII.11.9 ¶5 Decimal parsing tolerant of comma-as-decimal. The amount is a TextField bound to a String, parsed back to Decimal on save:

VII.11.9 ¶6
private var parsedAmount: Decimal? {
    Decimal(string: amountString.replacingOccurrences(of: ",", with: "."))
}

VII.11.9 ¶7 Many European locales write decimals with a comma (1,50) where US locales use a period (1.50). Swapping comma for period before Decimal(string:) handles both forms with one line. The Save button stays disabled until parsedAmount is non-nil and greater than zero.

VII.11.10  Empty State and Toolbar Conventions

VII.11.10 ¶1 The trip list uses ContentUnavailableView — SwiftUI's WWDC 2023 addition that gives empty-state design a built-in surface so every app does not invent its own.

VII.11.10 ¶2
if trips.isEmpty {
    ContentUnavailableView {
        Label("No Trips Yet", systemImage: "airplane.departure")
    } description: {
        Text("Tap **Add Trip** to start tracking expenses for a business trip.")

VII.11.10 ¶3 The toolbar pattern is consistent across the build-along apps: an info menu in the leading position holds Under the Hood and About entries; the primary action sits in the trailing position. ContentView places Add Trip in the trailing primaryAction slot; TripDetailView places Generate Report in the leading position and Add Expense in the trailing primaryAction slot, with the Generate Report button disabled until at least one expense exists.
