Source Tour 25: Transcription Keeper

Status: LIVE on the App Store (v1.1). Production audio-recorder + speech-to-text utility for iPhone and iPad. Apple's Speech framework on top of an audio-file recording pipeline.

Two paths: install the live app to use the finished product, or clone the repo and read the source. The architecture is small — ~1100 lines across nine Swift files — with one substantive teaching surface (the async wrapper around Apple's callback-based SFSpeechRecognizer API). See Book 21 Git-And-GitHub for the clone workflow.

What Transcription Keeper shows at production scale

  • Apple's Speech framework via SFSpeechRecognizer — on-device speech-to-text using Apple's first-party speech model. No third-party API calls, no audio data sent to a server.
  • The two-phase recorder-then-transcriber pattern — record audio first, save it as a file, then transcribe the file. Different shape than live-streaming transcription, simpler to reason about, easier to retry on failure.
  • The async wrapper around a callback-based Apple API — one of the most reusable patterns in modern Swift. Apple's older frameworks use closure callbacks; modern call sites want async/await. The wrapper bridges them.
  • A complete utility app at ~1100 lines — small enough to read end-to-end on an afternoon.

The async wrapper around SFSpeechRecognizer

Apple's SFSpeechRecognizer ships with a callback-based recognition API. You hand it a request and a closure; it calls your closure repeatedly with intermediate results, then once more with the final result. That's fine in 2017 SDK style, but in modern Swift you almost always want try await at the call site.

Open TranscriptionService.swift in the repo. The interesting part is at the bottom of the file:

extension SFSpeechRecognizer {
    /// Async wrapper for recognition task
    func recognitionTask(with request: SFSpeechRecognitionRequest) async throws -> SFSpeechRecognitionResult {
        try await withCheckedThrowingContinuation { continuation in
            recognitionTask(with: request) { result, error in
                if let error = error {
                    continuation.resume(throwing: error)
                } else if let result = result, result.isFinal {
                    continuation.resume(returning: result)
                }
            }
        }
    }
}

Three things to notice:

  • withCheckedThrowingContinuation is Swift's standard tool for bridging callback-based APIs into async/await. Inside the closure, continuation.resume(returning:) hands a value back to the awaiting call site; continuation.resume(throwing:) throws an error. You must call resume exactly once per continuation — calling it twice or zero times is a runtime error.
  • The result.isFinal guard is what makes this wrapper correct. SFSpeechRecognizer calls the closure multiple times during recognition with intermediate partial results. The wrapper only resumes the continuation when the final result arrives, ignoring the partial ones. Without that guard, the wrapper would resume on the first partial and throw on every subsequent callback (because resume-twice is the runtime error mentioned above).
  • The error path resumes too. If the recognition task fails, continuation.resume(throwing: error) propagates that error up to the awaiting call site, where it surfaces as a normal Swift throws. The call site doesn't need to know the API was originally callback-based.

Now the call site at line 66 reads cleanly:

let result = try await recognizer.recognitionTask(with: request)
transcription = result.bestTranscription.formattedString

That's the pattern: messy callback API at the bottom of the file, clean try await at the top. The wrapper lives in an extension so it doesn't pollute the type's public surface in places that don't import this file.

The two-phase recorder-then-transcriber design

Transcription Keeper does not do live streaming transcription. It records audio first, saves it to a file, then transcribes the file as a separate step. That choice shows up at SmartAudioRecorder.swift for the recording side and TranscriptionService.swift for the transcription side. The two services don't know about each other — ContentView orchestrates them.

Why split the phases?

  • Failure is recoverable. If transcription fails (network issue, recognition timeout, unsupported locale), the audio file is still on disk. The user can retry transcription without re-recording. Live streaming loses the audio when transcription fails.
  • The user can review what they recorded before transcribing. Trim the silence at the start, scrub to the part they want transcribed, share just the audio without transcription if that's what they need.
  • The recorder doesn't have to know about the recognizer. Each service has one job. SmartAudioRecorder writes m4a files; TranscriptionService reads them. The contract between them is just a file URL.

This is a small app demonstrating a general principle: when an operation is naturally two phases, separating them makes each phase simpler than a fused live pipeline would have been. The cost is the disk write between phases; the savings are recoverability and clean separation of concerns.
