Build-Along 06: BodyReadings — HealthKit and CoreMotion Together

BodyReadings is a single-screen iPhone app that shows three live readings: your latest heart rate (from Apple Health), today's step count, and a three-axis live accelerometer meter. Phosphor-green CRT aesthetic. The whole app is small enough that the load-bearing pieces fit in this chapter. Build it once, see HealthKit and CoreMotion working side by side.

The repository: github.com/fluhartyml/Body-Readings. The wiki: github.com/fluhartyml/Body-Readings/wiki. Clone-and-build, no App Store release planned in Volume 1's window.

The Brainstorm

Two of the most-requested iOS frameworks for new developers are HealthKit and CoreMotion. They are different in shape: HealthKit is a database of stored samples that you query asynchronously; CoreMotion is a live sensor stream that you subscribe to. A teaching app that demonstrates both side by side has to land authorization, async query, and live callback in the same screen without crowding the UI.

v0.1 spec:

  • Heart rate — latest BPM from Apple Health, with the timestamp of the reading
  • Steps today — running count from midnight
  • Live motion — three meters (X, Y, Z) bouncing in real time
  • Pulsing heart icon, animation tempo tied to BPM
  • Phosphor-green retro vitals-monitor look
  • Single screen, no navigation, no settings
  • iPhone-only (iPad works but is not the target form factor)

What is intentionally NOT in v0.1:

  • No persistence — every value is read fresh from Health or sensor
  • No charts — that is a later chapter (Swift Charts on top of HealthKit)
  • No widget — HealthKit + Widgets is its own concurrency story
  • No Apple Watch companion — doubles the build, separate chapter material

The Architecture

Two stores own the state. SwiftUI views observe them directly. Nothing else holds state.

@MainActor @Observable
final class HealthStore {
    static let isAvailable = HKHealthStore.isHealthDataAvailable()
    private let store = HKHealthStore()
    private let heartRateType = HKObjectType.quantityType(forIdentifier: .heartRate)!
    private let stepCountType = HKObjectType.quantityType(forIdentifier: .stepCount)!

    var heartRate: Double? = nil
    var heartRateTimestamp: Date? = nil
    var todaysSteps: Int? = nil
    var didFinishInitialLoad = false
    var lastError: String? = nil
    var isAuthorized = false
    var hasRequestedAuth = false
    // ...
}
@MainActor @Observable
final class MotionStore {
    private let manager = CMMotionManager()

    var x: Double = 0
    var y: Double = 0
    var z: Double = 0
    var isStreaming = false
    var isAvailable: Bool { manager.isAccelerometerAvailable }
    // ...
}

@MainActor on both stores keeps every method on the main thread, which is correct for state that drives UI. @Observable (Swift 5.9+) replaces the older ObservableObject + @Published dance — SwiftUI re-renders the views that read changed properties, automatically.

The app entry injects both stores via .environment and starts the motion stream as soon as the view appears. Note what is not in .task — the Health authorization request. That comes later.

@main
struct Body_ReadingsApp: App {
    @State private var health = HealthStore()
    @State private var motion = MotionStore()

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(health)
                .environment(motion)
                .task { motion.start() }
        }
    }
}

HealthKit: The Authorization Flow

HealthKit requires the user's explicit permission for every data type the app reads. The system shows a permission sheet with a toggle for each type; the user flips them on (or doesn't) and taps Allow. Two essential rules apply.

Rule one: the system dialog's toggles default to OFF. The user must flip them on to grant access. If the user taps Allow without flipping anything, the app sees no data — and Apple intentionally hides whether that happened.

Rule two: Apple's privacy design hides whether the user denied READ access. authorizationStatus(for:) returns .sharingDenied for both "user denied" and "user has not been asked." The only honest way to know whether you have read access is to attempt the read and see if data comes back.

The authorization call itself is straightforward async/await:

func requestAuthorization() async {
    hasRequestedAuth = true
    lastError = nil
    guard Self.isAvailable else {
        lastError = "Health data isn't available on this device."
        didFinishInitialLoad = true
        return
    }
    do {
        try await store.requestAuthorization(
            toShare: [],
            read: [heartRateType, stepCountType]
        )
        isAuthorized = true
        await refresh()
    } catch {
        lastError = error.localizedDescription
        didFinishInitialLoad = true
    }
}

The toShare parameter is empty — this app only reads, never writes. Read-only access doesn't need the data types enumerated in the entitlements file; only writes do.

HealthKit: The Two Queries

Heart rate uses HKSampleQuery — the right tool for "give me the most recent N samples of type X." Steps use HKStatisticsQuery with .cumulativeSum — the right tool for "give me the running total over a window."

Latest heart rate

private func loadLatestHeartRate() async {
    await withCheckedContinuation { continuation in
        let sortDescriptor = NSSortDescriptor(
            key: HKSampleSortIdentifierEndDate, ascending: false
        )
        let query = HKSampleQuery(
            sampleType: heartRateType,
            predicate: nil,
            limit: 1,
            sortDescriptors: [sortDescriptor]
        ) { [weak self] _, samples, _ in
            Task { @MainActor in
                guard let self else { continuation.resume(); return }
                if let sample = samples?.first as? HKQuantitySample {
                    let bpmUnit = HKUnit.count().unitDivided(by: .minute())
                    self.heartRate = sample.quantity.doubleValue(for: bpmUnit)
                    self.heartRateTimestamp = sample.endDate
                } else {
                    self.heartRate = nil
                    self.heartRateTimestamp = nil
                }
                continuation.resume()
            }
        }
        store.execute(query)
    }
}

Three things make this work. withCheckedContinuation bridges HealthKit's NSObject-callback API to Swift async: we suspend the calling task, execute the query, and resume the continuation when the callback fires. [weak self] avoids the closure retaining the store. Task { @MainActor in ... } hops back to main before touching @Observable properties — HealthKit delivers callbacks on a private queue, so writing observable state directly from there would be a concurrency violation.

The unit conversion deserves a beat. Heart rate is stored in HealthKit as count/sec internally, but BPM is the user-facing number. HKUnit.count().unitDivided(by: .minute()) reads as "counts per minute" — literally beats per minute. The same conversion idiom works for any other rate unit you might need (counts per second, steps per hour, etc.).

Today's steps

private func loadTodaysSteps() async {
    await withCheckedContinuation { continuation in
        let calendar = Calendar.current
        let startOfDay = calendar.startOfDay(for: Date())
        let predicate = HKQuery.predicateForSamples(
            withStart: startOfDay, end: nil, options: []
        )
        let query = HKStatisticsQuery(
            quantityType: stepCountType,
            quantitySamplePredicate: predicate,
            options: .cumulativeSum
        ) { [weak self] _, statistics, _ in
            Task { @MainActor in
                guard let self else { continuation.resume(); return }
                if let sum = statistics?.sumQuantity() {
                    self.todaysSteps = Int(sum.doubleValue(for: HKUnit.count()))
                } else {
                    self.todaysSteps = 0
                }
                continuation.resume()
            }
        }
        store.execute(query)
    }
}

Why HKStatisticsQuery with .cumulativeSum instead of fetching individual step samples and summing them? HealthKit deduplicates step samples across data sources — the iPhone pedometer and an Apple Watch on the same wrist would otherwise double-count overlapping windows. The statistics query runs Apple's deduplication for us. Naive summation would silently double the step count for any user wearing a Watch.

Calendar.current.startOfDay(for: Date()) honors the device's calendar and time zone. Using a UTC-based predicate would cause "today's steps" to roll over at random hours for non-UTC users.

CoreMotion: The Live Stream

CoreMotion is the simpler half. No async/await dance, no NSObject callback bridge — the framework already supports a closure-based callback that fires on the queue you specify.

func start() {
    guard manager.isAccelerometerAvailable, !isStreaming else { return }
    manager.accelerometerUpdateInterval = 1.0 / 30.0   // 30 Hz
    manager.startAccelerometerUpdates(to: .main) { [weak self] data, _ in
        guard let self, let data else { return }
        self.x = data.acceleration.x
        self.y = data.acceleration.y
        self.z = data.acceleration.z
    }
    isStreaming = true
}

Two design choices live in this short method.

30 Hz update interval. The accelerometer hardware can deliver up to 100 Hz, but UI bars don't need more than ~24 Hz to feel live. 30 Hz is the safe middle — smooth animation, negligible battery cost. Setting accelerometerUpdateInterval after startAccelerometerUpdates has no effect on the current stream; set it first.

Updates delivered on .main. Because the callback writes to @Observable properties that drive SwiftUI views, delivering on the main queue means we can write directly without an actor hop. SwiftUI re-renders automatically the next runloop tick.

The values you see in x, y, z are in g-units (1g ≈ 9.81 m/s²). At rest with the iPhone face-up, expect roughly (0, 0, -1) — gravity pulling down through the screen. Rotate the phone and the components redistribute; shake it and they spike past 1.0g.

Permissions and Entitlements

Two surfaces have to agree for HealthKit to work: the entitlements file and the Info.plist usage description.

Body_Readings.entitlements:

<key>com.apple.developer.healthkit</key>
<true/>
<key>com.apple.developer.healthkit.access</key>
<array/>

The empty array is correct — only "share" (write) data types need to be enumerated; read-only access doesn't.

Info.plist:

<key>NSHealthShareUsageDescription</key>
<string>Body Readings shows your latest heart rate and today's step count from Apple Health.</string>
<key>NSMotionUsageDescription</key>
<string>Body Readings shows live accelerometer values so you can see how the phone senses movement.</string>

Both strings are user-visible — iOS shows them inside the system permission dialogs verbatim. Write them in the user's voice, not the developer's.

The cleanest way to wire all of this in Xcode is the Capabilities tab: target → Signing & Capabilities → + Capability → HealthKit. That single click adds the framework reference, writes the entitlement, and prompts for the Info.plist key. CoreMotion does not need a capability — the NSMotionUsageDescription in Info.plist is sufficient.

The Auth-Timeout Story

The first real-device test failed in an instructive way. The app's launch flow originally called requestAuthorization from the App's .task modifier:

// Original v0.1 design
.task {
    await health.requestAuthorization()
    motion.start()
}

On the simulator the call worked fine. On a real iPhone, the system returned "Authorization session timed out" — with no permission dialog ever appearing. The error surfaced in the UI and the heart rate / steps cards stayed empty.

The diagnosis: .task fires very early in the view lifecycle, before the app's window is fully presented. HealthKit needs a presentable view hierarchy to show its sheet; calling requestAuthorization before that's ready fails silently with the timeout error. Simulator timing is forgiving enough that the bug doesn't reproduce; real-device timing surfaces it immediately.

The fix: replace the auto-trigger with a manual CONNECT TO HEALTH button in the UI. The user taps it; by the time their finger is on the button, the view hierarchy is unambiguously ready. The button calls requestAuthorization from inside its action closure, and the system dialog presents reliably every time.

private var connectButton: some View {
    Button {
        Task {
            isRequestingAuth = true
            await health.requestAuthorization()
            isRequestingAuth = false
        }
    } label: {
        // ... label content with spinner during auth
    }
    .disabled(isRequestingAuth)
}

Two lessons travel with this fix.

  1. Don't auto-prompt on launch. Even when the timing works, auto-prompting is annoying for users who already granted access (the call is idempotent and harmless, but a spinner flashes). With a manual button, authorized users skip straight to readings; new users tap CONNECT once.
  2. Cached denials. Once iOS records a denial, requestAuthorization returns immediately on every subsequent call without re-presenting the dialog. The user must go to Settings → Privacy & Security → Health → [App] to grant access manually. There is no API to re-prompt. The app's UI surfaces an OPEN SETTINGS button that deep-links to that page when readings stay blank after auth, so the user has a clear escape hatch.

The Three UI States

BodyReadings cards have to render correctly in three distinct states. A reader can hit any of them depending on whether they've granted access yet.

Pre-auth: the user hasn't tapped CONNECT yet. hasRequestedAuth == false. Cards show NOT CONNECTED. The CONNECT TO HEALTH button is visible.

In-flight: the user tapped CONNECT, the system dialog appeared, the user is responding. hasRequestedAuth == true AND didFinishInitialLoad == false. Cards show READING…. The button shows a spinner.

Resolved: the auth call returned. didFinishInitialLoad == true. Cards show actual data, OR the NO RECENT READING / 0 empty state, OR an error message with a TRY AGAIN button. If readings are blank, the OPEN SETTINGS button appears below.

Why three states instead of two? Empty heartRate is ambiguous. It could mean "still loading" OR "loaded but the read returned nothing." The UI needs to show different things for those two cases (spinner vs explanatory text). A separate didFinishInitialLoad Bool disambiguates them. Earlier versions of similar apps got infinite spinners on quiet failures — bad UX, hard to diagnose. The current shape is the lesson learned.

The Heart Animation

One small visual touch makes the readout feel alive: the heart icon pulses, and the pulse tempo is tied to the actual BPM.

Image(systemName: "heart.fill")
    .font(.system(size: 44))
    .foregroundStyle(Color.phosphor)
    .scaleEffect(pulse ? 1.12 : 0.94)
    .animation(
        .easeInOut(duration: heartAnimationDuration)
            .repeatForever(autoreverses: true),
        value: pulse
    )
    .onAppear { pulse = true }

private var heartAnimationDuration: Double {
    guard let bpm = health.heartRate, bpm > 0 else { return 0.6 }
    return min(1.5, max(0.3, 60.0 / bpm / 2.0))
}

60.0 / bpm gives seconds-per-beat; dividing by 2 gives a half-cycle (one beat = scale up + scale down). Clamps prevent UI weirdness at extreme values: 0.3s minimum stops the icon from buzzing at 200 BPM, 1.5s maximum keeps a slow heart from looking frozen.

If bpm is nil (pre-auth or no data), the animation falls back to a neutral 0.6s tempo so the heart still pulses gently — a static heart icon would read as broken.

What This Build-Along Teaches

  • HealthKit authorization — the modern async requestAuthorization(toShare: read:) shape, the read-only entitlement pattern, the privacy-by-design auth-status semantics
  • Bridging callback APIs to async via withCheckedContinuation — the pattern Apple's older NSObject-style frameworks need to play nicely with Swift concurrency
  • HKSampleQuery for "latest sample" — sort descending by endDate, limit 1, no predicate
  • HKStatisticsQuery with .cumulativeSum — the right query for "today's total" with automatic deduplication across data sources
  • HealthKit unit conversion — HKUnit.count().unitDivided(by: .minute()) for BPM
  • CMMotionManager.startAccelerometerUpdates — the closure-based live-stream API, delivered on a queue you specify
  • The auth-on-launch race and why a manual button is more reliable
  • Three-state UI design — pre-auth / in-flight / resolved, with an explicit didFinishInitialLoad flag to disambiguate empty-from-loading vs empty-from-result
  • Settings deep-link recovery — UIApplication.openSettingsURLString as the escape hatch when iOS has cached a denial
  • BPM-tied animation tempo — tying SwiftUI animation duration to live data so the UI feels the data

Cloning and Building

BodyReadings is a clone-and-build app for Volume 1 — not currently distributed via the App Store. To get a working copy:

  1. Open Xcode and choose Source Control → Clone; paste https://github.com/fluhartyml/Body-Readings.
  2. Pick a real iPhone destination (the simulator works for verifying the auth flow but has no Health data; you'll see NO RECENT READING and 0 steps).
  3. ⌘R to build and run.
  4. On first launch, tap CONNECT TO HEALTH. iOS shows the permission dialog — flip Heart Rate and Steps toggles ON, then tap Allow.
  5. Heart rate, steps, and live motion all populate.
