Source Tour 19: Tally Matrix Clock

Status: LIVE on the tvOS App Store (v2.4.1). Production clock app for Apple TV with matrix-grid time display, WeatherKit integration, and tvOS focus-engine handling.

Source tour for Tally Matrix Clock. Anchors two book lessons: the circular-time-model insight (modulo arithmetic for clocks) and the WeatherKit-attribution-isn't-sticky discipline. Clone the repo and follow along: github.com/fluhartyml/Tally-Matrix-Clock.

What Tally Matrix Clock shows at production scale

  • Modulo arithmetic for 12-hour clock display — the circular time model that turns out to be unexpectedly subtle (see below)
  • Custom matrix-grid digit rendering: 1×3 and 3×3 SwiftUI grids where the count of lit squares represents each digit
  • Pattern shuffling on a timer for visual variety while keeping the math correct
  • WeatherKit integration with the per-update attribution discipline (see lesson below)
  • tvOS focus-engine handling for d-pad navigation across shuffle/repeat controls

The circular time model

A clock face is a circle. Hours wrap around from 12 back to 1. Minutes wrap around from 59 back to 00. The math that backs this is modular arithmetic — the operator % in Swift — and Tally Matrix Clock's whole display is built on top of two clean modulo operations stacked on each other.

Open ContentView.swift and find the computed properties around line 527:

var displayHour: Int {
    let hour = Calendar.current.component(.hour, from: currentTime)
    if settings.use24Hour {
        return hour
    } else {
        let hour12 = hour % 12
        return hour12 == 0 ? 12 : hour12
    }
}

var isPM: Bool {
    Calendar.current.component(.hour, from: currentTime) >= 12
}

var hoursTens: Int { displayHour / 10 }
var hoursOnes: Int { displayHour % 10 }
var minutesTens: Int { Calendar.current.component(.minute, from: currentTime) / 10 }
var minutesOnes: Int { Calendar.current.component(.minute, from: currentTime) % 10 }

Two passes of modulo do the whole job:

  • First pass — 24-hour to 12-hour wrap. Calendar hands you an hour 0–23. hour % 12 wraps that to 0–11. Hour 13 becomes 1, hour 14 becomes 2, hour 23 becomes 11. The clock-face circularity falls out of the math automatically.
  • Second pass — digit extraction. Once you have the display value, / 10 gives you the tens digit and % 10 gives you the ones digit. Same modulo trick, applied to base-10 instead of base-12.

The boundary case that trips you up

Look at the special case: hour12 == 0 ? 12 : hour12.

If you trust modulo blindly, midnight (hour 0) gives 0 % 12 == 0, and noon (hour 12) gives 12 % 12 == 0. Both come out as 0. But on a 12-hour clock face, both display as 12, not 0 — there's no "0 o'clock" on the dial. The ternary catches the boundary and substitutes 12 for 0.

This is the kind of off-by-one that bites cyclic-data code everywhere — weekdays (is Sunday 0 or 7?), compass bearings (is North 0° or 360°?), card suit indices in a circular deck. The lesson: modulo gives you most of the cycle for free, but always check what your domain calls the boundary value.

Why the matrix grids work

Once displayHour is split into hoursTens and hoursOnes, each digit feeds a matrix view from TallyMatrixViews.swift:

  • TallyMatrix1x3 — a 1×3 column for the tens-of-hours digit (practical range 0–2)
  • TallyMatrix3x3 × 3 — for ones-of-hours, tens-of-minutes (practical range 0–5), and ones-of-minutes

Why the clock is base-10, not base-12 or base-60

It's worth being precise about this. The display reads as H H : M M — four positions, each one its own digit. The clock is base-10 at the digit level, not base-12 for the hour or base-60 for the minute. Every position draws from 0–9 independently.

The smaller practical ranges you see — tens-of-hours capped at 2 in 24-hour mode (or 1 in 12-hour mode), tens-of-minutes capped at 5 — come from the clock's value bounds, not from the digit base. The grid could show 0–9 in any slot. It just never needs to in the tens positions, because no clock has 70 minutes or 30 hours. The 3×3 grid is the canonical base-10 single-digit display surface; the 1×3 grid is a smaller fitted variant for the tens-of-hours position where 0–2 is the only range that can occur.

That's why the matrix lookup is so clean. hoursTens = displayHour / 10 and hoursOnes = displayHour % 10 — classic base-10 digit extraction. No special arithmetic for "minutes are base-60." The % 12 step earlier handled the clock-face cyclical math; once you're past that, you're back in plain base-10 territory and the rest of the math reads like a textbook.

The "matrix" name comes from the SwiftUI view, but the deeper insight is that the count of lit squares is the digit value, not their positions. That decoupling is what lets the pattern shuffle visually without breaking the math.

The pattern shuffle

Every patternInterval seconds (or whenever a digit changes), updatePatterns() in ContentView.swift:715 rebuilds all four matrices from the current time. The actual pattern picker lives at line 732:

func randomPattern(for value: Int, totalSquares: Int) -> Set<Int> {
    guard value > 0 else { return [] }
    var pattern = Set<Int>()
    while pattern.count < value {
        pattern.insert(Int.random(in: 0..<totalSquares))
    }
    return pattern
}

A Set<Int> of square indices is a clean way to express "these positions, in any order, are lit." Inserting random indices until the set reaches the target count handles deduplication automatically — if you happen to roll the same index twice, the set rejects the duplicate and the loop just keeps going. The displayed digit value stays correct because the set's count is the contract.

This is a small example of using the right collection type for the semantics you want. A [Int] array would have let you accidentally light the same square twice while still incrementing the visible count. Set<Int> makes that bug impossible by construction.

The tvOS focus engine

Tally Matrix Clock is a tvOS app. That changes how interaction works: there's no touch, no mouse cursor, no keyboard. Users navigate with the Apple TV remote's d-pad, and every focusable element gets a system-drawn highlight when the focus engine selects it. The default highlight is a soft white ring — clean, but bland against the clock's deep-black background.

Open Models.swift and find SettingsFocusButtonStyle at the bottom of the file:

struct SettingsFocusButtonStyle: ButtonStyle {
    @Environment(\.isFocused) var isFocused

    func makeBody(configuration: Configuration) -> some View {
        configuration.label
            .foregroundColor(isFocused ? .black : .white)
            .padding(.horizontal, 12)
            .padding(.vertical, 6)
            .background(
                RoundedRectangle(cornerRadius: 8)
                    .fill(isFocused ? Color.white : Color.clear)
            )
            .scaleEffect(isFocused ? 1.02 : 1.0)
            .animation(.easeInOut(duration: 0.15), value: isFocused)
    }
}

This is a custom ButtonStyle that takes over the focus highlight from the system. The key piece is @Environment(\.isFocused) — a built-in environment value tvOS sets to true when a button is the current focus target. The style flips the button's background to solid white, inverts the text to black, and adds a small scaleEffect bump for a tactile feel.

The lesson worth carrying to your own tvOS apps: read isFocused from the environment, write your own visual response, don't rely on the system default if your app's color palette doesn't match it. tvOS gives you the focus signal; the visual treatment is yours to own.

The WeatherKit attribution lesson

Tally Matrix Clock was previously approved with its WeatherKit integration, then flagged on a later update for attribution that had previously passed. The lesson that belongs here, not anywhere else: App Store approval is not sticky. Every update has to prove WeatherKit attribution in its own screenshots and copy. A reviewer who didn't notice before can notice now.
