VII.10  Build-Along 10: DragBetweenWindows — Cross-Scene Drag-and-Drop

Distribution: GitHub clone-and-build. DragBetweenWindows is a single-concept teaching app. Two windows side by side; a list of colored tokens on the left, a drop zone on the right. Pick a token up with a long-press, drag it across the seam between the windows, drop it into the dashed rectangle. The drop list updates and the app is essentially over — the entire teaching point is the seam-crossing itself.

The repository: github.com/fluhartyml/DragBetweenWindows. The wiki: github.com/fluhartyml/DragBetweenWindows/wiki. Built atop SwiftUI scenes (WindowGroup(id:)), the Transferable protocol, CodableRepresentation, and an @Observable class threaded through both windows via .environment(_:).

Hardware requirement: the demo runs on Mac (any model) and on M-series iPad (iPad Pro M1/M2/M4 or iPad Air M1/M2/M3) with Stage Manager on. A-series iPads (iPad mini, base iPad, older Pro/Air) cannot run the demo — Stage Manager is not supported on those chips, and without Stage Manager iPad has no way to show two windows at once. iPhone runs one window at a time and also cannot run the demo. The source code reads on any platform; the running demo does not.

VII.10.1  The Brainstorm

VII.10.1 ¶1 Drag-and-drop within a single window is well-trodden territory. Most apps move things around inside themselves — reordering a list, dropping a file onto a sidebar. That is not interesting in 2026. What still teaches is cross-scene drag-and-drop: picking up a payload in one window and depositing it in another window of the same app. This is the gesture the Finder uses every time you drag a file from one Finder window to another, the gesture Mail uses to move a message into a folder pane, the gesture every Mac-native app eventually needs.

VII.10.1 ¶2 v1.0 spec:

VII.10.1 ¶3
  • A Source window listing ten colored tokens (Crimson through Magenta) with names and hue values
  • A Drop window with a dashed-bordered drop zone and an empty-state prompt
  • Long-press-and-drag a token from Source to drop it into Drop
  • Visual feedback while dragging (the drop zone darkens and changes its label)
  • A list of dropped tokens persists for the lifetime of the app session
  • Clear button on the Drop window to empty the list
  • Under the Hood sheet (developer notes inside the app)
  • About sheet (icon, attribution, links)
  • Light + dark icon variants. No tinted variant.

VII.10.1 ¶4 What is intentionally NOT in v1.0:

VII.10.1 ¶5
  • No persistence beyond the session — SwiftData has no place here, and dropped tokens are not data the app needs to keep
  • No iPhone alternative layout — the chapter teaches the Mac-and-iPad path; iPhone is a future companion concept
  • No App Store submission — Apple's Guideline 2.2 reads gesture demos as "limited functionality," and that is a fair reading
  • No multi-select drag, no inter-app drag, no cross-process drag — one window to another window of the same process is enough

VII.10.2  The Architecture

VII.10.2 ¶1 Seven Swift files plus the Info.plist and the AppIcon set. The model layer is one file. Each window is one file. The cross-cutting plumbing (developer notes, Under the Hood, About) is one file each.

VII.10.2 ¶2
DragBetweenWindowsApp.swift   # @main · declares two WindowGroups
ContentView.swift             # Source list · .draggable on each row
DropWindowView.swift          # Drop zone · .dropDestination · isTargeted feedback
Token.swift                   # Token model + Transferable + Dropbox @Observable
DeveloperNotes.swift          # Six notes shown in Under the Hood
UnderTheHoodView.swift        # Sectioned reader for the notes
AboutView.swift               # Icon · attribution · links

VII.10.2 ¶3 The flow of a single drag-and-drop, end to end: a touch lands on a row in Source, becomes a long-press, the long-press becomes a drag, SwiftUI asks Token for its transferRepresentation, encodes the token as JSON, and hands the encoded payload off to the system drag manager. The user's finger crosses into the Drop window. The Drop window's .dropDestination(for: Token.self) recognizes the type, redraws the dashed border in a hover state, and waits. The user lifts their finger inside the zone. SwiftUI decodes the JSON back into a Token, hands it to the drop closure, and the closure appends the token to the shared Dropbox.

VII.10.3  Two Windows, One App

VII.10.3 ¶1 SwiftUI calls a window a scene. An app declares scenes inside the body of its App struct. Each scene gets a stable id so other parts of the app can ask the system to open it.

VII.10.3 ¶2
@main
struct DragBetweenWindowsApp: App {
    @State private var dropbox = Dropbox()

    var body: some Scene {
        WindowGroup("Drag Between Windows", id: "source") {
            ContentView()
                .environment(dropbox)
        }

        WindowGroup("Drop Window", id: "drop") {
            DropWindowView()
                .environment(dropbox)
        }
    }
}

VII.10.3 ¶3 Two WindowGroups with the ids "source" and "drop". Both receive the same dropbox instance via .environment(_:) — that is the seam through which state crosses windows. The @State on dropbox ties its lifetime to the App struct, which means it lives for the entire run of the app, not just for the lifetime of any one window.

VII.10.3 ¶4 Opening the second window from inside the first uses the openWindow environment action.

VII.10.3 ¶5
@Environment(\.openWindow) private var openWindow

Button {
    openWindow(id: "drop")
} label: {
    Image(systemName: "rectangle.on.rectangle")
}

VII.10.3 ¶6 The id passed to openWindow(id:) has to match the id declared on the target WindowGroup. There is no compile-time check; if you typo "drop" as "dropp", the button will silently do nothing. Treat these ids the way you treat URL routes — spell them once, in one place, and reach for that constant everywhere else if the app grows.

VII.10.4  Transferable, Not NSItemProvider

VII.10.4 ¶1 SwiftUI's drag-and-drop machinery used to be wrapped around AppKit and UIKit's NSItemProvider, which was awkward to read and worse to write. Swift 5.7 introduced the Transferable protocol, and the SwiftUI APIs moved to it as the canonical path. Transferable is the one you reach for now.

VII.10.4 ¶2 To make a value type draggable, conform it to Transferable and declare a transferRepresentation. The simplest representation is CodableRepresentation, which uses Codable conformance to encode and decode the payload as JSON.

VII.10.4 ¶3
struct Token: Identifiable, Hashable, Codable, Transferable {
    let id: UUID
    var name: String
    var hue: Double

    var color: Color {
        Color(hue: hue, saturation: 0.7, brightness: 0.95)
    }

    static var transferRepresentation: some TransferRepresentation {
        CodableRepresentation(contentType: .dragBetweenWindowsToken)
    }
}

extension UTType {
    static let dragBetweenWindowsToken = UTType(exportedAs: "me.fluharty.DragBetweenWindows.token")
}

VII.10.4 ¶4 The contentType: argument on CodableRepresentation tells the system the Uniform Type Identifier (UTI) of the encoded payload. UTIs are the same identifier system that lets a finder file know whether it is a JPEG, a PDF, or something custom. Token declares its own UTI — me.fluharty.DragBetweenWindows.token — because that is how cross-scene drag-and-drop knows which drop zones are willing to accept the payload.

VII.10.5  The UTType Trap (and the Built-In Fallback)

VII.10.5 ¶1 There is a real trap here that you will hit the first time you run the app. Custom UTIs need to be registered with the operating system, and the way you register them is by declaring them in the app's Info.plist under UTExportedTypeDeclarations. If the UTI is not registered, the system does not know what me.fluharty.DragBetweenWindows.token is, the drag fingerprint never matches the drop target's for: Token.self, and the drop silently fails. The console prints:

VII.10.5 ¶2
Type "me.fluharty.DragBetweenWindows.token" was expected to be declared
and exported in the Info.plist of DragBetweenWindows.app, but it was not found.

VII.10.5 ¶3 You have two ways out. The first is to add the Info.plist declaration, which looks like this in source form:

VII.10.5 ¶4
<key>UTExportedTypeDeclarations</key>
<array>
    <dict>
        <key>UTTypeIdentifier</key>
        <string>me.fluharty.DragBetweenWindows.token</string>
        <key>UTTypeConformsTo</key>
        <array>
            <string>public.data</string>
        </array>
        <key>UTTypeDescription</key>
        <string>DragBetweenWindows Token</string>
        <key>UTTypeTagSpecification</key>
        <dict/>
    </dict>
</array>

VII.10.5 ¶5 That is correct. It is also six lines of XML the reader has to memorize and a habit of editing the Info.plist by hand that the reader does not need yet.

VII.10.5 ¶6 The second way out is to give up on the custom UTI entirely and use a built-in content type that is already registered with the system. The cleanest one is .json, since Token is already Codable and CodableRepresentation is already serializing as JSON. The change is one line:

VII.10.5 ¶7
// Custom UTI — requires Info.plist declaration
static var transferRepresentation: some TransferRepresentation {
    CodableRepresentation(contentType: .dragBetweenWindowsToken)
}

// Built-in JSON — system-registered, no Info.plist work
static var transferRepresentation: some TransferRepresentation {
    CodableRepresentation(contentType: .json)
}

VII.10.5 ¶8 The trade is straightforward. The custom UTI is "production correct" in the sense that an app shipping serious data types in pasteboard or document format ought to declare its types properly so other apps can recognize them. The .json path skips that ceremony and gets the in-app drag working immediately, at the cost of generality — any other app that drops JSON onto your zone would also match the for: Token.self filter, and the decode would fail at the boundary instead of the type-match boundary.

VII.10.5 ¶9 For a teaching app where the entire interaction is in-process, the .json path is the right choice. The lesson is "reach for built-in content types before you reach for custom UTIs," and the lesson generalizes well: most apps never need a custom UTI in the first place.

VII.10.6  Shared State: the @Observable Dropbox

VII.10.6 ¶1 The Source window does not know what is in the Drop window. The Drop window does not know which token was just dragged. Both windows talk through a shared store, which is the Dropbox class.

VII.10.6 ¶2
@Observable
final class Dropbox {
    var dropped: [Token] = []

    func accept(_ token: Token) {
        guard !dropped.contains(token) else { return }
        dropped.append(token)
    }

    func clear() {
        dropped.removeAll()
    }
}

VII.10.6 ¶3 The @Observable macro is Swift 6's replacement for ObservableObject + @Published. It auto-generates change tracking for every stored property without having to mark each one. The class is shared across both windows by injecting the same instance into the environment of each WindowGroup:

VII.10.6 ¶4
.environment(dropbox)

VII.10.6 ¶5 Inside each window's view, the dropbox is read out of the environment with @Environment(Dropbox.self). SwiftUI handles the bookkeeping: when accept(_:) appends to dropped, the Drop window's list view re-renders. The Source window does not re-render, because it does not read dropped — only the Drop window does. That is the right kind of coupling: shared state, decoupled views.

VII.10.7  The Drop Zone: dropDestination + isTargeted

VII.10.7 ¶1 A drop zone is any view with a .dropDestination(for:action:isTargeted:) modifier attached. The modifier takes three pieces: the type to accept, a closure that runs on drop, and a binding that flips between true and false while a drag is hovering over the zone.

VII.10.7 ¶2
@State private var isTargeted = false

RoundedRectangle(cornerRadius: 12, style: .continuous)
    .strokeBorder(style: StrokeStyle(lineWidth: 2, dash: [8, 6]))
    .foregroundStyle(isTargeted ? Color.accentColor : Color.secondary)
    .overlay {
        Text(isTargeted ? "Release to drop" : "Drop a token here")
            .foregroundStyle(isTargeted ? Color.accentColor : Color.secondary)
    }
    .frame(height: 180)
    .padding()
    .dropDestination(for: Token.self) { tokens, _ in
        for token in tokens { dropbox.accept(token) }
        return true
    } isTargeted: { hovering in
        isTargeted = hovering
    }

VII.10.7 ¶3 The third argument is the one that makes the demo feel alive. As soon as the user's finger crosses the zone with a token in flight, isTargeted flips to true, the dashed border darkens to the accent color, and the label changes from "Drop a token here" to "Release to drop." The user gets confirmation before they release, which removes the "did it work?" uncertainty that drag-and-drop without feedback always carries.

VII.10.7 ¶4 The drop closure receives an array because the drag system supports multi-item drags — the user could in principle drag a selection of tokens, not just one. v1.0 only sets up single-item drags so the array always has exactly one element, but the API shape is forward-compatible.

VII.10.8  Hardware Requirements for the Demo

VII.10.8 ¶1 The cross-window experience works on some Apple hardware and not others. The deciding factor is whether the device supports Stage Manager, the iPadOS feature Apple introduced with iPadOS 16 to bring real multi-window behavior to iPad. Stage Manager requires an M-series Apple Silicon chip on iPad; on Mac, multi-window has always been native to the platform.

VII.10.8 ¶2 The breakdown:

VII.10.8 ¶3
  • Mac (any model) — the demo works. Multi-window is native to macOS. openWindow(id:) opens a real second window. Drag tokens across.
  • iPad Pro M1/M2/M4 or iPad Air M1/M2/M3, with Stage Manager enabled — the demo works. openWindow(id:) opens a real second iPad window inside the Stage Manager workspace; the user arranges the two side by side and drags across.
  • iPad mini (any), base iPad (any), or older iPad Pro/Air (A-series chips) — the demo cannot run on this hardware. Stage Manager is not supported on A-series iPads, and without Stage Manager, openWindow(id:) replaces the current window full-screen instead of opening a new one alongside. The reader can still read the source to learn the patterns, but the running demo needs Mac or M-series iPad.
  • iPhone (any model) — the demo cannot run. iPhone runs one window at a time as a hardware constraint, not a settings toggle. openWindow(id:) is a no-op. The second-window button is wired up but has nothing to act on.

VII.10.8 ¶4 For readers on M-series iPad, the path is:

VII.10.8 ¶5
  1. Turn Stage Manager on. Control Center (swipe down from the top-right corner of the screen) → tap the Stage Manager tile (a small rectangle with three dots beside it). It highlights when on. Or: Settings → Multitasking & Gestures → Stage Manager → toggle on.
  2. Launch the app. Build-and-run from Xcode to a connected iPad, or open the installed app from the Home Screen.
  3. Open the Drop window. Tap the second-window button (rectangle-on-rectangle icon) in the Source toolbar, to the left of the info button. The Drop window opens as a separate iPad window.
  4. Arrange the windows side by side. Stage Manager piles new windows toward the center of the screen. Drag one window's title bar to the right or left edge so the two windows sit next to each other.
  5. Drag a token. Long-press a token in the Source list, drag across into the dashed zone in the Drop window, release.

VII.10.8 ¶6 The chapter does not redesign the app for the unsupported hardware. A future revision may add a single-window inline variant (Source on top, Drop on bottom in one view) so iPhone and A-series iPad readers can experience an in-window drag, but v1.0 stays Mac-and-M-iPad in scope. The teaching content — Transferable, .draggable, .dropDestination, @Observable shared state — is platform-independent and reads in the source code regardless of where it can run.

VII.10.9  The Mac Tab Trap

VII.10.9 ¶1 This is the dead end every reader will hit on first run if they are testing the iPad target on an Apple Silicon Mac. macOS opens both WindowGroups as tabs of one window instead of as two separate windows. The reader sees one tab labeled "Drag Between Windows" and another labeled "Drop Window," clicks between them, and concludes the demo is broken — you can't drag between tabs.

VII.10.9 ¶2 The fix is to break a tab out of the tab bar into its own window. Hold a tab title and drag it down out of the tab bar. macOS will tear the tab off into a separate window. Position the two windows side by side on the desktop, and the drag-and-drop demo works as designed.

VII.10.9 ¶3 This behavior is not unique to DragBetweenWindows. It is how macOS handles multiple WindowGroups in any SwiftUI app: tabbing is the default presentation, and the user (or in this case the reader) decides whether to break tabs out into their own windows. A native Mac app target would have the same behavior. The chapter calls it out here because cross-window drag-and-drop is the one teaching scenario where tabbing actively breaks the lesson.
