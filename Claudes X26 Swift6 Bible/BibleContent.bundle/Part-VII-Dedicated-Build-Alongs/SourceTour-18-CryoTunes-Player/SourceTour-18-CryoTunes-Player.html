The data-layer-vs-UI-layer split

CryoTunes Player is a textbook example of why architectural rules matter in real apps. The rule:

CryoKit serves data only. The host app owns the UI.

CryoKit (the package) is responsible for talking to MusicKit, managing the playback session, holding observable state about what's playing. It does not make UI decisions. It does not write user-facing strings. It does not pop up alerts. CryoTunes Player (the app) reads CryoKit's data, presents it in the UI, and decides what the user sees.

In a small app the split feels academic. In a production app it pays off the moment you ship a bug. CryoTunes hit that moment on 2026-04-29 when a false-positive popup ("Unable to play station. Check your connection.") fired while music was actually playing. The popup string lived in CryoKit's MusicPlaybackManager — a UI-shaped piece of prose sitting on a data layer that has no business diagnosing Wi-Fi. CryoKit had no authority to make that claim; it had simply caught any throw and substituted a fabricated explanation.

The fix: CryoTunes stopped reading CryoKit's errorMessage property entirely. Severing that single binding eliminated the false-positive popup without touching CryoKit at all. The lesson generalizes:

  • A layer should only report on what it owns and observed. CryoKit owns MusicKit calls; it can throw "MusicKit call failed." It cannot diagnose the network without reading the network. Don't write user-facing prose in a data layer.
  • If a framework's API offers a UI-shaped property you didn't ask for, you don't have to read it. Public is an offer, not a requirement. Refusing to subscribe is a valid response when the offer is wrong.
  • Architectural rules earn their keep when bugs hit. If you'd kept the UI string in the data layer, the only fix would have been editing the data layer. By treating CryoKit as off-limits read-only, the fix lived entirely in the consumer.

Browse CryoTunes Player/ContentView.swift on GitHub before and after commit 06a1852 ("Stop reading CryoKit errorMessage in CryoTunes Player") to see the sever in action.

The Apple Music REST API as a backdoor

MusicKit's typed Swift API is generous, but it has gaps. The most common one: it does not expose a first-class call to mark a song as a favorite. There is no Song.markAsFavorite(), no MusicLibrary.shared.addToFavorites(song). Apple Music's "Favorite Songs" auto-playlist is auto-managed by the iOS app's star button, not by a typed Swift API.

What MusicKit does provide is MusicDataRequest — a wrapper that lets you make raw HTTP calls to the Apple Music REST API using the user's already-authorized session. CryoTunes uses this to wire its thumbs-up/thumbs-down buttons to Apple Music's love/dislike rating system. Open FavoriteManager.swift in the repo:

private func rate(songID: String, value: Int) async throws {
    guard let url = URL(string: "https://api.music.apple.com/v1/me/ratings/songs/\(songID)") else {
        return
    }
    var urlRequest = URLRequest(url: url)
    urlRequest.httpMethod = "PUT"
    urlRequest.setValue("application/json", forHTTPHeaderField: "Content-Type")
    let body: [String: Any] = [
        "type": "ratings",
        "attributes": ["value": value]
    ]
    urlRequest.httpBody = try JSONSerialization.data(withJSONObject: body)
    let request = MusicDataRequest(urlRequest: urlRequest)
    _ = try await request.response()
}

Two callable wrappers around it:

  • favorite(songID:) sends value: 1 — the "love" rating, which Apple Music auto-adds to the system Favorite Songs playlist
  • unfavorite(songID:) sends value: -1 — the "dislike" rating, which removes from Favorites and feeds the global "Suggest Less Like This" recommendation signal

The take-away: when MusicKit's typed surface is missing what you need, the REST API via MusicDataRequest is the supported escape hatch. Auth is handled for you; you write the URL and the request body.

iCloud Key-Value Store for preferences-tier sync

CryoTunes' DislikeManager tracks which songs the user has thumbs-down'd on each station, and syncs that across the user's devices via NSUbiquitousKeyValueStore — iCloud Key-Value Store. KVS is the lightweight cousin of CloudKit: a tiny dictionary (1MB total, 64KB per key, ~1024 keys) backed by iCloud, designed for preferences and small bits of state, not user content.

The real-world gotcha that bit this app: turning the entitlement on requires more than the plist key. The Key-Value Store capability has to be checked in Xcode's Signing & Capabilities pane — that's what triggers the entitlement to be added to the App Store-signed binary. A plist key without the capability checkbox compiles fine but doesn't sync once the binary's signed by Apple. The capability went on for v2.4.6 and KVS sync started working immediately.

The thumbs-up / thumbs-down design

CryoTunes' rating buttons fire two things on each tap, in parallel:

  • Thumbs-up — adds the song to a per-station playlist (e.g., "Jazz - CryoTunes") via MusicLibrary.shared.add(_:to:), AND sends value: 1 to the rating API to favorite the song globally in Apple Music
  • Thumbs-down — adds the song's ID to DislikeManager's per-station dislike set (auto-skip on this station next time, KVS-synced across devices), AND sends value: -1 to the rating API to dislike the song globally
  • Skip-back undo — if the user hits previous-track within the song window after a thumbs-down, the per-station dislike is removed and the song is re-favorited via the rating API

The two systems are complementary, not redundant. The per-station system gives guaranteed auto-skip behavior on that station with offline robustness; the Apple Music rating gives global recommendation tuning across all of Apple Music. Each thumbs-down both flags the song locally and informs the global engine. Browse Views/CryoTransportControls.swift on GitHub for the wiring.
