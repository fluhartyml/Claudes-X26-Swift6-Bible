Part-VII-Dedicated-Build-Alongs/BuildAlong-05-Claudes-Outdoor-Utility

  1. Build-Along 05: Claudes Outdoor Utility

  2. Status: planning & spec phase as of 2026-04-26. v1.0 will scaffold and ship as five Apple frameworks composed into a single useful diary app. v2.0 demonstrates an upgrade arc by adding a third-party radar tile provider on top.

  3. A weather-stamped photo journal. One tap captures a photo, the current weather, your location, a title, and a free-text note — one entry, frozen in time. Browse past entries chronologically or pinned on a map. Useful out of the gate; teaching the framework composition is what the book gets out of it.

  5. What this app is

  6. Apple Photos remembers GPS coordinates for every photo (when you allow it) but it does not remember the weather. Claudes Outdoor Utility fills that gap. Each journal entry stores a title, a timestamp, a location, the weather conditions at that location and moment, an optional photo, and a free-text note. The map shows every place the user has logged. The log shows every moment chronologically. The app is a lightweight diary built around Apple's audio-of-place — weather plus location plus a picture — and it is genuinely useful before any teaching layer is added.

  7. Primary identity is a useful App Store app. Teaching layer rides on top: design rationale callouts in every Swift file plus an Under the Hood tab that shows the app's own source code in-app. Same secondary-teaching pattern locked in Build-Along 04 (Claudes Audio Universe).

  8. What v1.0 teaches

  9. Five Apple frameworks composed into one product, no third-party dependencies:

    • CoreLocation — request when-in-use authorization, read the device's current coordinates, handle the authorization states cleanly
    • WeatherKit — fetch the current conditions for the user's coordinates at log time and freeze them into the entry
    • SwiftData — persist journal entries locally with a single @Model class, query them back with @Query, observe changes automatically through SwiftUI
    • PhotosUI & UIImagePickerController — let the user either pick an existing photo from the library (system privacy-preserving picker) or take a fresh one with the camera
    • MapKit — render a Home-tab map of every past entry as pins, render a per-entry detail map of one specific location

  11. Project setup — the GitHub checkbox matters

  12. Scaffold from Xcode → File → New → Project → iOS → App. Settings:

    • Product Name: Claudes Outdoor Utility
    • Organization Identifier: com.Claudes-X26-Swift-Bible
    • Interface: SwiftUI · Language: Swift · Storage: SwiftData
    • Save into ~/Developer.complex/ClaudesX26Swift6BibleApps/
  14. Caution — tick the Create Git Repository on my Mac checkbox at project creation time. Xcode places it on the same panel as the save location. If the box is unchecked, the project is created without an initialized git repo, and you have to retrofit it with git init + remote setup later — doable but a chore that desyncs Xcode's Source Control panel until you reload the project. Tick the checkbox once at creation and Xcode wires the repo, the first commit, the .gitignore, and the Source Control panel cleanly. Same lesson applies to every Xcode project on your roster: tick the box at create time.

  15. Naming and bundle identity

  16. Name discipline matters because the App Store rejects apps that read like demos or beta utilities (per Guideline 2.3.0 and the broader meaningful-app-experience requirement). Claudes Outdoor Utility names what the app does plainly and grants it a real product identity. Bundle ID: com.Claudes-X26-Swift-Bible.Claudes-Outdoor-Utility. GitHub repo: github.com/fluhartyml/Claudes-Outdoor-Utility.

  17. Architecture overview

  18. Three tabs: Home, New Entry, Log. Each one is wrapped in AppShell so the (i) info button + About sheet plumbing is shared across tabs (same pattern locked in Build-Along 04). The shell owns nothing beyond the (i)-button toolbar; each tab owns its own state, its own data flow, its own framework.

  19. One @Model drives the entire data layer. No central store object, no observable singleton, no service layer. SwiftData's modelContext environment value plus @Query property wrapper handle persistence and observation natively.

  20. Data model

  21. @Model final class OutsideLog {
    var id: UUID
    var timestamp: Date
    var title: String           // short user-supplied title
    var latitude: Double
    var longitude: Double
    var weatherSummary: String  // e.g. "72F, partly cloudy"
    var temperature: Double
    var condition: String       // SF Symbol name from Weather.symbolName
    var photoData: Data?        // raw bytes, untouched
    var note: String            // free text body
}

  22. The title is required at New Entry time so that every row in the Log tab is human-scannable months later. Empty-title entries become a bag of "Untitled" placeholders within weeks; requiring 2-5 words at log time costs almost nothing and pays off forever.

  23. Photo & location privacy — the rule

  24. Locked rule: never read or modify a photo's EXIF. The journal entry stores location in the @Model as latitude and longitude. The photo's bytes are stored exactly as the user gave them — no GPS injection into the in-app copy, no GPS stripping, no rewriting at all. The user's iOS Settings → Privacy → Location Services → Camera setting is the only authority on whether photos carry GPS EXIF in their pixels-plus-metadata blob. Many users keep camera location off so that texted photos do not leak their location; an app that "helpfully" injects EXIF GPS into its own internal copy defeats that decision the moment the user shares the entry. Treat photos as opaque media: accept, store, display, share — never modify.

  25. This is also a generalizable lesson worth carrying to any future app that mixes photos and location. The clean separation is: photo bytes are media, coordinates are journal metadata, and the two stay in their own lanes.

  26. Display rule — timestamp-led titles

  27. Every place an entry surfaces (Log row, detail navigation title, map-pin callout), the dominant text reads:

  28. YYYY MMM DD {title}

  29. For example, 2026 APR 26 Beach walk at sunset. Date-led-then-title is internally consistent with the apartment's screenshot folder naming convention and turns the Log into a chronologically scannable archive without sort-toggle complexity. Date is captured automatically; title is what the user types.

  30. Map placement rule — one-entry views, map last

  31. On per-entry views (New Entry sheet, Entry detail), the photo and the words lead. The map sits at the bottom of the layout as the geographic anchor, sized so it does not eat the visual real estate. On the Home tab, where the map IS the view's purpose (every entry pinned at once), the map fills the screen because that is its job. The principle: when a map represents one entry's data, it goes last; when it represents the whole archive at a glance, it leads.

  32. UI shape (sketch)

  33. Home tab

    • Map fills most of the tab, pinned with every past entry's location
    • "This Day" recall card at the top (optional v1.0 polish): if any entries match today's calendar day in past years, surface them
    • Tap a pin → push the matching Entry detail view

  35. New Entry tab (or sheet)

    • Title TextField at the top (placeholder "Title this entry", ~50 char practical limit)
    • "Add Photo" button → presents a confirmation dialog with two choices: Take Photo (camera) or Choose from Library (PhotosPicker)
    • Weather card auto-filled from WeatherKit (read-only, frozen at log time)
    • Note TextEditor for free-text body
    • Caption text showing the captured timestamp + coordinates
    • Live small Map (~150 pt) at the bottom showing where the entry will pin

  37. Log tab

    • Reverse-chronological list of entries
    • Each row: small cached map thumbnail (generated once via MKMapSnapshotter), date+title primary line, weather summary secondary line, photo thumbnail at the trailing edge
    • Tap row → push Entry detail view

  39. Entry detail view

    • Hero photo at the top
    • Weather card (the frozen snapshot from log time)
    • The note
    • Caption text with timestamp + coordinates
    • Map (~250 pt) at the bottom with the entry's pin centered
    • Toolbar: Edit, Delete, Share

  41. Locked design rules

    • iOS only. Project targets iphoneos iphonesimulator. macOS and visionOS skipped per the case-by-case platform rule (no pedagogical gain from cross-platform branching here)
    • SwiftData persists. Unlike Audio Universe (which was transient by design), Outdoor Utility's whole point is persistence. The diary survives restarts, reinstalls preserve through iOS Device Backup, and CloudKit-backed sync is a v2.x candidate
    • One framework per layer. Each Apple framework owns one slice of the app: CoreLocation owns coordinates, WeatherKit owns weather, SwiftData owns persistence, MapKit owns visual geography, PhotosUI/UIImagePickerController own image input. No leakage between layers
    • Photos untouched. Locked rule from above. The app never reads or writes EXIF
    • Title required. Forces the Log to stay browsable in the long term
    • Map last on per-entry views, first on archive views. Locked above

  43. Info.plist usage descriptions

    • NSLocationWhenInUseUsageDescription — CoreLocation reads your location when you log a new entry
    • NSCameraUsageDescription — only when you choose Take Photo
    • NSPhotoLibraryUsageDescription — not needed; PhotosPicker is privacy-preserving and does not require library permission

  45. App Services portal trip (one-time, before WeatherKit will work)

  46. WeatherKit fails at runtime with a JWT-authentication error until the App ID has WeatherKit enabled on developer.apple.com. CoreLocation, MapKit, PhotosUI, and SwiftData do not need portal enablement — they are part of the base SDK. Only WeatherKit triggers this trip in v1.0.

  47. Step by step:

    1. Sign in at developer.apple.com → Account → Certificates, Identifiers & Profiles → Identifiers
    2. Find the App ID for this project. If you let Xcode auto-register on first build, it appears with an XC prefix and the bundle ID matches what is in the project file. If it is not there, click + to register manually: select App IDs → App, paste the explicit bundle ID, fill the description
    3. Click into the App ID row to edit it
    4. Click the App Services tab at the top of the page (NOT the Capabilities tab — this is the trap; MusicKit, ShazamKit, WeatherKit live under App Services, not Capabilities)
    5. Tick WeatherKit
    6. Click Save at the top right
    7. Apple shows a "Modify App Capabilities" confirmation dialog warning that provisioning profiles tied to this App ID will be invalidated and must be regenerated. Confirm. With Xcode managed signing, regeneration is automatic on the next build — nothing for the developer to do
    8. Wait two to five minutes for Apple's signing infrastructure to propagate the entitlement
    9. Back in Xcode: Product → Clean Build Folder, then Run. The next WeatherKit fetch should succeed
  49. Caution — enable WeatherKit on the canonical App ID, not a stale auto-registered one. If the project was renamed at any point (a typo fix, a name change after first build), Xcode's first-build auto-registration may have created an App ID under the OLD bundle ID. Apple's portal does not delete that stale entry when the project is renamed; both entries exist side by side. WeatherKit must be enabled on the App ID whose bundle ID matches the project's current bundle ID — the one the next build will sign with. Enabling it on the stale entry does nothing for the running app. Optional cleanup: delete the stale entry from Identifiers afterwards to keep the list legible.

  50. WeatherKit attribution

  51. Apple requires visible attribution for WeatherKit data: the phrase "Weather data provided by  Weather" (using the Apple logo glyph at code point U+F8FF, which renders as the apple icon in any system font on Apple platforms) rendered alongside the data, linked to weatherkit.apple.com/legal-attribution.html. Apple's review team has rejected updates over missing or invisible WeatherKit attribution, even when prior versions were approved — treat this as load-bearing, not cosmetic.

  52. Two places carry the attribution in this app:

    1. The About sheet — reachable from the (i) info button on every tab. A small row below the outbound-link buttons, above the GPL footer, with the entire phrase as a single tap target
    2. The weather card itself — on the New Entry sheet and on the Entry detail view, the weather card carries the same attribution adjacent to the displayed conditions. The About-sheet attribution alone is not enough; reviewers want to see attribution on the same screen as the data

  54. Implementation pattern: wrap the whole phrase in a single Link so the entire row is one tap target. The apple glyph (U+F8FF) keeps the row tight without spelling out "Apple" as a separate word.

  55. Link(destination: URL(string:
    "https://weatherkit.apple.com/legal-attribution.html")!) {
    Text("Weather data provided by \u{F8FF} Weather")
        .font(.caption)
}

  56. The legal-attribution page is a static HTML page Apple maintains that lists every data source WeatherKit pulls from (Apple Weather, The Weather Channel, BreezoMeter, and several meteorological agencies). The page is the canonical destination required by Apple's WeatherKit terms.

  57. Caution — attribution belongs adjacent to displayed weather data, not always on screen. The About-sheet row covers the app-credits surface. The weather card needs attribution on its success branch, where Apple Weather data is actually rendered. Do NOT show the attribution in error states (no data to credit), loading states (no data yet), or idle/waiting states (still no data). Showing the attribution Link in an error state is actively harmful: extra interactive elements in the same row can hijack tap routing — a nearby Retry button can lose its tap to the Link. Code the card so the attribution row is conditionally rendered only in the success branch.
  58. @ViewBuilder
private var weatherCard: some View {
    if fetchingWeather {
        ProgressView("Fetching weather…")
        // No attribution — no data yet
    } else if let weather = weather {
        WeatherSummary(weather: weather)
        WeatherAttributionRow()    // Attribution adjacent to data
    } else if let weatherError = weatherError {
        Text(weatherError).foregroundStyle(.red)
        Button("Retry") { ... }
        // No attribution — no data displayed
    } else {
        Text("Waiting for location…")
        // No attribution — no data yet
    }
}

  59. A more future-proof alternative is to read WeatherService.shared.attribution at runtime and link to whatever legalPageURL it returns — that survives Apple changing the static URL, at the cost of a network read before the row can render.

    1. Xcode → New Project with the settings + the Create Git Repository checkbox ticked

    8. Wire features one at a time: location auth → weather fetch → SwiftData entry creation → photo input (camera + library) → map rendering on Home tab → entry detail view
    9. UnderTheHoodView.swift — same source-tour pattern as Audio Universe (callout per file + embedded source + Open on GitHub)

  62. v2.0 roadmap — the upgrade demonstration

  63. v2.0 layers RainViewer's free-tier radar tiles on top of the v1.0 MapKit basemap, turning the Home tab into a "this is what's happening weather-wise where I have logged" view in real time. The upgrade is architecturally meaningful: it adds the app's first third-party API integration, its first MKTileOverlay subclass, its first UIKit-into-SwiftUI bridge (because the SwiftUI Map view does not yet expose tile overlays), and a second visible attribution layer.

  64. What v2.0 adds and teaches:

    • Third-party JSON API integration — URLSession, Codable decoding of the RainViewer manifest at https://api.rainviewer.com/public/weather-maps.json
    • MKTileOverlay subclass — constructing tile URLs from the manifest, refreshing every ~10 minutes
    • UIViewRepresentable bridging — wrapping MKMapView in a SwiftUI-facing struct so MapKit's overlay APIs are reachable
    • Attribution discipline — "Powered by RainViewer" footer band on the Home tab per their free-tier ToS, plus the existing WeatherKit attribution. Two visible credits on the same screen, each with its own rules
    • The App Store update review cycle as its own teaching point — how a previously approved app moves through review when a substantial new feature lands, what reviewers look for in update submissions, attribution growth
