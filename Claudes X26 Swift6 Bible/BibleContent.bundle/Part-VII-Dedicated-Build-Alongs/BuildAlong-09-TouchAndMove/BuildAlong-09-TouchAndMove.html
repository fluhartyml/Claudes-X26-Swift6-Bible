VII.9  Build-Along 09: TouchAndMove — Every Gesture, One Shape

Distribution: GitHub clone-and-build. TouchAndMove is a SwiftUI gesture playground. One rounded-rectangle shape sits on a dark gradient background; the user can drag it around, pinch to scale, twist to rotate, tap to bounce, and long-press to recolor it. A live readout at the bottom of the screen shows the current offset, scale, angle, and tap count in real time. The teaching point is gesture composition — running drag, magnify, and rotate at the same time without them fighting each other — and the two-state-lane pattern that gives the shape its spring-back release feel.

The repository: github.com/fluhartyml/TouchAndMove. Built on DragGesture, MagnifyGesture, RotateGesture, SimultaneousGesture, onTapGesture, onLongPressGesture, and the .spring(response:dampingFraction:) animation curve. iPhone, iPad, and Mac universal target.

This chapter is the gesture companion to Build-Along 08: IntelligenceDemo. Both apps are single-feature concept demos — no persistence, no surrounding product. The pair show the two ends of the SwiftUI input spectrum: machine perception (Vision reading photos) on one side, direct manipulation (gestures driving animation) on the other.

VII.9.1  The Brainstorm

VII.9.1 ¶1 SwiftUI ships seven gesture primitives: TapGesture, LongPressGesture, DragGesture, MagnifyGesture, RotateGesture, SpatialTapGesture, and the empty-base Gesture protocol that user code can extend. Most apps reach for one or two of these and stop; the gestures most readers have written by hand are tap and drag, and the rest tend to live in framework documentation as "things SwiftUI offers" rather than "things I have ever shipped." The point of TouchAndMove is to fix that — one screen, every primary gesture, every gesture wired up to a visible effect, every effect animated.

VII.9.1 ¶2 The shape is a single rounded rectangle on purpose. With one shape there is no question about which shape responded; with one set of state variables there is no question about where the truth lives. The whole app is in one file with a small handful of subviews and gesture definitions, and the playground is meant to be cloned and modified — readers tweak the spring values, swap the shape, add a new gesture, see what changes.

VII.9.1 ¶3 v1.0 spec:

VII.9.1 ¶4
  • One rounded-rectangle shape, 180×180 points, blue by default
  • Drag the shape with one finger; release with a spring-back to where the user let go
  • Pinch with two fingers to scale (clamped between 0.4× and 4×); release with a spring-settle
  • Twist with two fingers to rotate; release with a spring-settle
  • Drag, pinch, and rotate run simultaneously — the user can pinch while dragging while twisting
  • Tap once for a bounce animation; tap count visible in the corner of the shape
  • Long-press to toggle the shape's color from blue to orange and back
  • Live readout strip at the bottom showing offset, scale, angle, taps
  • Reset button in the toolbar that returns everything to defaults with one spring animation
  • Under the Hood sheet (developer notes inside the app)
  • About sheet (icon, attribution, links)
  • Universal target: iPhone, iPad, Mac — same code, same UI

VII.9.1 ¶5 What is intentionally not in v1.0:

VII.9.1 ¶6
  • No persistence — every launch starts at the default position, scale, and rotation; the playground has no opinion about "where you left off"
  • No second shape — collision, snapping, and z-order are out of scope
  • No haptics — the visible feedback is enough for the lesson; haptics are a follow-on chapter's territory
  • No App Store submission — gesture playgrounds read as "limited functionality" under App Review Guideline 2.2, which is a fair reading

VII.9.3  The Two-State-Lane Pattern

VII.9.3 ¶1 This is the pattern that makes the shape feel right under the finger. SwiftUI's gesture API gives the developer a choice for how to track gesture state, and the choice the app makes determines whether the release feels alive or dead.

VII.9.3 ¶2
@State private var offset: CGSize = .zero
@State private var dragOffset: CGSize = .zero
@State private var scale: CGFloat = 1.0
@State private var pinchScale: CGFloat = 1.0
@State private var rotation: Angle = .zero
@State private var pinchRotation: Angle = .zero

VII.9.3 ¶3 Each of the three continuous gestures has two state variables: a committed value (offset, scale, rotation) and a live in-flight value (dragOffset, pinchScale, pinchRotation). While the gesture is active, the view reads the sum of both. On gesture end, the live value collapses into the committed one inside withAnimation, which gives the spring-back release the user feels at the end of every drag, pinch, or twist.

VII.9.3 ¶4
shape
    .offset(x: offset.width + dragOffset.width,
            y: offset.height + dragOffset.height)
    .scaleEffect(scale * pinchScale)
    .rotationEffect(rotation + pinchRotation)
    .gesture(combinedGesture)

VII.9.3 ¶5 While the user's finger is on the screen, dragOffset grows or shrinks; offset stays at its previous value. The visible position is the sum. When the finger lifts, the gesture's onEnded closure fires, and inside withAnimation two things happen at once: offset jumps to offset + value.translation, and dragOffset resets to zero. The visible position does not change at the moment of release — both updates are applied to the same view in the same tick — but the animation curve interpolates the spring trajectory because the change is wrapped in withAnimation.

VII.9.3 ¶6 The same pattern applies to scale and rotation. Pinch grows pinchScale while the fingers move; on release, scale multiplies in (clamped between 0.4 and 4.0) and pinchScale resets to 1.0. Rotation accumulates pinchRotation while the fingers twist; on release, rotation adds it in and pinchRotation resets to .zero.

VII.9.3 ¶7 If the app used a single state variable per gesture instead of two, the release would still work mechanically — the value would just stop changing — but the spring animation would have nothing to animate, because the value at release is exactly the value at rest. The two-lane structure separates the live, instantaneous value from the committed, animated value, and gives the spring something to interpolate.

VII.9.4  Composing Gestures with SimultaneousGesture

VII.9.4 ¶1 The drag, magnify, and rotate gestures are merged so all three run at once.

VII.9.4 ¶2
private var combinedGesture: some Gesture {
    let drag = DragGesture()
        .onChanged { dragOffset = $0.translation }
        .onEnded { value in
            withAnimation(.spring(response: 0.45, dampingFraction: 0.7)) {
                offset.width += value.translation.width
                offset.height += value.translation.height
                dragOffset = .zero
            }
        }

    let magnify = MagnifyGesture()
        .onChanged { pinchScale = $0.magnification }
        .onEnded { value in
            withAnimation(.spring(response: 0.5, dampingFraction: 0.75)) {
                scale = max(0.4, min(scale * value.magnification, 4.0))
                pinchScale = 1.0
            }
        }

    let rotate = RotateGesture()
        .onChanged { pinchRotation = $0.rotation }
        .onEnded { value in
            withAnimation(.spring(response: 0.5, dampingFraction: 0.75)) {
                rotation += value.rotation
                pinchRotation = .zero
            }
        }

    return SimultaneousGesture(drag, SimultaneousGesture(magnify, rotate))
}

VII.9.4 ¶3 SwiftUI offers three gesture-composition operators: SimultaneousGesture, SequenceGesture, and ExclusiveGesture. The names describe the semantics. SimultaneousGesture runs both gestures at the same time, and either one can update its state independently. SequenceGesture requires the first gesture to recognize before the second can begin. ExclusiveGesture runs both, but as soon as one recognizes, the other is canceled.

VII.9.4 ¶4 The right operator for a multi-touch playground is SimultaneousGesture, because the user can be dragging, pinching, and rotating all at once and SwiftUI has to track all three. Wrapping SimultaneousGesture twice (once over magnify+rotate, then over drag+the-pair) composes the three primitives without nesting issues. The result is a single some Gesture that the view attaches via .gesture(_:).

VII.9.4 ¶5 Tap and long-press hang off their own modifiers (.onTapGesture and .onLongPressGesture) instead of going into the same composition. The reason is that they are discrete, not continuous — they fire once when recognized, not continuously while a finger is down. Mixing discrete gestures into a SimultaneousGesture with continuous ones invites recognition order bugs, and the modifier form is shorter and more direct anyway.

VII.9.5  Spring Physics, Not Linear Curves

VII.9.5 ¶1 Every release in TouchAndMove uses .spring(response:dampingFraction:) rather than .linear or .easeInOut. The choice is deliberate.

VII.9.5 ¶2 A linear animation interpolates the value at a constant rate. The motion looks mechanical — constant velocity, sharp arrival. An ease-in-out animation slows down at both ends. The motion looks polite but lifeless. A spring animation models the motion as a damped harmonic oscillator: the value accelerates toward the target, overshoots a little, oscillates back, and settles. The motion looks alive.

VII.9.5 ¶3 response is the time the spring takes to settle, in seconds. Lower values are snappier; higher values are slower. dampingFraction is the ratio of damping to the spring's natural frequency; 1.0 is critically damped (no overshoot), values below 1.0 overshoot and oscillate, values above 1.0 are over-damped and feel sluggish.

VII.9.5 ¶4 The values in the source code are tuned for a quick, playful response:

VII.9.5 ¶5
  • Drag release: response: 0.45, dampingFraction: 0.7 — quick, slight overshoot
  • Magnify release: response: 0.5, dampingFraction: 0.75 — a hair slower, a hair more damped
  • Rotate release: response: 0.5, dampingFraction: 0.75 — same as magnify
  • Tap bounce up: response: 0.25, dampingFraction: 0.5 — very fast, very bouncy
  • Tap bounce return: response: 0.45, dampingFraction: 0.6 — slightly bouncier on the way back
  • Long-press color change: .easeInOut(duration: 0.25) — not a spring, because color does not bounce
  • Reset: response: 0.55, dampingFraction: 0.7 — slow enough to read, snappy enough to feel decisive

VII.9.5 ¶6 Readers tweaking these values is part of the lesson. Drop the damping fraction to 0.4 on the drag release and the shape oscillates visibly before settling; raise it to 1.0 and the spring becomes critically damped, with no overshoot at all. The fastest way to develop a feel for spring physics is to change the numbers and watch.

VII.9.6  The Tap Animation

VII.9.6 ¶1 Tap is the only gesture that animates without a release boundary, because tap has no "during" state — it fires once and is done. The animation is two consecutive springs:

VII.9.6 ¶2
private func handleTap() {
    tapCount += 1
    withAnimation(.spring(response: 0.25, dampingFraction: 0.5)) {
        scale *= 1.15
    }
    withAnimation(.spring(response: 0.45, dampingFraction: 0.6).delay(0.15)) {
        scale /= 1.15
    }
}

VII.9.6 ¶3 The first withAnimation bumps the scale up by 15%. The second withAnimation — with a 0.15-second delay so it does not fight the first — brings the scale back to where it was. The bounce is a brief overshoot-and-return that feels tactile without disturbing the shape's resting state. Each tap also increments tapCount, which the readout strip reads to show the running count.

VII.9.6 ¶4 Why the asymmetric spring values. The bounce up is fast and loose (response 0.25, damping 0.5) so it feels reactive. The return is slower and slightly more damped (response 0.45, damping 0.6) so it lands gently. If both halves used the same spring, the bounce would feel more mechanical — the asymmetry is what gives it personality.

VII.9.7  The Long-Press Color Toggle

VII.9.7 ¶1
.onLongPressGesture(minimumDuration: 0.4) { handleLongPress() }

private func handleLongPress() {
    withAnimation(.easeInOut(duration: 0.25)) {
        isLongPressed.toggle()
    }
}

VII.9.7 ¶2 The shape's fill is bound to isLongPressed:

VII.9.7 ¶3
RoundedRectangle(cornerRadius: 28, style: .continuous)
    .fill(isLongPressed ? Color.orange : Color.blue)
    .frame(width: 180, height: 180)

VII.9.7 ¶4 Long-press flips the boolean; the color crossfades to orange. Long-press again, the boolean flips back, the color crossfades to blue. The animation is .easeInOut, not a spring, because color is not a position — there is nothing to bounce. .easeInOut is the right curve for value changes that have no physical analog.

VII.9.7 ¶5 The 0.4-second minimum duration is shorter than iOS's default long-press (0.5) but long enough to distinguish from a tap. Tweaking it to 0.6 or 0.8 makes the gesture feel more deliberate; tweaking it to 0.2 makes it overlap with tap and conflict.

VII.9.8  The Live Readout

VII.9.8 ¶1 Below the shape, a translucent strip shows the current state of the gesture variables in real time:

VII.9.8 ¶2
private var readout: some View {
    VStack(spacing: 4) {
        Text("Drag · Pinch · Rotate · Tap · Long-press")
            .font(.caption)
            .foregroundStyle(.secondary)
        HStack(spacing: 16) {
            stat("Offset", "\(Int(offset.width)), \(Int(offset.height))")
            stat("Scale", String(format: "%.2f", scale))
            stat("Angle", String(format: "%.0f°", rotation.degrees))
            stat("Taps", "\(tapCount)")
        }
        .font(.caption.monospacedDigit())
    }
    .padding(.vertical, 10)
    .frame(maxWidth: .infinity)
    .background(.ultraThinMaterial)
}

VII.9.8 ¶3 The readout reads the committed values (offset, scale, rotation, tapCount), not the live in-flight ones. While the user is dragging, the offset shown is the previous resting offset; only when the gesture ends and the values commit does the readout update. This is the right call for a teaching playground — the readout shows where the shape is at rest, which is the value the user is conceptually controlling, not the moment-to-moment in-flight delta. Showing the live sum would technically be more accurate but harder to read because the numbers would never stop moving.

VII.9.8 ¶4 The strip uses .ultraThinMaterial as its background, which gives it the frosted-glass look that iOS uses on the Control Center, the lock screen, and most modal sheets. Materials are SwiftUI's way of saying "I want this to look like a system surface" without specifying the exact color — the actual rendering depends on what is behind it and on the system's appearance setting.

VII.9.8 ¶5 The readout attaches to the main ZStack via .safeAreaInset(edge: .bottom), which adds it inside the safe area without blocking touches on the rest of the screen. Safe-area insets are how SwiftUI adds persistent chrome to a view without taking it out of the layout flow.

VII.9.9  The Reset Action

VII.9.9 ¶1
private func reset() {
    withAnimation(.spring(response: 0.55, dampingFraction: 0.7)) {
        offset = .zero
        dragOffset = .zero
        scale = 1.0
        pinchScale = 1.0
        rotation = .zero
        pinchRotation = .zero
        isLongPressed = false
        tapCount = 0
    }
}

VII.9.9 ¶2 One withAnimation wraps every reset, so the shape springs back to its starting position, scale, rotation, color, and tap count all in one motion. The animation is a single spring, slightly slower than the gesture-release springs because the shape may have to travel further; the longer response time keeps the motion legible.

VII.9.9 ¶3 Resetting all eight state variables in one block is a small detail with real value — if any one were left out, the next interaction would carry that piece of leftover state into a fresh start, and the user would feel it. The exhaustive reset makes the playground reliably restartable, which is what readers need when they are tweaking spring values and want to see each new tuning from a clean slate.

VII.9.11  Universal Target: iPhone, iPad, Mac

VII.9.11 ¶1 TouchAndMove ships as a universal target. The same code runs on iPhone, iPad, and Mac — the only place the source diverges is one #if os(iOS) guard around .navigationBarTitleDisplayMode(.inline), because that modifier is iOS-only and would not compile on macOS:

VII.9.11 ¶2
.navigationTitle("Touch & Move")
#if os(iOS)
.navigationBarTitleDisplayMode(.inline)
#endif

VII.9.11 ¶3 On Mac, the gestures translate naturally: drag becomes a click-and-drag, magnify becomes pinch on a trackpad, rotate becomes the trackpad's two-finger rotate gesture. Tap becomes a click. Long-press becomes a click-and-hold. SwiftUI handles the mapping; the code does not change.

VII.9.11 ¶4 This is one of the lessons that compounds in unexpected places: gestures are inputs, not platforms. A gesture-based app written in SwiftUI on iOS will work on a Mac trackpad without a code change as long as the gestures themselves remain meaningful. Pinch-to-scale is meaningful on Mac; drag-to-move is meaningful on Mac; rotate-with-two-fingers is meaningful on Mac. Hover, on the other hand, has no iPhone analog — a Mac-only gesture would not compose into a universal app cleanly.
