Source Tour 24: NightGard DDNS (Self-Publishing Case Study)

Status: self-distributed, notarized. Mac utility. Pairs with NightGard Commander as the book's two-sided case study on self-publishing — Commander chose self-publishing over the App Store sandbox; DDNS had no choice because daemons can't be App Store distributed at all.

A tiny background service that keeps a Dynamic DNS record updated with the user's changing home IP. No windowed UI when running — just a launchd-managed binary and a small SettingsView the user opens to configure credentials. Source: github.com/fluhartyml/NightGardDDNS. See Book 21 Git-And-GitHub for the clone workflow.

What NightGard DDNS shows at production scale

  • The launchd / LaunchAgent integration pattern — the app installs a .plist in ~/Library/LaunchAgents/ that tells launchd when to start the service, what to run, and how often. The user never sees a Dock icon for the running daemon.
  • A persistent network client — the service polls the user's current public IP at a configurable interval and writes the result into the Dynamic DNS provider's API when it changes.
  • Keychain storage for service credentials — the API token for the DNS provider lives in the macOS Keychain, accessed via SecItemAdd / SecItemCopyMatching. Users never see the token after they enter it once; the service reads it from Keychain on every cycle.
  • The smallest viable Mac app shape — six Swift files, ~500 lines total, demonstrates that a useful production app does not have to be large.

Why App Store distribution was never an option

The Mac App Store has no app category for daemons. Apple's submission flow expects an app with a Dock icon, a main window, a menu bar, and an entry point the user invokes. A LaunchAgent has none of those things by design — it's a binary that launchd starts at boot or login, runs in the background, and the user never directly interacts with the running process.

Trying to fit DDNS into the App Store would mean changing it into something it isn't: adding a windowed UI that runs persistently in the dock, accepting the App Sandbox limits on network egress, working around the sandboxed Keychain access rules. The result would be slower, weaker, more visible, and worse for the user.

The book's lesson here is the inverse of the usual "ship to the App Store as your default": some apps' shapes are fundamentally incompatible with App Store distribution, and forcing the fit produces a degraded version. Recognize the shape early. Self-publishing isn't a fallback for these apps; it's the only honest path.

The two services in the binary

The whole architecture is in two files:

  • NightGardDDNSApp.swift — the SwiftUI app entry point. When the user launches the app from Finder, it shows the configuration window. When launchd starts it as a daemon, it runs the polling loop without a window.
  • DDNSService.swift — the core service: read Keychain credentials, fetch current public IP from a known echo endpoint, compare to last-known, post to the DNS provider's API if different, log the result, sleep until next interval.

Plus SettingsView.swift for the user-facing configuration UI (provider, hostname, API token, polling interval) and NightGardDDNS_DeveloperNotes.swift for the in-app documentation surface. Six files total, including assets and entitlements.

The launchd plist

Outside the app target, in the repo's installation script, is the launchd .plist that registers the service:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "...">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.fluhartyml.NightGardDDNS</string>
    <key>ProgramArguments</key>
    <array>
        <string>/Applications/NightGardDDNS.app/Contents/MacOS/NightGardDDNS</string>
        <string>--daemon</string>
    </array>
    <key>StartInterval</key>
    <integer>300</integer>
    <key>RunAtLoad</key>
    <true/>
</dict>
</plist>

This .plist goes in ~/Library/LaunchAgents/. launchd picks it up at next login (or via launchctl load) and starts the binary with the --daemon flag every 5 minutes. The app reads --daemon at launch and skips creating the configuration window.
