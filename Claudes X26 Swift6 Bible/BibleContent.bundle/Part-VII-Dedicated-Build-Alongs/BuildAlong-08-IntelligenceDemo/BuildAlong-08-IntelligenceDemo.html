Build-Along 08: IntelligenceDemo — Photo to Text in Two Files

Distribution: GitHub clone-and-build. IntelligenceDemo is the smallest possible app that puts the Vision framework's text recognition in front of a user. Pick a photo of a page, a sign, a receipt, or a handwritten note; the app reads the text on it and shows it back. Two Swift files, one screen, no persistence, no settings. The teaching point is the Vision API, isolated.

The repository: github.com/fluhartyml/IntelligenceDemo. Built on PhotosPicker (PhotosUI) for input, VNRecognizeTextRequest (Vision) for recognition, and async/await to keep the recognition off the main thread. iPhone and iPad universal target.

This chapter teaches OCR at demo scope — one feature, single screen, no surrounding product. Snap & ScanKeeper, on the App Store under Michael's developer account, is the production evolution of the same Vision API into a full document-scanning utility. The build-along teaches the primitive; Source Tour 20: Snap & ScanKeeper is the case study for what the same API looks like with persistence, document edges, and a shipping product wrapped around it.

The Brainstorm

The Vision framework has shipped on iOS since version 11 (2017), but the API has had a reputation for being intimidating. Most introductions reach for face detection, barcode reading, or saliency analysis — topics that need pages of explanation about request handlers, image orientation, and observation types before the reader sees a single character of recognized text. The reputation is unearned. Vision's text-recognition path is short, and once a reader has seen it work, the rest of Vision generalizes easily.

IntelligenceDemo strips the lesson down to its load-bearing parts: a photo source, a Vision request, an async wrapper, four UI states. No camera, no live capture, no document detection. The user picks an existing photo from the library; the app reads any text it finds.

v1.0 spec:

  • One screen, scrollable
  • PhotosPicker button at the top — "Pick a photo" / "Pick another photo"
  • Selected image rendered inline below the picker
  • Recognized text rendered below the image, selectable so the user can copy
  • Four UI states: empty (no photo picked), processing (spinner + "Reading text…"), found-text (results), no-text-found (graceful fallback)
  • Off-main-thread recognition via async/await
  • iPhone and iPad universal — same code, same UI

What is intentionally not in v1.0:

  • No camera capture — the user picks an existing photo, not takes a new one
  • No document edge detection — the recognizer reads whatever is in the frame, no perspective correction, no cropping
  • No saving recognized text — no SwiftData, no Files export, no share sheet; .textSelection(.enabled) lets the user copy what they want
  • No language picker — the recognizer uses its default English list
  • No handwriting-vs-print toggle — the recognizer figures it out

The Architecture

Two Swift files. Nothing else.

IntelligenceDemoApp.swift   # @main · one WindowGroup · ContentView()
ContentView.swift           # PhotosPicker + Vision + four UI states

The app entry is the SwiftUI default, unchanged from the Xcode template:

@main
struct IntelligenceDemoApp: App {
    var body: some Scene {
        WindowGroup {
            ContentView()
        }
    }
}

Everything else is in ContentView.swift. The whole file is 113 lines including imports, comments, and the SwiftUI Preview. That fits in one paragraph of mental model: pick a photo, run Vision on it, show the text.

The Four State Variables

@State private var pickedItem: PhotosPickerItem?
@State private var pickedImage: UIImage?
@State private var extractedText: String = ""
@State private var isProcessing: Bool = false

Each one corresponds to a stage of the pipeline.

pickedItem is what the picker writes to. A PhotosPickerItem is a lazy reference to a photo in the library — it is not the bytes themselves. The actual image data is fetched separately, asynchronously.

pickedImage holds the decoded UIImage once the bytes have been loaded. The view binds to this to render the photo.

extractedText holds the recognized text once Vision has finished. The view binds to this to show the result, with .textSelection(.enabled) so the user can copy it.

isProcessing gates the spinner state. It flips true the moment a new photo arrives and flips back to false after Vision returns.

PhotosPicker, Briefly

Build-Along 11: ReportMaker covers PhotosPicker at length in the receipt-attach context. The same API works the same way here:

PhotosPicker(
    selection: $pickedItem,
    matching: .images,
    photoLibrary: .shared()
) {
    Label(
        pickedImage == nil ? "Pick a photo" : "Pick another photo",
        systemImage: "photo.on.rectangle.angled"
    )
    .frame(maxWidth: .infinity)
    .padding()
    .background(Color.accentColor.opacity(0.15))
    .clipShape(RoundedRectangle(cornerRadius: 12))
}

The label changes copy ("Pick a photo" before any selection, "Pick another photo" once one exists) so the button stays useful after the first pick. The picker writes to pickedItem; onChange fires when that binding writes a non-nil value, kicking off the load:

.onChange(of: pickedItem) { _, newItem in
    Task { await load(item: newItem) }
}

The Task { ... } wraps the async call so SwiftUI's main-thread onChange closure can launch async work without becoming async itself.

Loading the Image Bytes

private func load(item: PhotosPickerItem?) async {
    guard let item else { return }
    extractedText = ""
    isProcessing = true
    defer { isProcessing = false }

    guard
        let data = try? await item.loadTransferable(type: Data.self),
        let image = UIImage(data: data)
    else { return }

    pickedImage = image
    extractedText = await recognizeText(in: image)
}

Three things happen here in order.

Reset and gate the UI. Clear any previous text, flip the spinner on, and set up a defer to flip the spinner off no matter how the function exits. The defer guarantees the UI state stays consistent even if the load fails.

Fetch the bytes. loadTransferable(type: Data.self) asks the picker item for its underlying bytes. The call is asynchronous because the photo may live in iCloud Photo Library and need to be downloaded first. try? swallows any error into nil; if either the data fetch or the UIImage construction fails, the function returns early with the spinner already on its way off.

Recognize. Once the image is in hand, hand it to recognizeText(in:) and store the result. The await here keeps the call off the main thread until Vision finishes.

The Vision Request

This is the chapter's centerpiece — the seven-line function that turns an image into text:

private func recognizeText(in image: UIImage) async -> String {
    guard let cgImage = image.cgImage else { return "" }

    let request = VNRecognizeTextRequest()
    request.recognitionLevel = .accurate
    request.usesLanguageCorrection = true

    let handler = VNImageRequestHandler(cgImage: cgImage, options: [:])

    do {
        try handler.perform([request])
        let observations = request.results ?? []
        return observations
            .compactMap { $0.topCandidates(1).first?.string }
            .joined(separator: "\n")
    } catch {
        return "Recognition failed: \(error.localizedDescription)"
    }
}

Walk it line by line.

image.cgImage. Vision works on Core Graphics images, not UIImage. The conversion is a property access; cgImage is non-nil for photos that came from the photo library, so the guard is mostly defensive.

VNRecognizeTextRequest(). The recognizer is a VNRequest subclass that knows how to find text. Constructing it does no work; the request is a configuration object, not a running operation.

recognitionLevel = .accurate. Vision offers two recognition levels: .fast and .accurate. Fast is for live-capture scenarios where the user is panning a camera and wants real-time hints; accurate is for the user-picks-a-photo case where they want the answer right and are willing to wait a fraction of a second longer. IntelligenceDemo is the second scenario.

usesLanguageCorrection = true. The recognizer can apply a language model on top of the raw character predictions to fix likely typos — "rece1pt" becomes "receipt," "haw" between two unambiguous words is more likely "have." Turning the correction on is almost always the right call for natural-language text. For non-language tokens (license plates, serial numbers, code), turning it off is the right call. The default is on; the explicit assignment is for documentation.

VNImageRequestHandler(cgImage: cgImage, options: [:]). The handler is the bridge between the request and the actual image. The options dictionary takes orientation hints if the image's metadata requires them; for photo-library images that have already been rotated to match their EXIF orientation, the empty dictionary is correct.

try handler.perform([request]). The synchronous call that does the actual recognition. perform([_:]) takes an array because a handler can run multiple Vision requests on the same image in one pass — text recognition plus face detection plus barcode reading, for example. IntelligenceDemo passes a single-request array because it only needs the one. The synchronous call is run inside an async function; the await at the call site keeps it from blocking the main thread.

request.results. After perform returns, the request's results property holds an array of VNRecognizedTextObservation. Each observation corresponds to a region of detected text — typically one line, sometimes a paragraph. The ?? [] handles the documented case where results can be nil if the request was never run successfully.

$0.topCandidates(1).first?.string. Each observation can have multiple candidate readings, ranked by confidence. topCandidates(1) asks for the single best candidate as an array (Vision's API is generous with candidates because some applications want to show the user "did you mean…?" alternatives). .first?.string pulls the top candidate's recognized text. compactMap drops any observation that somehow had zero candidates, which should never happen but the unwrap is free.

.joined(separator: "\n"). Each observation is one line of text in the source image; joining with newlines reconstructs the rough layout. Vision does not preserve column structure, indentation, or font information; the output is a flat plain-text approximation of the visible characters. For a receipt, that means each line of the receipt becomes one line of output; for a paragraph of prose, the line breaks reflect where the original text wrapped on the page, not where sentences end.

The catch branch returns a human-readable error string instead of throwing. Because the function returns String (not Result<String, Error>), surfacing the error as text keeps the call site simple at the cost of conflating "no text found" (empty string) with "recognition failed" (error string). For a teaching demo, this trade is acceptable; production code would distinguish.

The Four UI States

The body's content branches on the state variables in a single chain:

if isProcessing {
    HStack {
        ProgressView()
        Text("Reading text…")
            .foregroundStyle(.secondary)
    }
    .frame(maxWidth: .infinity)
} else if !extractedText.isEmpty {
    VStack(alignment: .leading, spacing: 8) {
        Text("Extracted Text")
            .font(.headline)
        Text(extractedText)
            .textSelection(.enabled)
    }
} else if pickedImage != nil {
    Text("No text found in this photo.")
        .foregroundStyle(.secondary)
} else {
    Text("Pick a photo of a page, sign, receipt, or note. The app will read the text on it.")
        .foregroundStyle(.secondary)
}

The chain reads top-down by priority:

  1. Processing wins over everything — if Vision is currently running, show the spinner.
  2. Has text shows the result, selectable.
  3. Has image but no text falls back to the "no text found" message. This branch fires when Vision returned zero observations — a photo of a blank wall, a sky, a person without any text in the frame.
  4. Initial — no image picked yet — shows the prompt explaining what the user can do.

The order matters. Putting extractedText.isEmpty ahead of isProcessing would cause the spinner to never appear on a second pick, because the previous text is reset to "" at the start of load(item:) — the empty-text branch would fire first and the user would see "No text found" briefly before recognition completed. Resetting extractedText before flipping isProcessing is intentional, and the chain order matches.

What's Not Here

Two practices that show up in production OCR apps are deliberately absent from IntelligenceDemo, and naming them is part of the lesson.

No request-recognition-language list. VNRecognizeTextRequest exposes a recognitionLanguages: [String] property where the developer can specify ISO language codes ("en-US", "es-ES", "ja") to bias the recognizer. IntelligenceDemo leaves the property at its default (English). For a multilingual app, the right move is to expose a language picker and bias the recognizer at request time. Adding it is one property assignment.

No custom words list. customWords: [String] lets the app push domain-specific vocabulary (proper nouns, product names, technical terms) into the language model so the recognizer prefers them when the raw character predictions are ambiguous. The receipt-scanner version of this app would add company names, store names, and currency symbols to customWords so "ammazom" gets corrected to "Amazon." IntelligenceDemo does not, because the demo runs on whatever photo the user picks and there is no domain to specialize for.

Snap & ScanKeeper: the Production Evolution

Snap & ScanKeeper is the live App Store evolution of the same Vision API. The build-along teaches the primitive; ScanKeeper is what the same primitive looks like when wrapped in a shipping product. The differences are worth naming because they map onto every "demo to product" gap.

  • ScanKeeper uses VNDocumentCameraViewController — the iOS-bundled document scanner — instead of PhotosPicker. The user holds the camera over the page; the scanner detects the page edges, applies perspective correction, and returns a clean image of just the document.
  • ScanKeeper persists the scanned documents via SwiftData, so each scan is saved, searchable, and re-shareable.
  • ScanKeeper exposes the recognized text as a searchable field, so a user can find "the Costco receipt from March" by typing a word that appeared on it.
  • ScanKeeper handles the full App Store privacy pass: NSCameraUsageDescription in Info.plist, a clear in-app rationale, no telemetry, and an App Privacy disclosure for "Photos" with no tracking.
