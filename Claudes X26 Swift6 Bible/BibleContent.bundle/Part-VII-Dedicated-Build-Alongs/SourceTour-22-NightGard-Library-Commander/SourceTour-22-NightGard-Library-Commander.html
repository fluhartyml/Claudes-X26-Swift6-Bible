Source Tour 22: NightGard Library Commander

Status: NOT YET LIVE — must reach the Mac App Store before book official release. Mac app. App-Store-compliant (sandboxed). Companion to CryoTunes Player.

Two paths to follow: clone the repo and read the source, or wait for the Mac App Store ship and install the live app. The architecture is split into two well-named services (LibraryService, PlaylistLockerService) and four pane views — small enough to read end-to-end. See Book 21 Git-And-GitHub for the clone workflow.

What Library Commander shows at production scale

  • Apple Music library metadata cleanup at scale — fills missing artist, album, genre, and artwork on tracks the user already has in their library. Operates on hundreds or thousands of tracks per session.
  • The sandbox-with-temporary-exception-apple-events entitlement pattern — how a Mac App Store app can ask Apple Music for library data via AppleScript while staying inside the sandbox boundary Apple requires for store distribution.
  • Security-scoped bookmarks — persisting access to user-picked working folders across app launches, the only sandboxed way to keep a folder reference alive without re-prompting the user every time.
  • The ported-not-rewritten Shazam stack — Library Commander pulls in the production-hardened Shazam stack that originated in NightGard Commander (see Source Tour 23). Re-implementing Shazam workflows from scratch is a bait Apple's rate limits set; porting the tuned stack from a sibling app is the correct discipline.
  • The CryoTunes Player ecosystem pairing — Library Commander cleans the library on Mac; CryoTunes plays from that cleaner library on iPhone. Both share the same iCloud Music Library. Readers see how production Mac + iOS apps compose into a two-device ecosystem.

The sandbox-with-temporary-exception pattern

Apple Music's library data is most accessible via AppleScript (the modern MusicKit.MusicLibrary Swift API is read-only for many properties Library Commander needs to write). On a Mac App Store sandboxed binary, AppleScript-to-Music is normally blocked — the sandbox doesn't let one app drive another by default. The escape hatch is a temporary-exception entitlement that names the specific apple-events targets the app needs to send to.

In NightGard_Library_Commander.entitlements you'll find the com.apple.security.temporary-exception.apple-events key with an array containing com.apple.Music. That single line is what makes the AppleScript pipeline work inside the sandbox. Apple reviews these temporary exceptions case-by-case during App Store review — you have to justify the use case in the App Review notes (Library Commander's note is short: "writes metadata back to Apple Music tracks the user already owns; no third-party data collection"). Apple has a track record of approving the exception when the use case is honest and narrow.

The lesson: sandboxed Mac App Store apps can still drive other apps via AppleScript, but you have to declare the targets up front and survive the App Review conversation about why you need them. Get the use case into one sentence before submitting; reviewers don't read paragraphs.

Security-scoped bookmarks

The user picks a working folder once (a music library folder, a backup destination, a cleaned-output target). A regular NSOpenPanel grants access only for that session — on next launch, the folder URL is no longer usable. Sandboxed apps don't get to reach into arbitrary disk paths.

The fix is a security-scoped bookmark. After the user picks the folder, Library Commander calls url.bookmarkData(options: .withSecurityScope, ...) and persists the resulting Data in UserDefaults or SwiftData. On next launch, the persisted data is resolved with URL(resolvingBookmarkData:options:[.withSecurityScope]...) and the URL is bracketed by startAccessingSecurityScopedResource() / stopAccessingSecurityScopedResource() calls during reads.

The pattern is bureaucratic but important to learn correctly — getting it wrong on a sandboxed app means the app silently fails to read folders the user clearly granted access to, and the failure mode is "nothing in the folder shows up" rather than an obvious error message.

The two-service split

Library Commander has two services in the Services/ folder:

  • LibraryService.swift — talks to Apple Music via AppleScript to read tracks, identify problem-state items (missing metadata, broken file references), and write fixes back to the library entries in place.
  • PlaylistLockerService.swift — manages a separate "locker" of playlists that should not be modified by automated cleanup. The user marks specific playlists as locked; the cleanup pipeline skips items in those playlists.

The split is one of the chapter's clearest production-scale lessons: name your services around what they own. LibraryService owns the connection to Apple Music; PlaylistLockerService owns the locked-list state. Mixing those concerns into a single service would have made testing harder and made the boundaries fuzzier as the app grows.

The four-pane view layout

The main window has four panes, each its own @MainActor SwiftUI view in Views/:

  • LibraryPaneView — the track list, filterable by problem state (missing artist, missing artwork, broken reference, etc.)
  • LockerPaneView — the locked-playlists configuration
  • PlaylistsPaneView — the user's full playlist roster
  • StatsPaneView — the running summary of what's been cleaned, what's remaining, what skipped because of locker rules

The user navigates between panes via a sidebar, classic Mac-app shape. Each pane stays in its own file; cross-pane communication happens through the shared services and SwiftData model context, not through inter-view bindings.
