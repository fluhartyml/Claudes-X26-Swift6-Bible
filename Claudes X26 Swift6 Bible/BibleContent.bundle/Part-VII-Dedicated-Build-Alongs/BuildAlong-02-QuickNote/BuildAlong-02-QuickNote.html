VII.2  Appendix: QuickNote — From Brainstorm to App Store

This appendix walks through the complete lifecycle of an iOS app — from the first brainstorm to App Store submission, rejection, and resubmission. QuickNote by Claude is a real app you can download. Every decision, every mistake, and every fix is documented here because that's how software actually gets built.

VII.2.1  The Brainstorm

VII.2.1 ¶1 QuickNote started as the Swift reference's first example app. Dual purpose: a teaching vehicle for the book AND a real App Store utility. Not a throwaway exercise — a published app that readers can download and compare against the source code.

VII.2.1 ¶2 v1.0 spec:

VII.2.1 ¶3
  • Text notes with titles and dates
  • SwiftData persistence
  • iCloud sync
  • Share sheet
  • Multiplatform (iOS, iPadOS, macOS)
  • Pre-dating: place notes on your future timeline (doctor visits, grocery runs)
  • Sort by dateCreated descending, not dateModified

VII.2.1 ¶4 v2.0 deferred: Camera, document scanner, OCR (VisionKit chapters). Each Swift Reference example app gets revisited when later chapters add relevant features.

VII.2.2  The Data Model

VII.2.2 ¶1 Four properties, in this order everywhere:

VII.2.2 ¶2
@Model
final class Note {
    var title: String
    var dateCreated: Date
    var body: String
    var dateModified: Date

    init(title: String = "", dateCreated: Date = .now,
         body: String = "", dateModified: Date = .now) {
        self.title = title
        self.dateCreated = dateCreated
        self.body = body
        self.dateModified = dateModified
    }
}

VII.2.2 ¶3 dateCreated is user-editable — the DatePicker lets you pre-date or back-date. dateModified updates automatically via .onChange modifiers on the title, date, and body fields.

VII.2.3  Build Errors That Taught Something

VII.2.3 ¶1 These aren't bugs — they're lessons. Each one appears in the relevant chapter earlier in this book and is collected here for reference.

VII.2.3.1  1. Date.FormatStyle Properties Aren't Assignable

VII.2.3.1 ¶1 What happened: Tried to build a custom date format using Date.FormatStyle property chaining. The properties are read-only — you can't assign to them.

VII.2.3.1 ¶2 Fix: Use DateFormatter with a dateFormat string:

VII.2.3.1 ¶3
let quickNoteDateFormatter: DateFormatter = {
    let f = DateFormatter()
    f.dateFormat = "yyyy MMM dd HHmm"
    f.locale = Locale(identifier: "en_US_POSIX")
    return f
}()

VII.2.3.1 ¶4 See: Chapter 2, Date Formatting section.

VII.2.3.2  2. DateFormatter Returns Title Case

VII.2.3.2 ¶1 What happened: DateFormatter returns "Apr" not "APR". The design called for uppercase month abbreviations.

VII.2.3.2 ¶2 Fix: .uppercased() on the formatted string.

VII.2.3.2 ¶3
Text(quickNoteDateFormatter.string(from: note.dateCreated).uppercased())

VII.2.3.3  3. NavigationSplitView Sidebar Truncation

VII.2.3.3 ¶1 What happened: Long note titles got cut off in the sidebar because NavigationSplitView defaults to a narrow column width.

VII.2.3.3 ¶2 Fix: .navigationSplitViewColumnWidth(min: 350, ideal: 380)

VII.2.3.3 ¶3 See: Chapter 5, NavigationSplitView section.

VII.2.3.4  4. TextField(axis: .vertical) Treats Return as Submit

VII.2.3.4 ¶1 What happened: Used TextField(axis: .vertical) for the note body. Pressing Return exits the field instead of creating a new line.

VII.2.3.4 ¶2 Fix: Use TextEditor for real multiline input. TextField is for single-line input, even with the vertical axis hint.

VII.2.3.4 ¶3 See: Chapter 9 (Text & TextField) and Chapter 10 (TextEditor & AttributedString).

VII.2.3.5  5. App Name Conflicts

VII.2.3.5 ¶1 What happened: "QuickNote" was already taken on the App Store. Archive > Validate App caught it.

VII.2.3.5 ¶2 Fix: Renamed to "QuickNote by Claude" in the Display Name field. The bundle ID stayed com.ClaudeX26Bible.QuickNote.

VII.2.3.6  6. Missing App Icons Fail Validation

VII.2.3.6 ¶1 What happened: Validate App failed because the asset catalog was missing the required icon sizes — 1024x1024 for iOS and all sizes for Mac.

VII.2.3.6 ¶2 Fix: Add the icons to the asset catalog before archiving. Xcode won't warn you during development — only during validation.

VII.2.3.7  7. Simulator Screenshots Don't Match App Store Sizes

VII.2.3.7 ¶1 What happened: iPhone simulator screenshots are 1320x2868. App Store Connect requires 1284x2778 for the 6.5" display.

VII.2.3.7 ¶2 Fix: Batch resize with sips:

VII.2.3.7 ¶3
sips -z 2778 1284 screenshot.png --out screenshot.png

VII.2.3.8  8. Export Compliance

VII.2.3.8 ¶1 What happened: App Store Connect asks about encryption every time you select a build. For a notes app: "None of the algorithms mentioned above."

VII.2.3.9  9. Privacy Policy URL Requires HTTPS

VII.2.3.9 ¶1 What happened: Entered an http:// URL for the privacy policy. App Store Connect requires https://.

VII.2.3.9 ¶2 Fix: Host the privacy policy on the app's GitHub wiki — GitHub provides HTTPS by default.

VII.2.3.10  10. Do App Privacy + Pricing BEFORE Distribution Metadata

VII.2.3.10 ¶1 What happened: Filled out the Distribution page first (screenshots, description, keywords). Hit Save. Nothing saved. No error message.

VII.2.3.10 ¶2 Fix: Complete App Privacy and Pricing sections first. The Distribution page won't save until those are done. App Store Connect doesn't tell you this — it just silently fails.

VII.2.3.11  11. App Store Connect Caches Errors

VII.2.3.11 ¶1 What happened: Fixed an issue, went back to the submission page. The error was still showing.

VII.2.3.11 ¶2 Fix: Refresh the browser page. App Store Connect caches aggressively.

VII.2.4  The Rejection

VII.2.4 ¶1 QuickNote v1.0 was rejected under Guideline 4.2 — Design: Minimum Functionality.

VII.2.4 ¶2 > The usefulness of the app is limited by the minimal functionality it currently provides. Specifically, the app primarily offers content for users to view or use, but there isn't enough of this content currently available in the app to make it useful to users.

VII.2.4 ¶3 Translation: a notes app that just creates, edits, and deletes text notes isn't enough. Apple Notes already does that. What makes yours different?

VII.2.4.1  The Fix

VII.2.4.1 ¶1 Three features added in response:

VII.2.4.1 ¶2
  1. Under the Hood tab — a source code browser that displays every Swift file in the app. Pop the hood, see the engine. The book (this book) is the Chilton's manual. The app is the car.
VII.2.4.1 ¶3
  1. Home screen widget — shows the 3 most recent notes. Built with WidgetKit (see Chapter 16). Uses SwiftData to read from the same store as the main app.
VII.2.4.1 ¶4
  1. Contact Developer — a feedback form that composes a mailto: URL with the user's message and device info. Same pattern used in CryoTunes Player.

VII.2.4.1 ¶5 The app category was also changed from Utilities to Education to match the teaching purpose.

VII.2.4.2  The Resubmission

VII.2.4.2 ¶1 App Review notes explained exactly what changed and why:

VII.2.4.2 ¶2 > This app was previously rejected under Guideline 4.2 (Minimum Functionality). We have added the following features in response: > 1. Under the Hood tab — users can browse the app's own Swift source code > 2. Home screen widget — displays the 3 most recent notes > 3. Contact Developer — built-in feedback form > This app serves as a companion app for an iOS development book.

VII.2.4.2 ¶3 Build number gotcha: The new build wasn't immediately available in App Store Connect after uploading from Xcode. There's a processing delay — sometimes a few minutes. If you rush to resubmit, you might grab the old build by accident. Wait for the new build number to appear in the Add Build dialog.

VII.2.5  The Reject-and-Resubmit Strategy

VII.2.5 ¶1 Sometimes an app sits in "Waiting for Review" for days with no movement. This happened with Tally Matrix Clock — all rejection issues fixed, resubmitted, and then silence for two days.

VII.2.5 ¶2 The fix: Developer Reject your own submission, then resubmit. This puts you into a fresh review queue.

VII.2.5 ¶3 How to do it:

VII.2.5 ¶4
  1. Go to App Store Connect > Your App > App Review
  2. Click on the submission that's stuck
  3. Scroll to the bottom — click "Cancel Submission"
  4. Confirm the cancellation
  5. Status changes from "Waiting for Review" → "Processing" → "Developer Rejected"
  6. Now go to Distribution, attach the new build, and submit again

VII.2.5 ¶5 You'll land in a different reviewer's queue. This isn't gaming the system — Apple expects developers to use this when submissions stall.

VII.2.6  Lessons for All Example Apps

VII.2.6 ¶1 Every Swift Reference example app will face these same hurdles. Plan for them:

VII.2.6 ¶2
  • Minimum functionality — a utility app needs more than just CRUD. Add a widget, add a Learn tab, add something that differentiates it.
  • Apple trademark compliance — don't use "Apple TV," "iPhone," or other Apple trademarks in your subtitle or promotional text. Use "your TV" or "your phone."
  • Screenshots must match App Store dimensions — simulator screenshots won't be the right size. Keep sips in your toolbox.
  • Build numbers must match — if your app embeds an extension (widget, share extension), both must have the same CFBundleVersion.
  • Do privacy and pricing first — before touching the Distribution page.
  • The review queue can stall — give it 48 hours, then reject and resubmit.

VII.2.7  v1.1 — The Widget Fix and Photo Attachments

VII.2.7 ¶1 QuickNote v1.0 shipped with a broken widget. The widget showed "No Notes" even when the app had notes. Apple didn't catch it during review — they likely didn't test adding a note and checking the widget.

VII.2.7.1  The Bug

VII.2.7.1 ¶1 The widget extension and the main app were using separate SwiftData stores. Each target created its own ModelContainer with no shared location:

VII.2.7.1 ¶2
// v1.0 — BROKEN: each target gets its own private database
let config = ModelConfiguration(schema: schema, isStoredInMemoryOnly: false)

VII.2.7.1 ¶3 The app wrote notes to its sandbox. The widget read from its own sandbox. Two empty rooms in the same building with no hallway between them.

VII.2.7.2  The Fix: App Groups + groupContainer

VII.2.7.2 ¶1 Three things had to happen:

VII.2.7.2 ¶2
  1. Register an App Group on developer.apple.com — group.com.ClaudeX26Bible.QuickNote
  2. Enable App Groups in Xcode's Signing & Capabilities for both the app and widget extension targets
  3. Use groupContainer in the ModelConfiguration:
VII.2.7.2 ¶3
// v1.1 — FIXED: both targets share the same database
let config = ModelConfiguration(
    schema: schema,
    groupContainer: .identifier("group.com.ClaudeX26Bible.QuickNote")
)

VII.2.7.2 ¶4 That single parameter change — groupContainer: .identifier(...) — tells SwiftData to put the database in the shared App Group container instead of each target's private sandbox.

VII.2.7.2 ¶5 The widget also needed WidgetCenter.shared.reloadAllTimelines() called after every note insert, edit, and delete so it refreshes immediately instead of waiting 30 minutes.

VII.2.7.3  Debugging the Fix

VII.2.7.3 ¶1 The fix didn't work on the first try. Three attempts:

VII.2.7.3 ¶2
  1. Manual URL approach — built the container URL with FileManager.default.containerURL(forSecurityApplicationGroupIdentifier:) and appending(path:). SwiftData couldn't find the store.
  2. Named ModelConfiguration — added a name parameter. Caused a mismatch between app and widget.
  3. groupContainer: .identifier(...) — the API SwiftData actually provides for this exact use case. Worked immediately.

VII.2.7.3 ¶3 The lesson: don't build your own paths when the framework has a dedicated API. The groupContainer parameter exists because Apple knew developers would need to share data between app and extension targets.

VII.2.7.4  Photo Attachments

VII.2.7.4 ¶1 v1.1 also added photo attachments:

VII.2.7.4 ¶2
  • PhotosPicker from PhotosUI for selecting library images
  • Camera capture via UIImagePickerController wrapped in UIViewControllerRepresentable
  • Images stored as [Data] with @Attribute(.externalStorage) so binary data doesn't bloat the SwiftData row
  • Adaptive grid display above the note body with per-image delete buttons

VII.2.7.4 ¶3 The model gained one property:

VII.2.7.4 ¶4
@Attribute(.externalStorage) var imageData: [Data]

VII.2.7.4 ¶5 This is a schema change — existing installs need to delete and reinstall to migrate. For a production app with users, you'd write a migration plan. For a v1.1 with one user (the developer testing it), a fresh install is fine.

VII.2.7.5  What v1.1 Teaches

VII.2.7.5 ¶1
  • App Groups are not optional for extensions — if your extension needs app data, configure this from day one
  • The developer portal and Xcode must agree — register the group online, then add it in Signing & Capabilities
  • Don't ship features you haven't tested end-to-end — the widget looked correct in the preview but was broken on the home screen
  • @Attribute(.externalStorage) keeps binary data efficient in SwiftData
  • PhotosPicker is the modern replacement for UIImagePickerController — except for camera, which still needs the UIKit bridge

VII.2.8  The "by Claude" v2.0 submission — cancelled, preserved as GitHub clone-and-build

VII.2.8 ¶1 Late on 2026 April 28, Audio Universe was rejected under App Store Guideline 4.1(a) Design (Copycats) for the explicit "by Claude" attribution in its display name. QuickNote v2.0(2) had already been submitted earlier the same day under the same naming form ("QuickNote by Claude") and was sitting in the Waiting for Review queue. The pattern was clear: a different reviewer pulling QuickNote next would almost certainly apply the same 4.1(a) reading.

VII.2.8 ¶2 Rather than wait for the predictable rejection, the v2.0(2) submission was cancelled by the developer in App Store Connect before a reviewer claimed it. This was the cleanest path forward — cancel before review, rename, resubmit fresh. Per the reusable rule (saved at feedback_app_store_withdraw_resubmit.md in the apartment memory), withdrawing a problem submission and resubmitting a new build that addresses the issue beats Reply-to-App-Review for almost every kind of name-or-metadata trip.

VII.2.8 ¶3 The renamed version that ships shortly thereafter carries the bare or developer-attributed display name (the family-wide rule landed on no "Claude" in App-Store-reviewer-visible name fields, with optional by Fluharty attribution where the bare name collides with existing apps). The "by Claude" lineage exists only in the source repository's commit history.

VII.2.8.1  What the by-Claude v2.0 source contained

VII.2.8.1 ¶1 The source on disk at the moment of cancellation was the v2.0 modernization complete: terracotta accent color, light-and-dark icon set, host + widget extension version aligned at 2.0 build 2, deployment-target raised to iOS / macOS 26.2, the Under the Hood retool to the AU pattern, the new About sheet, and the Lexicon Quick-Define wiring (LexiconContent + LexiconSheet + IdentifierTaggedSourceView ported from LockBox). All shipping-quality work; the only thing that didn't ship under "by Claude" was the App Store record.

VII.2.8.1 ¶2
  • INFOPLIST_KEY_CFBundleDisplayName set to "QuickNote by Claude" in both Debug and Release configurations
  • AboutView title text reading "QuickNote by Claude"
  • ContactDeveloperView mail subject and device-info label both referencing "QuickNote by Claude"
  • Under the Hood callouts and source-mirror file headers carrying the same attribution

VII.2.8.1 ¶3 The rename to drop "by Claude" from those reviewer-visible fields was a string-only edit pass — same shape as the Audio Universe rename, same lesson: keep your display-name surface separable from your app's identity in source. A naming policy shift should not require an architectural refactor.

VII.2.8.2  Cloning the by-Claude version

VII.2.8.2 ¶1 The "by Claude" source lineage is preserved in the public commit history at github.com/fluhartyml/QuickNote. To clone the cancelled-version source for study or your own modification:

VII.2.8.2 ¶2
  1. Open Xcode and choose Source Control → Clone; paste the repo URL above. See Book 21 Git-And-GitHub for the clone walkthrough.
  2. The latest commit on main reflects the renamed bare-name version. Use the commit-history view to find the last commit before the rename pass (search the log for "QuickNote by Claude" to locate the boundary) and check it out into a worktree.
  3. Build and run on your own device. The notes-and-photos functionality, the widget extension, the App Group container, and the home-screen widget all behave identically to the App Store version; only the display strings differ.

VII.2.8.2 ¶3 This version is not appropriate to resubmit to the App Store under the "by Claude" name — the family-wide naming rule moved on, and the same 4.1(a) wall awaits any new submission that puts "Claude" in the reviewer-visible name. Treat the cancelled lineage as a study artifact, not a starting point for a new submission. The license remains GPL v3 with attribution.

VII.2.8.3  Why this beat lives in the chapter

VII.2.8.3 ¶1 QuickNote's two App Store interactions in 24 hours — submit-and-cancel as "QuickNote by Claude," then resubmit under the renamed form — are an honest snapshot of how a working developer's day goes when policy guidance shifts. The book's no-mistake-teaching rule means we don't dwell on the rejection-as-failure narrative; we dwell on the recovery as a teachable habit. Cancel-before-review when the wall is predictable. Keep your display name separable from your source. Have your rename pass scoped to a handful of plist keys and string literals, not threaded through the codebase. The chapter shows the v2.0 build as it shipped; this section preserves access to the version Apple wouldn't accept.

VII.2.8.3 ¶2 QuickNote is available on the App Store under its current naming. Download it, open the Under the Hood tab, and follow along with this appendix. The "by Claude" lineage available via GitHub clone is the alternate path described in the section above.
